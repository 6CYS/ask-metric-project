## 3. 引用契约与兼容（复查后更新）

现行正文引用使用 `{{e1.v1}}`；已经写明数值时，在同段使用 `{{e1.v1|cite}}` 关联依据，最终不展示引用标记。机构、正式指标、统计日、单位及数值来自已授权事实，计算结果沿用经过核验的计算原子。

本轮撤回强制手抄 `org/metric/date` 的要求。上轮运行提示及工具要求完整坐标，但实际可读的 `inquiry-analysis` 技能仍使用短引用，造成合法追问在交付阶段失败。坐标一致也不能证明自由文字中的机构、日期或业务判断正确，继续强制声明没有充分收益。

- 保留完整旧坐标的解析和一致性核对，仅用于在途调用兼容；未提供时不补造声明、不拒绝短引用。
- 字面数值只匹配本段引用或旧章节显式关联的依据，包含计算和判断所依赖的原始事实；不再借用其他段落声明的数字。
- 残缺引用、部分坐标属于 `FORMAT`，未知引用或完整坐标矛盾属于 `REFERENCE`，数值与本段依据不符属于 `NUMBER`。这些是协议、来源和数值边界，不按自然问句增加分支。
- 保持原有两次回答预算。格式错误先局部修正；数值恢复仍从授权事实重新生成，并受尚未解决的来源、范围及权限错误约束。没有增加格式失败的自动事实兜底。
- 正常缺数、模型服务异常和回答整理失败分别交付。前端共享接收器同时处理实时与历史的版本化终态，不把内部失败回执解释为成功业务结果。
- 历史已交付正文继续回放，无数据库迁移。Agent 在启动时加载技能，代码与技能须一同重启生效；后端同时部署对应实现。旧传输上限保留兼容，后端正文上限不变。

## 6. 性能结论

**本轮没有证据证明整体变快，也没有达到“与 MFWS 效果相当且明显更快”的验收结论。** T08 完成的是分阶段测量、本次重复实现和恢复状态的收敛及真实对照；不能将它表述为性能问题全部解决。

工具时间包含目录、后端取数、授权与报告校验，不等于 SQL 时间。改后各场景模型首 token 等待合计约 5.02—10.30 秒，是模型调用总时间的子集，不能再次相加。正文仍在核验后交付，`first_visible_ms` 接近结束时间；前端实际按回执展示进度，没有人为延迟或动画伪装提速。

A2 的额外目录查询与数字修正、A3 的事实重读/计算及数字修正、B1 的参考日期补查均可从回执追踪。A3 基线的 3.67 秒是绕过证据校验的错误路径，不能作为应恢复的性能目标。B1 改后比基线多交付了参考排名及图表，也不是等量工作比较。

缓存未强制清空，模型缓存命中和服务端负载不可控；统计时间跨午夜，但问题都使用明确的绝对日期。这里只报告单次样本，不计算 P95，也不将差异全部归因于代码。未调大超时、放开推理、删除权限或新增二次审核模型来改善数字。

后续性能工作的已有证据指向首次正文引用成功率及不必要的模型往返。应先测量再修改，不能通过放行无来源金额、按问题句式走捷径或隐去失败来“提速”。

- 本轮形成了可定位、可验证的实现边界，后续开发继续遵循同一流程：定位职责与证据 → 修改对应实现 → 退出被替代代码 → 验证受影响类别。现有局限不转换成新的词语白名单，也不扩成通用审核框架。
