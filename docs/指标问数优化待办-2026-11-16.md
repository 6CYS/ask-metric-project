# 指标问数优化待办

日期：2026-11-16。代码参考：`develop-ws`，提交 `ea964a1`。

目标：优先提高日常问数和连续追问的正确性、稳定性，再处理有实际证据的等待时间与能力缺口。近期从现有测评中心和真实失败记录入手，暂不扩大界面改版或新功能范围。

以下任务均待执行。代码检查发现的改进机会不等于已经确认的业务故障；是否实施、具体范围和顺序，应根据真实基线结果调整。

## 执行顺序

| 顺序 | 待办 | 启动条件 | 交付物 |
| --- | --- | --- | --- |
| 1 | T01 建立真实问数基线 | 优先开始 | 可复用的问题集、复核结果与失败排序 |
| 2 | T02 修复最影响使用的实际问题 | T01 找到可复现问题 | 聚焦根因的修复与同类回归证据 |
| 3 | T03 核实比较日期和指标频率 | 随 T01 核查，有缺口再改 | 明确的比较、趋势期间规则及验证结果 |
| 4 | T04 缩短已核验正文的等待 | 分段计时确认存在可减少的等待 | 同条件前后对照与最小链路改动 |

## T01 建立真实问数基线

- [ ] 从日常高频问题、已有会话和已发生的失败中选取一批代表性题目，复用[测评中心](测评中心使用说明.md)，保留首问和后续追问的完整顺序。
- [ ] 覆盖查值、换机构、改日期、改指标、追加比较、趋势、较早历史回指，以及未找到指标、部分缺数和服务异常。选用当前真实可用的指标与机构，不为凑题目编造业务数据。
- [ ] 逐题核对用户目标、实际查询条件、来源、数值、单位、计算和最终表达。缺数时核对是否准确说明范围；模型生成了答案、工具执行成功不能直接记为业务通过。
- [ ] 记录代码版本、实际生效的模型和配置、权限范围、数据条件、工具调用及耗时。区分模型首个输出、首段有效正文和完整结束；现有服务端发送计时不能直接当成浏览器可见时间。
- [ ] 按业务影响、复现频率和首次偏离环节整理失败；数据或服务不可用单独记录，不混入语义正确率，也不当作通过。

**验收：** 每题有通过、未通过或待复核结论及依据；每个待修问题能定位到理解、目标继承、查询执行、计算或交付环节。输出下一批最值得修的问题，不以少量成功样例宣称整体准确率。

**已有基础：** 已有多轮问题集、人工复核和版本对比能力；仓库也有题集，可筛选复用，不能未经业务核对直接当作标准答案。先完成这一步，无需另建测评系统。

## T02 修复最影响使用的实际问题

- [ ] 从 T01 中选择高影响、反复出现的问题，先核对真实会话与调用链，再确定修改模块。
- [ ] 优先纠正错误状态或数据契约，删除、合并无依据或重复校验；保留权限、正式指标、来源、单位精度和计算保护。
- [ ] 每类修复同时验证原问题、必要的换机构或换日期表达、连续追问，以及应拒绝或应说明缺数的路径。
- [ ] 复核当前“首次检索加一次扩展仍无候选”的收尾行为：无进展及时结束，已有结果保留，确有证据缺口时仍允许预算内定向补查。

**验收：** 原问题及同类变化有可核对的结果；说明修正的根因、收敛的限制、保留的保护和未覆盖范围。不能靠原句白名单、追加关键词或软化报错文案代替修复。

## T03 核实比较日期和指标频率

- [ ] 用真实数据分别核对“同一日期比较”“各自最新值”和“用户指定日期”。多机构日期不齐时，不静默换日期或把不同日期的值当成同日比较。
- [ ] 如普通问数确需共同可用日期，优先复用主题查询已有能力，保留范围、分页和预算约束；共同日期可能更早，回答应说明实际采用日期。
- [ ] 核对实际生效的指标频率和数量性质配置，再验证日、月、季、年指标的趋势与同期计算。季度指标没有月度记录，不应直接解释成月度数据缺失。

**代码依据：** 普通 `metric_availability` 使用 `match: "any"`；主题查询已有基于 `match: "all"` 的共同日期计算。趋势执行的一条路径按月取最后有效观测；语义模型已有 `frequency`、`quantity_kind` 字段。需要结合实际配置和调用路径确认是否影响现有业务，不能据此断言当前比较全部错误。

**验收：** 指定日期保持不变；共同日期存在、不存在及各自最新值均有正确表达；趋势粒度与已确认业务频率一致，不补零、不凭名称猜频率。配置加载需核对实际来源，不能只看仓库 JSON 判断运行时配置是否完整。

**定位：** `agent-service/src/inquiry/queryTools.ts`、`agent-service/src/inquiry/topics/tool.ts`、`backend-next/src/ask_metric/application/metric_semantics.py`、`backend-next/src/ask_metric/application/analysis_execution.py`。

## T04 缩短已核验正文的等待

- [ ] 对简单查值和带图分析分别采集分段耗时，区分上游模型等待、查询、正文校验、图表准备和前端展示。保持比较时的模型、配置、问题与数据条件可比。
- [ ] 若图表准备确实阻塞已核验正文，调整为正文先交付，图表随后补齐；正文仍须通过必要的事实与来源核验。
- [ ] 检查取消、后续正文修订、图表失败、刷新历史和最终保存，确保没有重复内容、旧图错挂或正文与图表使用不同数据。

**代码依据：** `agent-service/src/inquiry/reportTool.ts` 的预览路径在正文校验成功后仍等待 `buildInquiryChart`；这是可优化的位置，但尚未测得实际收益，也不能解决上游模型本身的等待。

**验收：** 使用同类问题多次对照，报告首段有效正文与总耗时的实际变化、失败情况和样本量；单独说明服务端发送与浏览器可见时间。无图查询不退化，已有保护和最终结果保持一致。不预先承诺固定秒数或提升比例。

## T05 持续积累真实案例和已验证方案

- [ ] 先用现有测评中心把真实问题及人工确认的预期纳入回归，记录配置和数据条件；相似问题去重，保留有意义的上下文变化。
- [ ] 对高频且口径稳定的业务问题，复用现有业务主题或方案维护入口，明确正式指标、适用范围、期间规则、计算方法与版本。
- [ ] 当人工整理成为实际负担时，再考虑从会话直接提交问题到测评的轻量入口；业务反馈先复核，不直接变成全局规则。
- [ ] 将独立验收题与运行时示例区分开，避免把记住题目误当成理解能力提升。

**验收：** 真实反馈能追溯到原会话和核验依据；已验证方案在换机构、换日期后仍查询真实授权数据，不缓存旧答案冒充新结果。现有流程能完成时，不新增后台系统或页面。

## T06 按实际需要支持批量计算

- [ ] 先统计真实高频分析是否因多个逐项计算调用耗尽预算、导致必要结果未交付；若没有实际影响，保持后置。
- [ ] 需要时扩展现有计算工具为有界批量输入，逐项返回成功、缺数或不适用原因，兼容单对计算。
- [ ] 复用原始事实引用和现有计算规则，保留权限、同指标、日期可比性、比例编码、零或负基期及精度保护。

**代码依据：** `agent-service/src/inquiry/calculationTool.ts` 当前一次接收一对 `current_ref`、`base_ref`；工具调用预算可能限制大量比较。但减少工具调用不等于按相同数量减少模型轮次，不能据此直接承诺响应提速。

**验收：** 对受影响的真实问题核对结果完整性、调用数量与耗时；某项失败不丢失其他有效结果。不得只扩大总预算来掩盖重复工作。

## 保持的产品约束

- 执行过程默认展开，保留实际耗时、指标、机构和数据日期；本待办不安排整体界面重设计。
- 进展文案面向业务用户；正常无数据、部分可用与执行失败分别表达，不把失败伪装成成功。
- 优先复用正式指标、受治理查询、现有计算、业务方案和测评能力；不另建自由 SQL 查询链路或通用审核系统。
- 真实业务验收使用已有真实数据、实际模型及执行链路；隔离单元测试不能代替真实业务验收。
