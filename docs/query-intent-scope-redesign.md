## 1. 目标与已核实的问题

目标：对“查询2026年4月末各家农商行信贷客户数量当日数前3名”及同类查询，系统能保留全部业务条件，在当前账号权限内确定正确机构层级、日期和排名规则，再执行受控查询。真正有歧义才询问用户；内部参数错误由系统处理；失败不能通过缩小或扩大条件伪装成成功。

用户已确认：“各家农商行”指当前账号权限内可查看的农商行。授权集合可能含省级汇总、法人行和支行，不能把权限内全部节点直接混在一张法人行榜单里。

2026-09-22 09:00 本地会话回执已核实：指标匹配成功，日期解析为 2026-04-30；机构原文“各家农商行”返回 not_found；Pi 同时提交 selection=exact、order=desc、top_n=3；Validator 返回 NEEDS_CLARIFICATION，未调用执行工具。

代码核查还发现：

- `agent-service/src/business-context/capabilities.ts` 将日期取值与排名放在同一 selection 枚举中，机构字段只表达名称/候选，排名强制一个范围机构。
- `backend-next/src/ask_metric/api/routes/business_context.py` 先做目录权限过滤，再把集合短语交给具体名称匹配，缺少集合解析协议。
- `backend-next/src/ask_metric/domain/basic_query.py` 的 org_codes 在普通查询中表示实际查询对象，在排名中表示上级范围机构，空数组又表示缺省范围。
- `application/ports.py` 会把非管理员的空机构补为本人机构；`query_execution_service.py` 随后扩展该机构的直接下级。空数组对不同身份的实际排名范围不一致，不能拿它作为新集合语义的补丁。
- 通用权限服务支持配置中的全机构授权，排名分支还会单独调用 allowed_org_codes；授权算法分散，需要统一并用契约测试约束。
- `infrastructure/db/org_hierarchy.py` 在层级不完整时，会以名称含“全省汇总”的节点为根、把其他启用机构作为其下级；即便有唯一根，现有判断也不等于已验证无环和完整父链。新集合排名不能直接继承该宽松回退。
- `business-context/core.ts` 将字段和交叉校验问题合并为待澄清；`harnessHost.ts` 对待澄清禁用工具，内部可纠正错误也会落入等待用户的路径。
- `backend-next/tests/test_ranking_regressions.py` 主要覆盖旧 SemanticEngine/SlotFrame 及查询计划，不能证明 Pi → Business Frame 新入口正确。

## 2. 改造边界

保留 Pi 的语义理解、多轮 Frame、目录匹配、SQLGlot builder、后端鉴权、幂等和结果快照。改造意图字段、范围解析、规范化查询计划和错误协议；不在通用上下文核心增加“各家农商行”“前三名”等自然语言特判。

由 Pi 理解业务目标；服务端确定实体、日期、层级、授权和可执行组合。无需再增加一个全面重解析用户问题的模型链路。提示词与示例从新契约更新，但不承担权限和数据正确性保证。

“彻底”在此指消除已确认的结构缺陷，并为同类问题建立可验证的边界；不承诺任意自然语言一次理解正确。模型遗漏目标仍须通过意图证据、受控纠错和真实模型验收发现，不能只凭 JSON 合法就宣称语义正确。

## 3. 将业务条件拆成独立维度

新增版本化 Query Intent 契约，把以下维度分开：

| 维度 | 职责 | 本次示例 |
| --- | --- | --- |
| metrics | 引用目录算法匹配的指标 | 信贷客户数量当日数 |
| organization_scope | 表达具体对象、集合或下级范围 | 当前账号可见的农商行同级集合 |
| time | 日期原文、解析结果、时间取值方式 | 2026年4月末；指定日 |
| operation | 取值或排名等已支持操作 | 按机构排名 |
| ranking | 排序方向、条数、分组/排序依据 | 降序、每榜最多3条 |

time 的 exact/latest_in_range/all_in_range 不再与 operation=ranking 互斥。时间解析仍由既有 DateResolver 完成；Pi 不自行生成可信日期。

Pi 提交的是原文证据和结构化意图，不能提交可信授权结果。下面仅表示解析后的目标，不是新增接口的最终字段定稿：

```json
{
  "schema_version": 2,
  "metrics": "引用本轮目录算法结果",
  "organization_scope": {
    "kind": "authorized_cohort",
    "cohort": "rural_commercial_banks",
    "source_text": "各家农商行"
  },
  "time": {
    "source_text": "2026年4月末",
    "selection": "exact",
    "resolved": {"start": "2026-04-30", "end": "2026-04-30"}
  },
  "operation": "ranking",
  "ranking": {"direction": "desc", "limit": 3, "source_text": "前3名"}
}
```

来源证据必须来自当前用户原文、可信父 Frame 或已配置且公开的缺省规则；区分 explicit、inherited、defaulted。证据片段存在只能证明来源，不能证明语义映射必然正确。指标名称内部的“排名”“增幅”等保留为指标名称，不自动转成操作。

排名参数采用判别联合：value 没有 ranking 参数，ranking 必须有有效参数或明确的缺省来源。服务端不得通过丢弃 top_n、改成普通查询来“修复”冲突。

## 4. 机构范围成为有类型的业务对象

### 4.1 三种范围与缺项严格区分

| 范围 | 示例 | 服务端行为 |
| --- | --- | --- |
| explicit_entities | 甲行和乙行 | 逐一解析名称，逐一校验权限；任一不可用不能静默只查其余机构 |
| authorized_cohort | 各家农商行、权限内各行 | 根据正式层级/类别定义生成同级集合，与当前授权取交集 |
| children_of | 某行下属各支行 | 解析上级与目标层级，展开指定关系，再按授权取交集 |

没有表达范围、来源不明的“这些行”、未知具体名称都不是 authorized_cohort。不能将“找不到机构”降级为查询所有可见机构。“我行”“本行”可作为 actor 绑定的主体引用，不接受模型自报所属机构。

cohort 的定义必须复用正式目录和治理层级：当前已有省级根机构及其直接下级约定，先核查是否完整对应法人农商行。若目录有可靠类别/层级字段则使用它；若只能通过受治理根节点定义则显式登记该定义。缺失或不一致返回配置错误，不能靠名称后缀、出现“汇总”与否猜层级，也不能临时改排支行。

新 Scope Resolver 使用严格的目录快照：验证父节点存在、无自环/循环、目标集合可达且层级/类别一致；同步中间态不能发布为新可用版本。迁移调用方后删除现有按名称猜根并展开全部节点的逻辑；授权与目录读取基于同一个可用快照，避免多次读取恰逢同步导致集合混合。

### 4.2 一处产生授权后的目标集合

新增/提取统一 Scope Resolver，覆盖解析、计划、执行和结果回读的权限判定来源：

```text
目标机构集合 = 正式目录中满足用户范围和层级的启用机构 ∩ 当前账号授权机构
```

先确定业务候选，再按同一授权服务裁剪，再对授权集合取数和排名。账号身份、管理员规则、省级配置授权均由服务端提供。集合裁剪与显式越权拒绝继续保持不同语义。

规范化后记录 scope kind、治理定义版本、授权后机构编码、集合摘要及授权上下文指纹；不把未授权候选或其数量暴露给用户。大集合留在服务端，不塞进模型上下文、不因工具数组上限截取前100个机构；执行层用完整集合或服务端范围引用，并实施明确的查询资源限制。

READY 不代表永久授权。执行前重新解析启用状态与授权：若与准备时集合一致则执行；不一致返回可识别的 SCOPE_CHANGED，失效旧计划，由本轮意图重新准备，不能沿用旧编码或旧幂等结果执行。结果回读同样复查权限。

授权复核以服务端权限版本/规范化指纹作为一致性依据：开始取数前验证，完成取数且发送第一字节结果前再次验证；版本变化则本次结果不发布、标记失效，重新授权后准备新计划。该保证的生效点是响应发布前，已发出的历史内容不能被事后“收回”。不提供业务行的提前流式输出。历史榜单任何组成机构失权时整体拒绝回放，不能仅删去越权行却继续展示原名次；重新查询才能生成新权限范围的榜单。普通明细历史结果也先采用整体拒绝，避免不完整结果冒充原快照。

### 4.3 修正后端机构参数的双重含义

新规范化查询计划中的 target_org_codes 只表示实际参与查询的机构。父机构、cohort 等描述只存在于 scope 阶段，不能进入 planner 后再次展开。

禁止把已展开的多个候选编码直接传入旧 selection=ranking 契约，它只接受一个范围机构，会拒绝或产生二次展开。用新的查询契约/准备入口替换该契约，将授权后的候选集合直接交给现有 QueryPlanner/SQL builder。本文称其为v2，但不要求同时保留一套v1查询接口；全部调用方在配套发布中切换，删除旧分支。

## 5. 规范化计划成为唯一执行依据

流程调整为：用户原文与可信上下文 → Pi 意图 Delta → 字段解析 → 范围与权限解析 → 组合校验 → 服务端规范化计划 → READY → 执行 → 结果回执。

Frame 保存意图及计划引用；计划绑定 actor、session、turn、Frame版本、契约版本、目录/范围版本、条件哈希和失效条件。执行工具只接收当前 Frame/计划引用，禁止重填条件。后端仍独立校验引用归属、当前权限与计划完整性，不能信任 Agent 的 READY 标签。

服务端契约为唯一正式定义，通过生成的 Schema/类型和契约测试同步 Agent 工具、模型可见 Schema、后端请求验证与计划构造，避免四处独立维护枚举和交叉规则。部署时校验协议版本，不兼容时明确报错。

当前工具的 fieldChanges.rawValue 是通用 Unknown，模型精简视图也没有展示机构对象的完整 inputSchema。改造时须把新判别联合实际接入工具参数和模型可见 Schema，不能只在后端定义一个模型看不到的类型；保留跨能力扩展点，并在调用边界逐能力验证字段/操作/值的组合。

组合能力必须显式登记：

- 指定日 + 普通取值；指定日 + 同级机构排名：本次必须完整支持。
- 区间取值和区间最新一期排名：每指标在指定区间、授权候选集合及有效数据版本内，选择存在有效数值的最大业务日期；仅对此日期有值的机构排名。不是所有机构共同有数据的最新日，也不是每家各自最新日。分母为授权候选机构数，缺数为该分母减去目标日有有效数值的机构数。若用户要求“全部机构共同有数日”，按独立组合能力处理，不偷换默认口径。
- 多指标排名：沿用已有每指标独立分榜能力；“按某一指标排序并展示其他指标”是不同目标，须有排序依据和明确能力支持，不得自行猜测或混合不同单位。
- 整月每日排名、跨层级混排、复合评分等：未实现的组合返回 UNSUPPORTED；不能只保留一天、一个指标或改成普通取值。

排名方向与条数由用户语义明确生成（例如“前3名”对应降序3条），后端不补猜缺失参数。延续 ROW_NUMBER 语义，同值追加稳定机构编码作为次序，统一 builder 的 MySQL/Inceptor 方言。若用户明确要求并列名次或包含全部并列，则走已登记的对应能力；尚未实现时明确说明，不暗中切换 RANK/DENSE_RANK。

NULL/缺数不当作0；必须明确定义可排名记录及缺数统计。先对授权集合取符合日期口径的完整有效记录再排名，不先取样、分页或截断后排名。目标日期没有数据时返回该日无数据，不自动退到前一天；实际有值机构不足3家时如实返回不足3家，不能补入越权对象。

规范化事实唯一键为“正式指标编码、机构编码、业务日期”。在已有数据源映射中确定有效状态、批次优先级和稳定版本次序，先去重再选日期和排名；builder 的 MySQL、Inceptor 方言必须对同一基线得到相同事实。不能拿物理返回顺序挑一条。MySQL 同一事实键重复或 Inceptor 相同最高有效批次重复时返回 DATA_CONFLICT（同值重复也保守拒绝）；不得求和、取最大或任取一条掩盖冲突。具体源字段由数据源映射提供，现场缺失则列为数据治理前置条件，不能编造批次字段。

例如授权集合为甲乙两行、指定区间内甲在30日有值而乙最后有值日为29日：最新一期榜单日期为30日，仅甲参与，明确“2家可见，1家有值，1家缺数”；不得把乙29日的值加入同榜，也不能自行退到29日。本次明确4月末的查询始终只取4月30日。

回执包含实际日期、授权范围说明、排序与并列口径、授权候选/有效数据/缺数数量、结果引用、截断状态。零行、部分缺数、查询失败分开表达。

## 6. 错误分类决定下一步动作

| 类型 | 例子 | 动作 |
| --- | --- | --- |
| ARGUMENT_ERROR | 枚举、字段组合错误，缺少模型应提交的意图证据 | 本轮纠正；不覆盖原焦点、不写成待用户澄清 |
| NEEDS_CLARIFICATION | 两个同名候选、来源不明、真实排序依据不清楚 | 保存待澄清 Frame，只问业务缺项 |
| PERMISSION_DENIED / EMPTY_AUTHORIZED_SCOPE | 显式越权或目标层级没有可见机构 | 明确范围不可用，不换范围重试、不泄露目录详情 |
| CONFIGURATION_ERROR / UNSUPPORTED | 层级未配置、组合未实现 | 说明能力或配置阻塞，不要求用户确认内部枚举 |
| TEMPORARY_ERROR | 目录/服务暂不可用 | 只按幂等和重试策略恢复，耗尽后返回服务错误 |
| READY / SUCCESS / NO_DATA | 合法计划、成功结果、零行结果 | 执行或展示，不转成待澄清 |

同一调用可能同时存在真实缺项和参数错误：先保留有效字段与业务候选，在同轮纠正参数；参数修正后仍有真实缺项，才进入待澄清。不能靠整体 invalid 状态决定都问用户。

纠错预算建议最多2次参数修订；等价错误指纹再次出现则提前停止。修正必须保留用户已表达的机构范围、指标、日期和操作；无业务依据不能自动把取值改成排名。系统确定可规范化的别名/默认才自动处理，其他由 Pi 依据结构化原因修订。预算耗尽返回解析失败和可诊断关联号，不能伪造“用户未说清”。

只允许 READY 且 executionMode=execute 的当前计划调用执行。查询超时后结果未知继续沿用已有幂等键恢复，不另建任务；真正改变查询条件才生成新的计划和幂等键。

## 7. 多轮继承与恢复

- “改成5月末”：只改日期，保留指标、机构范围和排名操作，重建计划。
- “看前5名”：只改排名条数，保留其余条件。
- “不排名，全部列出来”：明确切换 value，并由操作联合类型移除失效排名参数，不能要求用户清除内部字段。
- “只看甲行”：保留“只看这一机构”的范围约束；不得把甲行默认为上级后改查其支行。若与此前排名目标存在真实歧义，仅核对该目标。
- “改成支行排名”：明确修改 cohort/层级，重新展开和授权，不沿用法人行编码集合。
- 新独立问题不能默认继承上一轮的前3名；有歧义的指代使用既有 FrameSelector 澄清。
- 失败修改不覆盖原焦点；历史结果回读不重查，权限撤销后不能继续显示旧授权结果。

历史 Frame 按 schema_version 识别。保留原审计记录与成功结果的只读展示，但不保留旧语义执行器来续跑旧任务。旧待执行/待澄清会话归档为只读，用户可新建会话按原问题重新建立目标；不自动导入可能含exact+top_n冲突的旧条件。成功历史结果仍可按resultRef经统一结果读取服务回读并复查权限。读取旧数据格式是有限的只读适配，不是第二套查询实现。

### 8.2 配套切换和整包回退

采用前端、Agent、后端配套发布，切换窗口暂停接纳新操作。版本检查不匹配时不接纳新查询，不要求新代码同时跑两套业务契约。

切换顺序：核对调用方迁移完成 → 停止接纳并排空在途任务 → 用原幂等键对账未知结果 → 备份会话、配置和必要状态 → 旧会话只读归档 → 发布配套新版本 → 验证新查询/历史结果读取/旧入口不可执行 → 开放流量。未知结果未对账完成就不切换，不能靠重建任务消除不确定性。

回退使用上一套完整发布包、匹配配置与切换前会话快照；不在新版本里建设兼容执行层。回退前同样排空并对账新版本操作，新版本产生的历史和结果完整封存，不删除；旧版本只挂载它能识别的状态，不读取或续跑新Frame。回退期间新版本独有会话可能暂不能在旧界面展示，应明确说明，恢复新版本后继续提供只读查询。若改造涉及持久化数据库字段，回退演练必须证明旧版本对新增数据的隔离/兼容，不能未经评估整库恢复而覆盖其他业务写入。同一数据根始终只有一个写实例。

## 9. 验收矩阵与发布门槛

| 类别 | 必测场景 | 通过标准 |
| --- | --- | --- |
| 原问题 | 原句及“前三家/客户最多的三家”等改写 | 日期、指标、授权同级范围和降序3条全部保留；无需多余确认；执行一次 |
| 反例 | 未知具体行、独立“这些行”、指标名含“排名” | 不扩大范围、不伪造实体、不误加动态排名 |
| 权限 | 管理员、省级配置授权、法人行、支行、显式越权、权限变化 | 相同治理规则；无越权结果；先裁剪再排名；失效计划不执行 |
| 层级 | 省汇总、法人行汇总、支行混合目录；根缺失 | 正确同级集合，保留合法法人行汇总节点；缺配置明确失败 |
| 数据 | 0/1/2/3/多家有值、NULL、0、同值、多批次、跨日 | 不足如实返回、缺数不补0、去重与同值排序稳定、不混日、不采样排名 |
| 多轮 | 换月、换指标、换范围、前3改前5、取消排名、独立新题 | 仅修改用户要求的维度；无失效参数、无历史错误污染 |
| 错误 | 模型冲突参数、参数错误与业务歧义并存、服务中断 | 同轮有界纠错；真实歧义才问；服务错误不伪装缺项 |
| 恢复与清理 | 重启、重试、重复执行、并发、历史只读、整包回退、旧入口移除 | 不重复取数、不抢新焦点、不绕过权限；旧状态不误执行；无残余旧链路调用 |
| 跨层 | 工具Schema→Frame→v2请求→计划→SQL→结果 | 参数、范围、日期、排序保持一致；builder 的 MySQL/Inceptor 方言契约一致 |

验证分三层，报告必须分别标注：

1. 确定性离线测试：合成目录、合成层级/权限、数据桩/可丢弃SQLite；契约和回归全部通过，越权、条件丢失、错误层级、重复执行为零容忍。
2. 真实Pi入口+真实模型+合成后端：用新入口全链路跑固定验收集，建议至少30个正反例、每例3次；报告首次/纠错后成功率、错误澄清率、延迟和工具次数。原句及明确等价问法必须全部按契约完成；任何越权/静默改目标均禁止发布。未达标则调整契约可见性或语义策略并重跑，不以挑选成功样本验收。
3. 授权测试环境业务验收：用该环境的正式目录、层级和已知数据基线，分别以省级和受限账号核对榜单、缺数和权限；浏览器验证过程展示、结果表、刷新恢复和错误提示。生产连接与写入另遵循环境授权，不将合成通过冒充业务验收。

真实入口验收必须留存可复核证据：代码/契约版本、模型实际标识及配置摘要、用例清单与独立期望、贯穿请求→Pi工具→Frame→后端计划→执行→结果的关联ID。对新问数入口断言调用了 resolve_business_turn 与 execute_business_frame，且未调用旧 metric_ask/SemanticEngine；记录实际取数次数，不能用手造READY Frame代替语义验收。完整原文仅使用合成用例，禁止写入模型密钥。

专用验收脚本命令为 `node --env-file=.env --import tsx scripts/check-query-intent-v2.ts --live`；其离线模式只校验用例定义，live模式必须经真实会话入口与上述调用链。运行前按授权配置模型及合成后端，不能因加载.env而连接真实业务库。自动配套版本握手、渠道旧语义入口迁移与整包回退演练仍须作为发布工作完成；当前不能宣称这些已实施或通过。实际执行命令与记录见交付记录。

推荐检查命令以各模块现有脚本为准：Agent typecheck/test/build；后端定向pytest及受影响回归；前端有交互变更才执行其typecheck/test/build及浏览器用例；交付前git diff --check。方案本身不触发真实模型、服务或数据库测试。

## 10. 可观测性与完成定义

每次失败能够定位到原文意图、字段解析、机构范围、授权、组合校验、计划或执行中的具体阶段；日志记录关联ID、版本、状态、错误码、纠错次数与脱敏摘要。完整原文/目录候选仍留在按账号隔离的状态中，不进入公共日志。

记录并监控：参数冲突率、无依据澄清率、原句验收成功率、范围配置错误、空授权范围、查询零行、服务错误、修订预算耗尽、重复执行拦截。无依据澄清率通过有标签验收集或授权脱敏抽样判定，不能把所有澄清都算错误。

完成必须同时满足：新契约能表达合法业务目标；正式范围与权限贯穿执行和回读；截图问题及多轮/负例通过真实入口验收；在用调用方已迁移、旧执行链路已清理且整包回退可操作；用户仅在真实业务歧义时被询问。设计完成、代码完成、合成验证通过、业务环境验收通过分开记录。
