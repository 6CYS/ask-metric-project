# 通用追问与数据覆盖查询

## 行为合同

追问以一笔已成功且当前仍有权访问的任务为来源，模型理解本轮想改什么，后端合并、验证并执行。
前端不要求用户重新选择已确定的机构；有多个合理来源、目录匹配有歧义或缺少必要条件时才澄清。
新问题继续独立解析，当前未完成任务继续使用原有 task/version/clarification_id 澄清协议。
输入框不提供“作为新问题发送”开关。普通手输由对话链判断；只有当前缺项的纯目录选择才显式绑定澄清目标。
有待澄清任务时，完整独立问题仍可直接提出；最新待澄清或失败状态不能被更早的成功回执覆盖。

| 用户意图 | 行为 |
| --- | --- |
| “这个指标有哪些月份有数据” | 继承机构、指标，查询实际可用月份；切换目标时解除上一笔日期限制 |
| “最早哪天开始有”“最近有数的是哪天” | 按机构与指标分别查询最早/最新数据日 |
| “只看今年有数据的月份” | 将明确日期范围作为覆盖查询的筛选 |
| “换成乙行去年的，按月看” | 同时替换机构、时间和查询操作 |
| “加上乙行，改查四月” | 追加机构、替换时间，继承指标 |
| “去掉甲行，保留乙行” | 只移除被指定的机构，保留其余条件 |
| 原因分析、未支持的筛选或操作组合 | 明确返回能力不支持，不通过补齐机构/日期诱导用户继续 |

自然语言仍可能解析失败，不能承诺所有表达都一次理解正确。模型漏掉本轮明确的新实体、
修改清单与值不一致时，后端先固定已提取的实体、时间和操作，再最多调用一次 `reference_change_map`
补齐遗漏的动作。已有动作不可改写，仍不一致则阻止执行。不会重新提槽或静默退回旧条件。

## 接口与责任

Agent 的 `metric_ask followup` 统一提交：

```json
{"query_reference":{"task_id":"来源任务","version":3,"change_field":"compose"}}
```

即使 Agent 误用 `new`，宿主也从本轮用户消息之前的最近成功业务回执派生候选：

```json
{"query_reference":{"task_id":"候选任务","version":3,"change_field":"compose","mode":"candidate"}}
```

候选不表示必须继承。后端同次提槽输出 `context_relation=followup|independent|ambiguous`：
追问合并条件，独立问题移除候选且不得复制历史缺项，关系不明确则停止执行并请用户明确条件。
目录查询不改变候选，待澄清或失败回执阻断自动回退；来源仍需验证归属、会话、版本、目录和权限。
未传 `mode` 按 `explicit` 处理，并保留既有显式引用的幂等指纹。候选模式只允许 `compose`。

固定日历表达在模型漏掉时间时复用已有解析器保留；多个未完整解析的日期不得退回旧期间。
裸月份继承来源单一年份，跨年来源需要明确年份。未知指标由模型提取原文，不再将删去日期、机构后的残句当指标。

用户原文原样提交。后端冻结来源槽位与规范 DSL，再由 `slot_extraction` 输出本轮增量：

```json
{
  "context_relation": "followup",
  "orgs": ["目录中的乙机构"],
  "time": "2025-01-01至2025-12-31",
  "ops": [{"type":"trend","grain":"month"}],
  "changes": {"orgs":"replace","time":"replace","ops":"replace"}
}
```

`changes` 可声明 metrics/orgs/time/ops/filters/dimensions 的 replace/add/remove/clear；
time 只支持 replace/clear。未声明字段继承，声明字段按操作修改；保留旧 orgs/time API 的严格
单字段边界。合并支持某个字段不代表执行能力支持任意筛选和组合，能力合同会再次校验。
目录解析、归属/版本、权限、幂等与只读 SQL 仍由既有后端链路控制，模型不能直接执行 SQL。
调试状态 `reference_merge` 记录来源、修改项与继承项。

`clarify_context` 仅处理无法确定来源或修改含义的情况，不创建业务任务。
当前只支持一个经过验证的来源，不支持多任务拼接、任意分析、归因或自定义 SQL。

## 数据覆盖结果

`availability` 操作有 `grain=day|month` 和 `selection=all|earliest|latest`。
对应 `query_shape=metric_availability`，结果字段为 metric_code/org_code/available_period/
first_date/last_date，并复用目录名称补齐。evidence.response_kind 为 availability。

- 不指定日期时查询可用范围，不注入隐含 latest；明确日期时先筛选。
- 按每个指标、机构独立聚合，零值属于有数据，NULL 不属于有数据。
- Inceptor 沿用最新批次去重、数值有效性和无效哨兵值过滤口径。
- 先计算各实体日期边界，再应用结果上限；截断必须披露，不能称为全部月份。
- 完整结果里缺失的请求对象明确披露；已截断时不推断其他对象无数据。
- 后端按查询结果生成回答，Agent 和页面展示同一份证据；月份覆盖不冒充指标数值。

## 失败与重试

失败任务不能作为澄清目标。自然语言的 `clarify` 必须能对应最新正式回执中的
`WAITING_USER/clarification_required` 与 `task_id/clarification_id`；宿主在写入前拦截
不存在或已关闭的目标，允许模型依据反馈改为 `new`，由后端检查新问题的缺项。
结构化选项仍由后端验证版本和有效澄清编号。拦截反馈本身不覆盖正式业务状态。
前端实时、历史恢复和任务回读统一保留工具的公开失败原因；无公开原因时才使用通用文案。
混合查询包含停用指标时仍整笔拒绝，不静默只执行其中启用的指标，也不修改目录启停状态。

## 升级与回退

无需数据库表迁移。需同步发布后端、Agent、前端，以及配置和 SQL 资源：

1. 将实际 `PROMPT_CONFIG_PATH` 中的 `slot_extraction` 合并为仓库的 2.1.0 协议，并新增 `reference_change_map` 提示词。
   兼容路径 `prompts.query-only.json` 同步维护。持久配置的已有提示词不会因补充默认值而自动覆盖，
   仅更新代码或镜像不足以启用新行为；保留环境中的其他自定义配置。
2. 在实际语义配置 operations 中增加 availability，合并 query-templates 注册及两种方言的
   metric_availability.sql。即使使用 builder，也需保证模板注册完整。
3. 同步更新 Agent、前端与配置；旧前端的 `send_as` 字段不再接受，需刷新页面。
   升级前先停止接纳并等待活动 operation 结束。新候选引用进入业务指纹；不得让升级前未完成的 new 命令跨版本恢复，
   也不能换请求键重建未知结果的任务。升级后同版本的断线/重启恢复仍沿用原命令及来源。
4. 重启加载后按测试矩阵验收，包括自然补充、独立切换、错误 new、目录检索后的追问和会话重开。
5. 回退时整体回退代码、提示词和配置，先停止新 compose/availability 请求。
   新格式任务不能交给旧执行器继续分析或执行；保留既有任务与结果，不删除历史数据。
