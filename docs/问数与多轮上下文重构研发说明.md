# 问数与多轮上下文重构研发说明

## 1 目标

支持完整问题直接查询，以及缺少指标、机构、日期、名称或口径模糊时的澄清和补齐；连续问答能定位当前及历史任务。用户明确的指标、机构、时间及其对应关系保持准确，只修改本轮要求修改的内容。

将现有多层语义校验与准入链替换为一个语义入口和一份工作状态。**旧重复校验、签票和准入调用必须删除，不能通过新增包装层或关闭开关保留两套运行逻辑。**

## 2 目标调用链与职责

`用户原话与当前状态 → 模型给出结构化条件或增量动作 → 宿主统一绑定并更新状态 → 后端执行 → 根据正式结果回答`

| 位置 | 职责 |
| --- | --- |
| 模型 | 新查询输出机构、指标、时间、取数方式和操作；续问输出目标引用与增量动作，真实缺项写明未定 |
| 宿主统一入口 | 定位目标，绑定正式目录和日历，自动归一，应用本轮修改，决定执行、追问或展示结果 |
| 后端 | 鉴权、会话归属、目录和机构范围、能力边界、SQL 参数绑定与只读、查询幂等和数据冲突处理 |
| 结果出口 | 使用实际执行条件和正式结果回答，区分成功、无数据、失败和状态未知 |

保留 `resolve_business_turn` 入口，重构其内部实现。已接受的语义由后续模块直接使用，后端不再按原话重新裁定指标、机构和日期含义。普通数值回答直接渲染正式结果；排名、计算和分析继续使用既有执行能力。

完整查询使用 `target.query`，局部修改使用 `target.operations`；`structuredQuery.ts` 将二者接到同一个字段更新与执行链。排名方向、条数、完整排序、关注对象与比较范围均由结构化字段表达，不把模型已经确定的操作拼回一句话再解析。

## 3 工作状态与更新规则

复用 Native Session 保存一份版本化工作状态：任务及目标 ID、每个目标的指标/机构/时间/取数方式/操作、待明确字段与问题绑定、结果引用。字段保存当前正式值和来源轮次；原文表达和动作保存在本轮操作记录中，供继承和追溯。

每轮固定入场状态，模型修正和历史读取不移动这个基线。Plan、Task、Frame 的业务条件由该状态生成；Frame 负责执行状态与结果关联。执行授权统一绑定到工作状态版本和执行快照，删除 Plan 与 Task 分别维护的重复准入结论。

**定位规则：**回答已发布问题时接到对应目标；明确历史引用时按轮次、机构、指标或原日期定位；唯一续问承接当前工作任务。独立新问题建立新任务，省略条件仅继承唯一且已确认的上下文；明确不沿用时清空继承。有多个合理对象才追问，并保存本轮修改意图。最近成功结果不能覆盖当前待补任务。

**补齐与澄清：**先采用可确定的继承条件，再识别真实缺项；只询问缺少或有歧义的内容。候选保留正式身份和口径差异，用户可通过选项、名称或明确更正继续回答；拒绝候选时保留未决状态。多指标中已确定的成员保留，只澄清未定成员；补充回答也可同时修改其他字段。仍有必需条件未定时不执行，补齐后按完整目标查询，并支持继续续问。

| 本轮输入 | 状态更新 |
| --- | --- |
| 唯一别名或可唯一确定的名称 | 绑定正式编码；宿主直接纠正模型表达，无需重提 |
| 明确条件被模型漏填，且目标归属唯一 | 宿主补入该目标；无法确定归属时继续解释或追问 |
| `add` / 追加 | 取并集，重复成员无需变化 |
| `exclude` / 排除 | 取差集；确定指向的成员已不在集合时也成功 |
| `set` / 只看 | 替换为明确集合，不带入旧集合额外成员 |
| `replace` / 替换 | 替换指定成员并保留其他成员；对象不明确时追问 |
| 修改日期 | 结合已选上下文年份和业务日期换算一次，保留其他条件 |
| 重述相同条件 | 接受等值表达，不重新证明旧字段来源 |
| 修改的新值尚未确定 | 保存未决修改，不回退旧值执行；其他已确认条件保留 |

每个动作绑定相关原文子句和目标，保留否定、替换及范围含义；按目标保存机构、指标、日期的对应关系，不能只比较三个全局集合。统一入口接住明确条件遗漏和错误绑定后，删除旧的原句覆盖与跨轮复核。

不确定的名称或口径只问必要问题；采用明确约定的默认口径或唯一口径时回显。相近指标不能替代用户指标，无数据不能静默换日期。实现不得硬编码个别银行、指标、日期或一句话的特殊处理。

## 4 旧链清理范围

以下路径以仓库根目录为起点。

| 模块 | 必须完成的改造与清理 |
| --- | --- |
| `agent-service/src/semantic-task/service.ts` | 合并字段绑定和归一；删除独立 `coverage()` 复扫、重复来源/对齐阻断、`target.transition` 证明构造及等待准入占位问题 |
| `agent-service/src/semantic-task/planService.ts` | 删除 `groupAdmission` 整批准入、来源票据组装/回填和 `Plan.admitted` 重复准入；保留目标组织与计算依赖 |
| `agent-service/src/semantic-task/transition.ts` | 删除 `SemanticTransition`、`transitionBasis` 及证明组装；仍需的字段投影和 spec 构造合入统一状态模块 |
| `agent-service/src/backendClient.ts`、`backend-next/src/ask_metric/api/routes/business_context.py` | 删除 `admitSemanticPlan`、`/admit-plan` 及专用请求结构；保留目录、字段解析和真实历史定位能力 |
| `backend-next/src/ask_metric/application/semantic_transition.py` | 迁移有效行为用例后，删除 `validate_transition`、`verify_transition_fragment` 及仅供旧准入使用的类型和辅助函数 |
| 票据消费调用方 | 清理 `semanticSelectionReceipt`、`source_semantic_receipt` 及旧签票/验票调用，覆盖 `adapters.ts`、`structuredQuery.ts`、`directDelivery.ts`、`tasks.py` 和历史来源接口；无调用方的 `analysis_selection.py` 代码删除 |
| `protocol.ts`、`tools.ts`、`feedback.ts`、`harnessHost.ts`、`toolRecovery.ts` | Schema 统一参数形状和字段动作组合；运行器根据明确决策驱动，删除业务层重复形状判断、旧准入错误分支及反复重提指引 |

后端使用规范化 `BasicQuerySpec` 执行。旧证明字段从当前请求、适配器和提示词中一并清理，不能只在某个调用点省略参数。历史记录可保留读取适配，适配不得重新启用旧准入或自动重跑查询。鉴权、资源归属、SQL、执行恢复和正式结果引用继续由原有模块负责。

同步修改调用方、Schema、提示词、接口说明、部署说明及测试。错误码的合并随旧职责删除完成，不另建规则登记或额外准入体系。

已落地的绑定入口为 `actionBinding.ts`：复用本轮事实、绑定字段和集合动作；`sourceGuard.ts` 在同一入口定位续补及历史来源。Plan 的 `requirements/checks` 及状态更新后的日期对账一并删除，完成度只取正式步骤状态。

## 5 运行与实施要求

能确定的字段由宿主直接归一；缺少用户信息才追问；需要理解指代或动作时允许模型据真实候选修正。条件确认、候选收敛、目标确定或新增依据才算进展，换 `target_ref` 或改写文案不算。同一原因再次出现且没有进展，结束该修正路径，并说明实际缺项或失败原因。

条件无需变化时，仍按本轮目的处理：展示旧结果则读取；明确重新查询则执行；没有对应结果且要求查询则取数。同请求 ID 复用原操作；执行状态未知只回查原执行，不能当成无数据或重新提交。

实施顺序：先统一状态与更新函数，再切换唯一绑定入口并删除旧准入链，最后清理调用方、提示词和测试。**交付必须包含旧生产调用及无调用方实现的实际删除，不保留恢复旧准入的运行开关。** 将仍有效的机构/指标/日期对应、权限和结果行为测试迁移到新入口，不能以删除旧测试代替验证。

工作状态格式版本独立于工具协议版本。历史会话及结果保持可读，新操作从可确认的旧状态适配；在途执行按原执行 ID 结算。接口变更由 Agent 与后端配套发布；回退读取保留版本信息的记录，不恢复旧语义链或重放 SQL。

## 6 改造后验收

验收覆盖完整查询、真实缺项、模糊表达、候选确认、时间理解、上下文定位及结果交付。缺项和歧义用例先设置无可信继承条件、无可适用默认值的前提，再单独验证已有上下文可以继承的情况。

| 类别 | 场景或对话 | 必须成立 |
| --- | --- | --- |
| 完整问题 | 指标、机构、日期均明确 | 直接按正确条件查询，不重复确认已知信息 |
| 缺指标 | 机构和日期已给出 → 追问指标 → 用户补充 | 只补指标，保留机构和日期，补齐后查询 |
| 缺日期 | 机构和指标已给出 → 追问日期 → 用户补充 | 只补日期，保留机构和指标，补齐后查询 |
| 缺机构 | 指标和日期已给出 → 追问机构 → 用户补充 | 只补机构，保留指标和日期，补齐后查询 |
| 多项缺失 | 只给指标 → 分轮或一次补充机构与日期 | 逐轮积累已确认条件；未补齐不查，补齐后查完整目标 |
| 可继承条件 | 同一任务续问省略部分字段 | 准确继承已确认条件，不要求重述，不反复读历史 |
| 指标模糊 | 指标表达对应多个合理名称或口径 | 给出相关候选或必要追问，不擅选；确认后完成原查询 |
| 唯一名称与默认口径 | 正式别名唯一命中，或适用已约定默认口径 | 绑定正确身份并回显；相近名称不能当作等价指标 |
| 候选回答 | 分别用序号、完整名称和页面选项回答 | 都对应实际发布的同一候选身份，不错选或扩大范围 |
| 否认与更正 | 用户回复“都不是” → 重新描述指标 | 不采纳被否认候选，保留机构和日期，新描述确定后继续查询 |
| 部分指标未定 | 两个指标中一个明确、一个模糊 → 确认未定项 | 保留明确指标及其他条件，最终查询完整指标集合 |
| 机构模糊或名称不存在 | 机构有多个候选或指标/机构未命中 → 用户澄清 | 询问实际未定项，不用相近实体替代，澄清后可继续完成 |
| 澄清中修改条件 | 指标待确认时说“日期改成3号”，再回答指标 | 修改日期并保留待确认指标；不能把日期数字当候选序号 |
| 时间理解 | 相对日期、上下文年份、区间及离散日期分别提问 | 得到各自正确日历和取数方式；有真实歧义先澄清，不缩短范围或强套当前年 |
| 集合变更 | 三家 → 去掉江阴 → 六月末；再排除已排除成员或重述剩余集合 | 等价说法得到相同条件；指标不变，重复排除不阻断 |
| 单字段替换 | 三家 → 只看江阴 → 改成无锡；另测修改指标或口径 | 仅修改指定字段，其他条件准确保留 |
| 多目标绑定 | 甲五月、乙六月 → 两家交换日期 | 分别更新正确目标，不能因全局日期集合相同误放行 |
| 历史定位 | 多笔历史 → 定位较早一笔 → 仅修改该笔 | 定位准确，其他任务不变；纯历史展示不移动工作任务 |
| 新问题与指代歧义 | 明确不沿用旧条件；或无法确定“那一笔” | 前者不带入旧条件；后者保留修改意图，用户指明后操作正确目标 |
| 未决修改续接 | 新机构或日期未确定 → 修改其他字段 → 补齐未决项 | 不恢复旧值执行，保留每项有效修改，最终按补齐后的条件查询 |
| 无数据与重新查询 | 指定日期无数据；同条件要求重查；重复同请求 ID | 不换日期或伪造数值；明确重查产生新查询，同请求 ID 不重复执行 |
| 刷新与恢复 | 澄清中刷新后回答；执行未知后恢复；换引用重提同一失败 | 问题和目标保持准确，原执行只回查，无效重提不耗尽工具预算 |

每类用例采用隔离合成目录与结果，并覆盖同义表达。澄清类必须走完“首问 → 必要追问 → 补充或确认 → 查询结果 → 再次续问”，不能以出现追问文案作为通过。每轮核对已保存条件、未决字段、目标引用、实际提交的 `metric_codes`、`org_codes`、`time`、操作、执行次数及最终结果；必需条件未定时不得执行，已知条件不得丢失。

先运行统一状态与入口的用例，再运行 Agent 的 `npm run typecheck`、`npm test`、`npm run build`，以及受影响的后端 `verification` 用例和 `git diff --check`。

将上述对话补入现有 `agent-service/scripts/check-clarification-acceptance.ts`、`check-multiturn-model.ts`，复用指标名称、口径确认与历史定位相关用例，同步更新 fixture 并清掉旧准入依赖。运行带 `--live` 的真实模型验收，按类别记录各轮条件、执行次数、结果和实际失败；真实数据库取数及页面刷新续问分别验收并记录。交付提供旧链删除清单和各类实际验收结果。
