# Ask Metric 指标问数优化需求与融合讨论纪要

日期：2026-10-23

状态：需求讨论稿；用户已确认 `ads_lake` 导入包是真实数据。已完成一条“提问 → 机构确认 → 查询”的本地基线及源值核对，详见第 8.4 节；尚未开展全面业务验收。

本文整理已确认需求、源码现状、建议方案和待验证事项，供后续业务讨论、工程分析与改造使用。本文不代表实施方案已经批准，也不代表融合效果已经验证。

## 1. 背景与目标

领导认为 `jjccb-release` 的 Agent 在理解业务问题方面表现较好，希望 Ask Metric 吸收这部分能力。用户已确认首期范围为：**保留 Ask Metric 的页面、会话、指标和取数能力，先融合语义意图理解与追问能力。**

用户更关注 mfws 中的 `jjccb-release` 和 `release` 分支。本轮具体机制分析主要依据 `jjccb-release`，没有把 `mfws-app/develop` 的实现作为这两个分支的现状。

随着讨论深入，用户提出：当前业务主要是固定三张源表的指标问数，直接搬入一整套 Agent 是否过重。因此，后续需要根据真实问数问题确定最小改造范围，避免为了融合而扩大系统复杂度。

期望改善的用户体验是：能听懂自然业务表达，准确确定指标、机构、时间和操作；连续追问能继承正确条件；有歧义时提出必要问题，用户补充后能继续原任务。

## 3. 当前业务范围：固定指标问数

### 3.1 三张源表分别承担什么职责

根据当前源码默认值和部署映射，外部数据湖的三张源表为：

| 源表默认名称 | 主要职责 |
| --- | --- |
| `ads_lake.adm_rmt_pub_gnrl_drv_indcr_tab` | 指标事实：指标码、机构码、业务日期、数值、增量及批次。 |
| `ads_lake.adm_rmt_pub_drv_indcr_cnfgon_infotab` | 指标配置：基础指标名称及版本，参与同步正式指标目录和口径。 |
| `ads_lake.fdm_pub_org_inf_all` | 机构目录：机构编号、名称及范围、层级等信息。 |

表名可由现场 `SIT_*` 配置覆盖，上表不是对现场数据库的实际连接核查结果。应用库中的 `metric_terms`、`metric_synonyms`、`org_terms` 是同步和人工维护后的语义目录，不应与这三张源表混为一谈。

### 3.2 这对融合规模意味着什么

当前日常问数先利用指标、机构目录确定正式编码，再由程序按编码、日期和已支持的查询形态构建 SQL。模型无需每轮探索三张表的结构或重新决定关联方式。

因此，优化重点应首先落在“把业务问题转换成正确查询条件”。三张表仍可能包含大量指标和复杂口径，表少并不意味着理解简单；但这也不能成为引入通用选表、自由 SQL、任意代码执行等能力的理由。

## 4. Ask Metric 已有的理解能力

### 4.1 当前主链路

```text
用户问题 + 当前任务、历史、业务提示词
                  ↓
             模型理解问题
                  ↕
       按需读取目录、业务知识、历史
                  ↓
       resolve_business_turn 语义提案
                  ↓
        程序绑定、归一、修正和校验
                  ↓
   执行取数 / 保存追问 / 反馈模型修正
```

模型负责提出业务意图、目标、条件和字段变化。业务提案中已有 `query`、`analyze`、`calculate`、`availability`、`reuse`、`prepare` 等意图；新问题和续问通过来源与字段操作表达。

例如，已确认某机构、某日的存款余额查询后，用户说“换成贷款余额，时间不变”，理想处理是继承原机构和日期，只替换指标。此处是行为示意，不是已经通过的真实测试。

### 4.2 后续程序并非只做安全校验

当前代码还包含业务语义解释和修正，例如：

- 判断新问题与续问的来源关系，在特定条件下修正模型提案的任务来源。
- 根据原文和已确认条件，绑定、补充或清除字段操作。
- 将明确单日归一为指定时点取数；区间取数方式不明确时生成待补问题。
- 对“你好”“谢谢”等有限普通对话进行规则识别。

因此，排查理解错误时必须比较两份内容：**模型提交的原始提案，以及程序处理后的最终查询条件。** 不应直接把所有失败归因于模型，也不应为了保留模型输出而撤掉权限、归属或执行许可校验。

### 5.1 已有页面，但覆盖范围不同

| 内容 | 当前维护方式 | 关键边界 |

以上是源码确认的能力，尚未登录当前部署验证其写入开关和发布效果。

### 5.2 保存的知识怎样进入理解过程

- **机构名称与别名：** 每轮读取当前用户有权访问的机构目录，动态加入发送给模型的上下文副本，不写入固定系统提示词。
- **指标名称与同义词：** 用于后台目录匹配，也可通过模型按需调用的目录检索工具返回相关条目；不会每轮将全部指标装入提示词。
- **指标说明与口径：** 后台目录会读取这些字段，部分匹配机制会使用它们；但当前指标 `catalog search` 返回的条目只有编码、名称、单位、同义词、分数和匹配类型，没有完整说明与口径。

这里需要区分：**已经存储、参与后台匹配、实际被模型读取，是三件事。** 后续可以评估按需返回相关指标定义和口径，避免维护了知识却没有在需要的理解环节使用。该项属于优化建议，具体接口与展示方式尚未决定。

## 6. jjccb-release 值得借鉴的部分与迁移限制

从源码看，jjccb 的问题理解依赖业务知识、案例、指标检索、机构和时间背景、历史及工具反馈。领导感受到的理解优势可能来自这些因素的共同作用，当前没有同条件对比结果证明各因素的贡献。

值得验证的能力包括：

1. 从自然业务表达中识别指标及限定口径。
2. 发现信息不足，主动查证目录或知识。
3. 理解连续对话中的指代和条件变化。
4. 发现真实歧义，生成清楚、必要的追问。
5. 根据工具反馈修正理解，保留已经正确的条件。

迁移时需要注意：

- 这些能力没有封装成一个可以直接复制的单一提示词文件。
- 当前 jjccb 聊天入口会驱动完整 Agent，工具包括 SQL、Python、图表及可选 MCP；没有核实到可直接复用、保证只理解不执行的正式提案接口。
- jjccb 的规则触发消歧、问题生成与回答补充机制，不等同于 Ask Metric 已有的问题版本、用户确认和任务协议。
- 不能把 `mfws-app` 新架构中的能力写成 `jjccb-release` 已有能力，也不能将本轮结论自动套用到未经同等核查的 `release` 实现。

## 7. 建议的优化方向，尚待真实数据验证

### 7.1 优先增强现有问数链路

建议保留 Ask Metric 现有 Agent、任务状态与取数链路，吸收 jjccb 中经验证有效的理解方法和必要模块。

| 优先评估的内容 | 首期不建议直接引入的内容 |
| --- | --- |
| 业务问法、指标口径、时间与机构范围理解 | 通用数据库选表、表结构探索及自由 SQL 生成 |
| 当前任务继承、历史引用、条件增删改 | 第二套权威会话、业务状态和结果存储 |
| 相关指标定义、必要业务知识与案例检索 | 未经筛选的完整知识库和全部工具集合 |
| 必要追问及依据反馈进行修正 | 任意 Python 执行环境和通用 MCP 能力 |

这不要求将所有问题固定为一次模型调用。简单问题直接完成，复杂问题允许按需查证或修正；是否需要多轮、如何限制重复调用和总耗时，应根据真实失败案例确定。

### 7.2 优化要求的具体化

下表是对用户目标的工程化整理，用于后续确认和验收设计，尚不是已经通过的测试清单。

| 关注点 | 期望行为 | 观察依据 |
| --- | --- | --- |
| 意图与目标 | 区分新查询、继续修改、查看旧结果、口径解释等实际目的，并遵守已有执行能力边界。 | 模型提案与用户原问句是否一致。 |
| 查询条件 | 保留完整指标口径、机构范围、日期与操作，真实缺项不擅自补值。 | 正式目录绑定和最终执行条件。 |
| 多轮上下文 | 只修改本轮要求变化的条件；明确引用旧任务时选对来源。 | 每轮修改前后的条件差异和来源。 |
| 追问 | 只询问影响结果的未决事项；回答后继续原任务，不丢失已确认条件。 | 问题、候选版本、用户回答和恢复后的任务。 |
| 知识使用 | 在需要时读取相关定义、口径与案例，避免整库无差别注入。 | 实际返回给模型的知识内容及使用结果。 |
| 响应与可维护性 | 减少重复检索、无进展修正和规则相互覆盖，便于定位错误层次。 | 工具调用、最终条件、结果和分阶段耗时。 |

### 7.3 暂不固定的方案选择

独立 Python 理解服务只是备选，不作为首期默认。是否保留 jjccb 原运行框架，应在确认其有效能力无法合理迁入现有 Agent 后，再评估收益、部署成本、响应耗时和状态适配工作。

同样，不预先决定新增一套意图分类模型、重写模型、知识库平台或大型管理后台。先验证实际缺口，再确定最小改造。

## 8. 数据到位后的验证安排

### 8.1 希望对方提供的材料

| 材料 | 用途 |
| --- | --- |
| 可用的只读测试环境或获准导出的真实数据 | 验证真实取数链路，不用演示数据替代业务事实。 |
| 三张表结构、字段映射和实际数据日期范围 | 确认当前代码与现场数据结构一致，区分理解问题和数据缺失。 |
| 正式指标、机构目录与指标口径、单位 | 核对编码、范围与业务含义。 |
| 几条原始业务问题及人工或 SQL 核实的标准答案 | 判断查询是否正确，而不只是接口是否成功。 |
| 对应连续追问及预期条件变化 | 验证上下文继承和澄清恢复。 |

连接凭据通过既有安全方式配置，不写入本文、业务用例或代码仓库。

### 8.2 首轮先建立现状基线

1. 保留现有实现和配置作为本次基线，记录实际部署版本、模型配置及目录版本或快照。
2. 先完成一条指标、机构、日期都明确且有标准答案的真实问数。
3. 在同一会话继续两三轮真实追问，检查指标替换、日期修改、条件保留或必要澄清。
4. 记录用户输入、相关上下文、模型原始提案、最终执行条件、结果、单位、日期和耗时。
5. 按证据定位问题，再选择对应优化；优化后重跑相同问题，比较变化。

初始样例选择以业务实际问题为准，不以人为构造的顺利路径证明效果。真实数据、模型或外部依赖不可用时，记录真实失败及原因，不以 Mock、硬编码结果或模拟业务数据替代验收。

### 8.3 判断结果时的边界

- 查不到数据不一定是理解错误；需要核对数据覆盖、目录编码、权限和日期。
- 查出数据不一定是理解正确；需要核对指标口径、机构范围和最终条件。
- 跑通一条问题只能证明该样例链路通过，不能证明所有追问或整个系统都已验收。
- 若比较 jjccb 与 Ask Metric，应尽量统一数据、目录、业务口径、问题及上下文；模型配置差异必须记录，避免将混合因素全部归因为 Agent 实现。
- 暂不承诺准确率、模型调用次数或响应秒数目标；先记录基线，再确认合理阈值。
