# 二期工具参数精简验证（2026-09-30）

本文记录首次候选实现的历史验证结果，330 回合的原始记录和门禁结果保持不变。发现退步后已继续排查并修复运行时；本文的通过率和耗时不能用作修复后候选的验收结果。最新原因、修改和验证边界见 [语义退步排查与修复](./compact-turn-args-diagnosis-20260930.md)。

## 交付范围

- `resolve_business_turn` 的模型参数改用 `capability/base/mode/set/remove/clear/retain`，开关 `AGENT_COMPACT_TURN_ARGS` 默认关闭。
- `prepareArguments` 在原生 Schema 校验前双向兼容正常新旧参数；内部仍为 `ContextDelta`，确定性执行和回读仍使用 `{frameId}`。
- 系统提示、能力 Schema、焦点和历史索引、纠错回执、历史工具调用仅在模型发送副本中选择参数写法，不回写原生记录或业务 Frame。
- 保留现有 `capability`、`base` 必填约束。来源省略与 `null` 的内部语义仍保留；无法无损转换的非规范旧参数不补值、不丢值。
- 转换错误的历史来源只读定位：仅唯一且可继承来源附 `retry_reference`，不切焦点；`current` 不绕过最新在途、不可继承失败或坏引用快照。

## 真实模型对照

正式命令：

```bash
cd agent-service
node --env-file=.env --import tsx scripts/check-compact-turn-args.ts --live --repeat 3 --concurrency 3 --supplementary --report /tmp/phase2-compact-full.json
```

模型为项目配置的 `deepseek-ai/DeepSeek-V4-Flash`。两侧均启用一期回答流式输出，模型配置相同；每个用例旧/新版本串行，相邻比较，三组独立用例对并发，各轮之间有屏障。业务后端为隔离合成数据，指标和日期算法使用真实 Python 实现；未调用生产后端或执行业务 SQL。

query-intent：47 个场景、55 个回合，每侧重复三次，共 330 回合。另七套合成探针由统一入口各执行三次新旧对照。首次模型输出 token 取本轮第一条原生 assistant 的提供方用量，未知为 `null`；首字取首个非空 `answer_delta`，或最终投影的非空回答。成功纠错的早期输出仍计入首调用和等待时间，不用后续调用替代。

性能只纳入同案、同轮次两侧均语义成功的取数回合，防止短失败响应制造虚假提速。门禁要求：新版本不得出现“失败至少两次、基线至多一次”的单案回归，总通过率不降低，首调用输出 token 中位减少至少 30%，首字中位改善至少 1.5 秒。

主集已完成。两侧均成功的 106 对取数回合结果如下：

| 指标 | 基线 | 二期 | 门禁结果 |
| --- | --- | --- | --- |
| 首调用输出 token 中位数 | 255 | 177 | 减少 30.59%，通过 |
| 服务端首字中位数 | 8,126 ms | 7,094 ms | 改善 1,032 ms，未达到 1,500 ms |
| 主集全部语义通过率 | 146/165，88.48% | 139/165，84.24% | 下降 4.24 个百分点，未通过 |

首字统计为服务端投影观测，不包含浏览器渲染和网络传输。全部 132 对取数回合的首字中位数为 8,313.5→6,937 ms，改善 1,376.5 ms；其中失败回合也在分母中，不能据此替代门禁要求的成功配对口径。首字 P90（最近秩）为 14,834→12,023 ms。取数语义失败次数为 18→24，额外失败不能从体验结论中隐去。

主集未出现单案三次中“新失败至少两次、旧至多一次”的重复回归，但总通过率门禁失败。原生模型 assistant/usage 事件总数为 368→369，并未减少调用次数；`ARGUMENT_ERROR` 占全部工具回执为 20/209→20/208，两侧原生 `isError` 回执均为零。一个基线失败回合的首调用用量未知，保留 `null`；106 对成功性能样本没有用量缺失。

### 失败链核对

- 集合/下辖范围被模型直接写为 `organizations` 字符串，随后机构目录解析退回澄清；日期解析正确。原始工具参数、内部 Delta 和实际查询一致，未发现转换丢字段。
- 指标名称含“排名”的回合，模型把它当作独立排序目标；另有排名方向误选在两侧都出现。没有发现服务器转换改变方向。
- 不支持的查询组合、空授权范围出现重复解析；部分续问在纠错时漏掉本轮机构或取消排名条件。没有绕过校验执行查询。

首次验证结束时尚未追加运行时文案修改。之后的排查已增强 compact 工具的字段输入说明，并修复确定失败处理及日期表达契约；这些改动尚未完成新的真实模型对照，详见上方排查报告。

### 补充回归与外部失败

七套补充探针各三次新旧作业均已结束，共 42 个作业，但仅保存了 260/276 条预期结果，不能视作完整有效验收。后段真实模型接口返回 `HTTP 402`，第三轮广泛受影响，且两个多轮作业未生成报告。HTTP 状态本身不足以确定具体账户原因；这些失败不能作为参数方言导致语义退化的证据。

另确认 `history-focus-model` 的普通对话断言过时：原生 assistant 为 `toolUse`、`respond_without_business_action` 回执已完成、页面投影有正文，本来符合当前终止工具合同；探针却强制原生 assistant 必须为 `stop`。该断言在正式运行后修正，原始失败仍保留，提前退出后的步骤和修正后真实模型结果尚未验证。其他业务断言未放宽。

修正后完成严格 TypeScript 检查、离线入口检查，以及正式运行两侧原生普通对话记录的投影回放；两侧均输出一条完整正文。缺少回执或仅有上一轮回答的反例均不能通过。没有追加模型调用。

统一报告 `complete=true` 表示调度已结束，`supplementary.status=incomplete` 表示补充覆盖不完整，二者不能混同。报告中已观察到多轮指标澄清、上下文续问的重复失败，但由于缺失结果和模型接口故障，不能将整套补充门禁声称为通过。

原始主集记录、补充报告内容、门禁原值和已测代码指纹保存于 [模型对照证据](./compact-turn-args-phase2-20260930.json)。交付副本移除了临时目录路径，未改写样本结果；所有业务事实均来自隔离合成数据。

## 验收边界与运行状态

真实页面与数据库的 32 组 `tool-governance` 尚未验证：原入口含旧工具断言及额外模型等待，需要单独适配。统一报告明确 `full_gate_passed=false`，合成回归不能代替该门禁。

结论：二期核心代码已实现，静态检查通过；真实模型主集表明 token 和首字有所改善，但未达到启用门禁。用户确认模型账户尚未恢复，先保留实现和结果，因此停止继续调用模型，未开启二期或为启用二期重启服务。

交付时再次读取本地配置确认 `AGENT_ANSWER_STREAMING=true`、`AGENT_COMPACT_TURN_ARGS=false`。后续需在相同配置下完成优化候选的新旧完整复测，再执行真实页面与数据库验收；全部通过后方可按既有授权启用并重启。没有提交或推送二期改动。
