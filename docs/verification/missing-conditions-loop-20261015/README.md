# 缺项查询反复读取历史：根因、修复及验证

本次规则：继承当前会话唯一且已确认的机构、日期；没有的条件直接追问并结束本轮。用户明确修改或清除条件时，不回退旧值。多目标保留原始绑定，不任取历史目标。

## 原始请求证据

2026-10-15 09:54:02 的原始请求运行于 `semantic_v2` 全新会话，之前没有可继承机构或日期。总运行 72,734 ms，完成 23 次工具调用，其中 18 次 `read`，仅一次 `resolve_business_turn`，没有查询执行，最终被取消。原生日志保留在原数据目录；本文不复制业务日志、真实查询值或凭据。

首份提案把未提供的日期、机构占位词和指标口径另写入取数方式。后端正确拒绝了无来源日期，但回执同时包含 `FIELD_REQUIRED(time, user)`、`ENTITY_NOT_DETERMINED(organizations, user)` 和 `SELECTION_NOT_INTERPRETED(selection, pi)`。

## 根因

1. 真实用户缺项与日期依赖的内部解释问题混在一起，非用户问题使整体回执变成 `needs_interpretation / pi / revise_proposal`，无法交付已知缺项澄清。
2. 宿主只有少数诊断会指定重提工具，其余统一设置 `tool_choice=required` 并开放全部工具。成功读取历史不会修正提案，也不会触发重复失败保护，后续一直沿用同一待修回执。
3. 原生历史读取包含本轮读取活动；模型又把语义 `task_ref` 用作后端 `task_id`、把当前任务引用用作历史分页游标。这些误用放大了无效探索，语义任务本身并未丢失。
4. 真实模型候选验证另外发现：只读空上下文也被算成已完成动作，纯计划文字可直接结束；仅补机构时误用 `new` 可重建任务并丢失原指标来源。这两条路径也纳入修复。
5. 多指标回归发现：模型用 `current` 只想沿用条件时，计划却沿用上轮指标义务，正确重提仍无法收敛。普通新指标查询现在派生本轮目标，只继承可信范围；实际续补、集合修改、确认和分析继续保留原义务。

## 实现

- `semantic-task/service.ts`：依据原句事实区分真实缺项和模型遗漏；无日期时延后取数方式解释；占位机构或无来源的合法机构不成为条件；正式操作已规范化后清理相应过期诊断。
- `semantic-task/planService.ts`、`store.ts`：仅继承可信、唯一、已解析且无待决修改的机构/日期；默认条件固定保存在本轮计划，同轮修提不借移动后的焦点。唯一待补任务的实际机构/日期续补保留原任务、完整指标口径和来源，不因模型误填 `new` 丢失。多余旧空引用在修改计划前按指标、机构和日期校验并要求直接修正；本轮未获准草案可完整重组，历史任务和已执行目标保留。
- `harnessHost.ts`：正式澄清在发送、工具执行及回答边界结束本轮；内部修复落实为实际重提，网关忽略工具选择时也不执行无关读取；上下文探索不能代替正式业务处理。确有目录或引用证据缺口时保留探索能力。
- 提示词和工具描述：同步本轮目的、可信继承、候选确认、分页游标以及两类任务引用的使用契约。

没有增加超时或重试次数，没有针对某个银行、指标名称或日期添加运行时分支。验证目录中的原问法仅作为合成目录回归用例。
