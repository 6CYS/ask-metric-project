# 焦点与实际动作契约修复及稳定性验证

## 原因与改动

此前 [读取入口回归](history-focus-replay-2026-09-28.md) 已暴露：只切历史焦点或只换机构时，用户原文未必包含指标名称，旧宿主的指标命中约束没有生效。模型可输出“我将调用工具”后直接结束，导致焦点未切换或实际查询次数为零。只有成功进入工具链后，原来的焦点、字段来源及执行门禁才有效。

本次在 `harnessHost.ts` 与 `tools/turnContract.ts` 接入通用首动作契约。Pi 必须选择真实业务工具，或明确选择无业务副作用的普通回答；不再以是否提到指标决定是否需要实际调用。网关忽略工具选择要求时，使用原生内部工具回执纠错，最多两次，仍无动作则正式失败。没有添加第二个 Agent、问句关键词分支或从计划文字猜测业务参数，也没有锁死整个用户回合的历史来源。

普通回答不能夹带或随后追加业务动作；业务回执之后不能改报“无需动作”。其他优化和原有 Frame 关联、字段来源、历史索引、幂等、鉴权、澄清、只解析、错误保留及恢复行为沿用现有实现。

扩大模型回归又发现：模型虽调用了 `reuse_result`，却漏传 `baseReference`，实际回读当前第三笔而在文字中描述第一笔。模型工具 Schema 因此收紧为显式选择 `null`（新问题）、`current`（当前焦点）、历史选择对象，漏传直接拒绝，继承服务继续保留旧的内部省略语义。此改动没有取消普通追问的继承能力，只取消模型调用中的隐式来源选择。

幂等复核同时先复现了工具层把 current 展开成移动快照会导致同参数重试重新建操作的问题。最终由业务服务直接处理稳定的 current 值，在读取焦点前以稳定参数检查既有命令；执行成功、焦点推进后同轮同参数重试仍复用原操作。错误回执继续保留确切来源，不锁死整轮合法的多来源处理。

第三个实际模型回归缺口发生在八轮连续对话：第一问被模型拆成准备与执行，旧代码给两个解析阶段各建一个操作根，后面的 `ordinal=2` 因而选中了第一问的执行阶段。最终将同轮、同能力、未改条件的 READY→execute 处理为同一操作的快照推进，历史仍只计一笔；不删除快照，也不合并已经完成后的新分支。新增回归先失败后通过，覆盖 `resolve_more` 和 `execute` 两种准备模式。

## 自动回归

- Agent 全量：33 文件、370 项通过，其中历史引用专项 30 项。
- 类型检查、构建通过。
- 真实模型脚本独立 TypeScript 检查通过。
- 故障注入先复现旧实现直接交付计划；修复后同一 Pi 循环纠正并产生真实业务 Frame。
- 连续两次协议纠错后仍只有计划，原生 operation 正式失败，没有查询或无限重试。
- 普通问候及概念解释不建 Frame、不访问业务取数；即使网关随后提议查询也被阻止。
- 重开后新用户回合重新要求动作，上一轮回执不能解除本轮约束，纠错不追加用户消息。
- 原有缺项澄清、查询幂等、权限、错误恢复、旧操作恢复及模型超时测试继续通过。
- 模型省略来源被拒绝，显式 current 正常继承，空焦点拒绝；参数纠错保留来源；焦点推进后同参数重试不新增操作。
- 同轮准备到执行不重复占用历史序号，之后的“第二笔”仍指第二次业务操作；旧准备快照可回读。

受接口调整影响，普通回答测试现在显式调用普通回答工具，仍断言原回答持久化、用户消息不增加、没有业务查询；工具列表测试区分模型可见工具和宿主内部协议工具。没有删除有效行为断言来掩盖失败。

## 重复真实模型验证

正在对冻结后的运行代码执行九类场景、连续三轮验证，结果完成后写入本记录。所有目录和取数均为隔离合成实现，模型读取项目 `.env` 配置。每轮核对实际查询次数、完整指标/机构/日期、持久化焦点、必要结果回读、最终回答和结束状态；并记录回合耗时。

```sh
node --env-file=.env --import tsx scripts/check-history-focus-model.ts --live --repeat=3
```

`--case=名称` 可单独复核，`--repeat` 为 1 到 10；未加 `--live` 仅列场景，不代表执行了验证。

## 生效与边界

代码在当前工作区，未提交或推送；Agent 服务必须重新加载本次构建才生效，无数据库迁移，无旧会话数据改写。这里验证的是 Agent/Pi/焦点链与配置模型的配合，不等于真实业务数据库、浏览器交互、生产部署、长时间高并发或任意自然语言的稳定性保证。
