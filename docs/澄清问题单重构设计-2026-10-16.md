# 澄清问题单重构设计（PendingQuestion / Answer）

- 日期：2026-10-16
- 状态：草案，待评审；P0 已完成，P1-a（候选唯一编号清单）已落地，见第 11 节
- 范围：`agent-service`（semantic_v2 主路径、business-context 底座）、`frontend-vue`
- 关联文档：`docs/pi-business-context.md`、`docs/business-context-reference-recovery.md`

---

## 1. 背景

用户问数时经常出现“名称对应多个候选”的情况（例如“农商行”对应多家机构、“存款余额”对应多个口径）。系统会列出候选让用户选择，用户再用点选或自然语言回复。

当前实现中，“理解用户回复选了哪一项”主要由宿主用词表和正则完成。这与项目既定原则冲突：

> 不在多轮核心中按自然语言关键词、具体指标或机构名称分支。（`docs/pi-business-context.md`）
>
> 由大模型做意图识别，不另建分类模型，也不用关键词规则。（`docs/智能问数改造技术方案-汇报版.md`）

本文提出把“澄清”重构为**带身份的待答问题（PendingQuestion）**&#x4E0E;**结构化回答（Answer）**：点选和模型翻译都只是在回答问题单，宿主只核对合法性与原文依据，不再理解自然语言。

## 2. 现状

### 2.1 协议与路径

- 默认协议为 `semantic_v2`（`config.ts`：`AGENT_BUSINESS_PROTOCOL` 缺省取 `semantic_v2`）。
- 新会话写入 `semantic_v2` 标记；无标记或 `fixed_v1` 的历史会话只读，不再恢复执行（`harnessHost.ts` 第 305-307 行附近）。
- `semantic-task/` 是语义协议层；`business-context/` 是业务底座（类型、能力注册、字段解析、目录识别、执行适配、持久化），仍被 v2 直接依赖。

### 2.2 三套澄清机制

| 机制             | 位置                                                                              | 用途                                  | 编号/展示                                | 回复判定                                                        |
| -------------- | ------------------------------------------------------------------------------- | ----------------------------------- | ------------------------------------ | ----------------------------------------------------------- |
| 字段候选（v2）       | `semantic-task/service.ts` `selectSavedCandidates`；展示在 `feedback.ts`、`store.ts` | 机构/指标/日期字段的 `needs_confirmation` 候选 | `feedback.ts` 生成“1. 名称”，有首推时重排       | 小句切分 + 否定词 + `candidateOrdinal` 正则 + 肯定词表 + 名称命中            |
| 目标澄清（v2）       | `clarify_business_turn`；`store.ts` `SemanticClarification`                      | 多个合理目标解释时保存追问与备选引用                  | `pending_clarification.alternatives` | 模型以 `reference` + `context_action=resume` 续接                |
| 字段候选（fixed_v1） | `business-context/clarificationOptions.ts` `selectOptions`                      | fixed_v1 的 Frame 候选                 | 全局连续编号 + `choiceSet`                 | 点选 `optionIds` / 目录编码 / 名称命中 / `replyOrdinals` 正则 / 肯定与否定词表 |

三套机制的编号、展示和判定各自独立，词表也不一致：

| 项    | fixed_v1 `selectOptions`                | v2 `selectSavedCandidates`               |
| ---- | --------------------------------------- | ---------------------------------------- |
| 肯定词  | 是、是的、对、对的、可以、好、好的、同意、确认、没错、就是这个、就这个     | 好（的）、是（的）、可以、确认、同意、就按你说的                 |
| 否定处理 | 整句命中即返回空                                | 按小句排除                                    |
| 序号识别 | `replyOrdinals`：整句列表或句中任意位置的“第N个/选N/N号” | `candidateOrdinal`：整小句只能是序号，前缀只认“选/用/就用” |

### 2.3 模型在选择中的角色

- v2 模型能看到带编号的候选名称（`feedback.ts`、`store.ts` 投影 `candidates: [{name}]`）。
- 但宿主有意不采信模型：`selectSavedCandidates` 注释为“只用真实用户原句选择已保存候选，模型填写的确认文本不能建立选择事实”。
- fixed_v1 模型只看到候选数量（`modelView.ts` `pendingChoices.count`），只能提交 `{confirm:true, evidence:{decision:'accept', sourceText}}`，且“同一项有多个候选时须用户明确选择，不能用 accept 任选”。

结论：模型即使理解了用户选哪一项，也没有结构化通道提交。

### 2.4 前端点选通道

- 前端 `BackendNextChatPanel.vue` 点选时发送 `clarification_selection: {frame_id, option_ids}`。
- `routes.ts` 校验形状后放入请求；`harnessHost.ts` 转为 `clarificationSelection`。
- fixed_v1 的 `service.ts` 会逐项核对 `optionIds`（属于当前清单、无重复、非空）。
- **已确认（P0）**：全 `src/` 中读取点选的只有 fixed_v1 的 `business-context/service.ts`（读 `confirmationSelection`）；`semantic-task/` 没有任何读取方。v2 下前端点选被静默丢弃。
- **疑点**：宿主写入的字段名是 `clarificationSelection`，fixed_v1 读取的是 `confirmationSelection`，静态检索未发现两者的映射，fixed_v1 的点选也可能未生效。fixed_v1 会话已只读，影响有限，但应在 P1-b 一并确认。

### 3.2 已验证（v2 `selectSavedCandidates`）

测试文件 `agent-service/specs/semantic-task/candidateReplyEdgeCases.spec.ts`，候选为 [无锡, 江阴, 苏州]：

| #  | 用户回复                 | P0 实测                | 定性          | 归属        |
| -- | -------------------- | -------------------- | ----------- | --------- |
| ①  | 不是第一个，是第二个           | 拒收                   | 序号正则前缀不认“是” | P2（结构化回答） |
| ①b | 不是无锡的，是江阴农商行         | 选中江阴                 | 正确（小句级否定）   | —         |
| ②  | 没错，不要改日期（单一提案）       | 拒收                   | 肯定词表无“没错”   | P2        |
| ④  | 改成10月3号              | 拒收                   | 正确（不误选）     | —         |
| ⑤  | 行 / 嗯 / OK / 没问题 / 对 | 拒收                   | 不在肯定词表      | P2        |
| ⑥  | 首推江阴置顶后回复“第1个”       | **选中无锡**（展示第 1 项是江阴） | **静默误选**    | P1-a（已修复） |
| ⑥b | 首推江阴置顶后回复“第2个”       | **选中江阴**（展示第 2 项是无锡） | **静默误选**    | P1-a（已修复） |

根因：`feedback.ts` 在展示时自行把唯一首推置顶再编号，`selectSavedCandidates` 却按存储数组下标取候选，`store.ts` 给模型的投影又是第三种顺序。同一份候选存在三处独立的“编号”事实，是问题 3.3-3 的具体体现。

### 3.3 结构性问题

1. **宿主做自然语言理解**：词表与正则无法穷举银行用户的口语说法，每次补规则只修个例。
2. **理解者与裁决者错位**：最懂语义的模型没有提交选择的通道；做决定的规则不懂语义。
3. **三套机制并存**：编号、展示、判定各一份，词表已不一致，修一处不影响另一处。
4. **展示编号与选择编号不一致**（P0 已复现为静默误选，P1-a 已修复）：`feedback.ts` 有首推时重排展示，`selectSavedCandidates` 按存储数组下标取候选。
5. **点选通道在 v2 未接通**（P0 已确认，P1-b 处理；见 2.4）。
6. **无版本防护**：条件变化后，用户对旧清单的回复（或旧页面的点选）缺少明确的过期判定。
7. **复合回复被整句拒绝**：“第二个，日期改成上月”这类“回答 + 改条件”的说法缺少分离处理。
8. **选错不可见**：确认后没有固定明示“按哪一项查询”，用户不易发现误选。
9. **质量不可度量**：没有记录选择来源与事后改选，无法统计误选率。

## 4. 目标与非目标

### 4.1 目标

- G1：宿主不再依赖词表或正则理解用户回复；语义理解归模型，裁决归宿主。
- G2：所有澄清使用同一数据结构，展示、按钮、模型视图、核对共用一份编号。
- G3：点选成为一等公民，在 v2 下可靠生效。
- G4：保持安全边界：选择必须落在已保存清单内；选择依据必须锚定本轮用户原文；编码不交给模型。
- G5：支持一句话中“回答 + 修改其它条件”。
- G6：确认结果对用户可见并可一键改选。
- G7：选择质量可度量。

### 4.2 非目标

- 不改变字段解析、目录识别、权限复核、执行门禁本身的规则。
- 不在本期实施“按风险自动执行首推”（见 5.8，需产品确认）。
- 不恢复 fixed_v1 会话的执行能力。

## 5. 设计

### 5.1 核心思想

```
          ── 生成 ──▶  PendingQuestion（唯一事实源）──▶ 用户文字 / 前端按钮 / 模型视图
宿主                                   ▲
          ◀─ 核对 ──  Answer ◀── 点选（前端直接组装）
                              ◀── 打字（模型翻译，附原文片段）
```

- 问题单由宿主生成并持久化，是编号与选项的唯一来源。
- 回答只有一种结构，来源可以是点选或模型。
- 宿主只做客观核对，不做语言理解。

### 5.2 数据模型

```ts
interface PendingQuestion {
  question_id: string;              // 宿主签发，会话内唯一
  version: string;                  // 绑定目标快照摘要（可复用 snapshotDigest）
  origin: "field_candidates" | "target_alternatives";
  scope: {task_ref: string; target_ref?: string; field?: string; item?: number};
  kind: "single_choice" | "multi_choice" | "confirm" | "free_input";
  prompt: string;                   // 展示给用户的问句（宿主生成）
  options: Array<{
    option_id: string;              // 稳定标识：字段 + 待确认项 + 候选键
    no: number;                     // 展示编号，与展示顺序一致
    label: string;                  // 业务名称，不含编码
    aliases?: string[];             // 用于核对原文依据，不用于理解
  }>;
  preferred?: string;               // 首推 option_id
  status: "open" | "answered" | "superseded" | "abandoned";
  created_turn: string;
}

interface Answer {
  question_id: string;
  version: string;
  choice:
    | {type: "select"; option_ids: string[]}
    | {type: "accept"}              // 仅用于唯一提案或唯一首推
    | {type: "reject"}              // 不接受提案，继续等待
    | {type: "none_of_these"};      // 都不是，配合新条件提交
  evidence:
    | {channel: "click"}
    | {channel: "model"; excerpt: string};
}
```

说明：

- `option_id` 沿用 fixed_v1 `ClarificationOption.id` 的生成方式（字段 + 待确认项 + 候选键），同名不同编码可区分。
- `no` 由生成函数一次性确定；首推置顶等排序在生成时完成，展示与核对不再各自排序。
- `version` 变化即代表问题失效，旧回答一律拒收。

**与已落地代码的对应（P1-a）**：`semantic-task/candidateOptions.ts` 的 `CandidateOption {no, optionId, label, candidate}` 就是 `PendingQuestion.options` 的最小形态。P1-c 引入完整 `PendingQuestion` 时直接复用该函数生成 `options`，不得另写第二套编号逻辑。

**架构约束（不变量）**：

| 编号 | 约束                                            | 保障方式                                                             |
| -- | --------------------------------------------- | ---------------------------------------------------------------- |
| I1 | 候选的编号与排序只由 `candidateOptions` 产生；首推置顶规则只在此处定义 | 代码评审；单测“候选唯一编号清单”                                                |
| I2 | 宿主按编号或 `optionId` 取候选，禁止按存储数组下标解释用户编号         | 单测 ⑥ ⑥b；建议增加静态检查，禁止 `semantic-task/` 内出现 `candidates[…index]` 形式 |
| I3 | 用户文字、模型投影、前端按钮展示的编号必须来自同一清单                   | feedback.ts / store.ts 已改用清单；前端在 P1-b 对齐                         |
| I4 | 点选与结构化回答按 `optionId` 绑定，不按展示文字或编号重新匹配         | P1-b、P2                                                          |

### 5.3 生成时机与生命周期

| 事件                                          | 问题单变化                                             |
| ------------------------------------------- | ------------------------------------------------- |
| 字段解析得到 `needs_confirmation` / `ambiguous`   | 为每个待确认项生成 `single_choice`（唯一提案时为 `confirm`）       |
| `clarify_business_turn`                     | 生成 `origin=target_alternatives` 的 `single_choice` |
| 缺必填字段（`needs_user`）                         | 可选生成 `free_input`（本期可不实现）                         |
| 收到合法 Answer                                 | `answered`，字段绑定所选候选                               |
| 目标条件被修改、快照变化                                | 旧问题 `superseded`，必要时生成新版本                         |
| `context_action=abandon` / 新问题 `source=new` | `abandoned`                                       |

存储建议放在 `semantic-task/store.ts` 的计划快照中，与 `SemanticClarification` 合并为同一字段（例如 `pending_questions`）。

### 5.4 协议与模型契约

**模型视图**（注入 `admitted_context` / 状态投影）：

```json
{"pending_questions": [{
  "question_id": "q_7f3",
  "version": "a91c",
  "kind": "single_choice",
  "prompt": "「农商行」对应多个机构，请选择：",
  "options": [{"no": 1, "option_id": "o1", "label": "无锡农商行"},
              {"no": 2, "option_id": "o2", "label": "江阴农商行"}]
}]}
```

**提交方式**：`resolve_business_turn` 增加可选顶层字段 `answers: Answer[]`，与 `operations` 同次提交。

```json
{
  "protocol_version": 2,
  "intent": "query",
  "answers": [{"question_id": "q_7f3", "version": "a91c",
               "choice": {"type": "select", "option_ids": ["o2"]},
               "evidence": {"channel": "model", "excerpt": "是第二个"}}],
  "targets": [{"source": {"kind": "current"},
               "operations": [{"field": "time", "action": "set", "value": "上月末"}]}]
}
```

提示词增补（精简版约一句）：

> 用户回复待答问题时，用 answers 按 question_id 提交所选 option_id，excerpt 原样摘自本轮原句；否定、转折按语义理解；无法判断就不提交，由宿主重问。

对应地，字段级 `confirm` 动作保留兼容，但不再承载“选哪一项”的语义。

### 5.5 宿主核对规则

按顺序核对，任一失败则该问题保持 `open`，返回可修复的反馈并重问用户，不猜。

| #  | 规则                                                              | 失败码（建议）                   |
| -- | --------------------------------------------------------------- | ------------------------- |
| R1 | `question_id` 存在且 `status=open`                                 | `QUESTION_NOT_OPEN`       |
| R2 | `version` 等于当前版本                                                | `QUESTION_SUPERSEDED`     |
| R3 | `option_ids` 全部属于该问题，无重复；`single_choice` 恰一项                    | `OPTION_NOT_IN_QUESTION`  |
| R4 | `accept` 仅用于 `kind=confirm`，或 `single_choice` 且恰有一个 `preferred` | `ACCEPT_NOT_UNIQUE`       |
| R5 | `channel=model` 时，`excerpt` 锚定本轮原文（`hasInputEvidence`）          | `EVIDENCE_NOT_IN_INPUT`   |
| R6 | `select` 时，`excerpt` 含所选项的 `no`（含中文数字）、`label` 或 `aliases` 之一   | `EVIDENCE_NOT_FOR_OPTION` |
| R7 | `accept` 时，`excerpt` 非空；是否为同意语义由模型负责，宿主不判词                      | —                         |
| R8 | 点选与模型回答同轮冲突时，以点选为准并记录冲突                                         | —                         |

要点：

- R6 是“证据存在性”检查，不是语义理解。它保证模型不能凭空选一项，又不需要词表。
- 不再做否定词判定。“不是第一个，是第二个”由模型理解为选 2，excerpt=“是第二个”，R6 命中“二”。
- 若担心模型把否定句当成选择，可保留一条轻量的反向保护：**excerpt 自身**以否定词开头时拒收（只判 excerpt，不判整句）。这一条是否保留列为待决问题。

### 5.6 优先级与兜底

1. 前端点选 Answer（`channel=click`）。
2. 模型 Answer（`channel=model`）。
3. 兜底规则（过渡期保留，最终删除或收窄）：仅当整句回复**只是**序号（“2”“第二个”）或**只是**某个选项名称时生效；不做句中局部匹配，不用肯定/否定词表。
4. 以上都没有结果：问题保持 `open`，重新展示同一问题单。

每次启用兜底都记录事件，用于评估删除时机。

### 5.7 复合回复

| 用户说法        | 处理                                                        |
| ----------- | --------------------------------------------------------- |
| 第二个，日期改成上月  | `answers` 选 o2；`operations` 修改 time。先应用回答，再应用修改           |
| 没错，不要改日期    | `answers` 为 accept；“不要改日期”无需操作                            |
| 都不是，我要苏州的   | `answers` 为 none_of_these；机构按普通 value / suggestion 路径重新解析 |
| 先不选了，看看上次结果 | 不提交 answers；`context_action=defer`                        |

顺序约束：同一字段既有 Answer 又有 `set` 时，以 `set` 为准并把问题标为 `superseded`；不同字段互不影响。

### 5.8 明示与改选

- 回执与答案固定追加一行：“已按第 2 项「江阴农商行」确认”。实现参考 `business-context/resolutionNotice.ts` 的 `orgResolutionNotices` / `withOrgResolutionNotices`。
- 前端在该行提供“改选”入口：以新版本重新打开同一问题，改选后仅重新执行受影响的目标。
- 明示文案由宿主生成，不依赖模型。

### 5.9 按风险减少提问（可选，需产品确认）

当存在唯一首推、且为字面或别名命中、且属于低风险字段时，可直接按首推执行，同时明示并提供改选，不先提问。该策略改变交互语义，银行场景需业务方认可，并以 5.10 的改选率作为放宽或收紧依据。

### 5.10 度量

每次问题生命周期事件写入结构化日志：

| 指标     | 定义                          | 用途          |
| ------ | --------------------------- | ----------- |
| 选择来源分布 | click / model / fallback 占比 | 评估兜底可否删除    |

### 11.2 P1-a 唯一编号清单（2026-10-16）

**为什么不是局部修补**：只把 `selectSavedCandidates` 改成与 `feedback.ts` 同样的重排，会形成第二份重排逻辑，下次任一处调整排序又会分叉；`store.ts` 给模型的投影也会继续是第三种顺序。因此按本文档 G2 先建立唯一事实源，再让所有消费方依赖它。

| 文件                                      | 改动                                                                                          |
| --------------------------------------- | ------------------------------------------------------------------------------------------- |
| `semantic-task/candidateOptions.ts`（新增） | `candidateOptions()` 生成 `{no, optionId, label, candidate}`，唯一首推置顶；`preferredOption()` 取唯一首推 |
| `semantic-task/feedback.ts`             | 待确认展示改为从清单生成，删除本地重排                                                                         |
| `semantic-task/service.ts`              | 序号按清单 `no` 取候选，不再按存储下标；`selectSavedCandidates` 导出供测试                                        |
| `semantic-task/store.ts`                | 两处模型状态投影改为清单顺序，并附 `no`，模型看到的编号与用户一致                                                         |

行为变化：只在存在唯一首推、且首推不在第 1 位时，宿主对序号的解释与模型投影顺序变化（由错变对）；其余情况不变。
