# 问数失败提示优化设计

## 1 设计目标与主案例

用户在对话中补充日期后，看到了以下提示：

> 本轮工具调用参数连续未通过校验，系统未完成查询。可以重试本轮问题，无需重复已确认的条件。

这段话把系统内部的执行原因直接交给了业务用户，还要求用户理解“本轮问题”和“已确认条件”才能继续操作。类似的模型超时、工具限额、证据拦截和语义校验提示，来自不同生成入口，措辞也不一致。

**本方案优化的是问数对话中这类失败提示及其生成链路。用户看到结果是否取得、缺少什么、当前能做什么；内部诊断保留具体失败原因。** 提示保持简短，已有结果与条件按原业务状态保留。

针对截图中的内部参数处理失败，最终展示采用：

> 没能完成这次查询。

这句话只用于内部处理失败且没有可交付结果的情况。它不要求用户修改原本正确的业务条件，也不承诺等待、换问法或发送“重试”就一定能恢复。如果系统确实需要用户补充日期，则直接询问日期；如果已有部分结果，则展示结果并说明缺少的部分。

本方案以当前工作区代码为依据。截图中的原句也保留在历史验证记录中；当前源码已经出现其他版本的措辞，不能只替换这一句历史文本。

## 3 用户提示规则

### 3.1 按用户处境表达

内部错误码继续细分，用户提示按可理解、可操作的处境收敛。下表是展示规则，不增加业务状态机。

| 用户处境 | 展示示例 | 用户能做什么 |
| --- | --- | --- |
| 系统内部处理失败，没有可交付结果 | 没能完成这次查询。 | 保留原提问；不要求用户检查内部参数或反复换问法。 |
| 已明确是短暂服务故障，本次操作已确认结束 | 服务暂时不可用，请稍后再查询。 | 服务恢复后重新发起查询。 |
| 需要补充真实业务条件 | 要查询哪个时间范围？ | 在现有澄清卡或输入框中补充缺项。 |
| 用户输入存在具体可修正的问题 | 开始日期不能晚于结束日期。 | 修改对应日期，保留其他有效输入。 |
| 查询成功，正式结果明确为零行 | 当前条件下未查到数据。 | 查看本次机构、指标、日期，需要时调整条件。 |
| 一部分查询目标已有可展示结果 | 已查到「目标甲」；「目标乙」未完成。 | 查看已有结果，明确哪些内容尚未取得。 |
| 全部所需数据已有可查看结果，说明文字生成失败 | 数据已查到，结果说明未完成。 | 直接查看表格或数值。 |
| 查询已完成，但结果读取或展示失败 | 查询已完成，结果暂时无法显示。 | 重新加载原结果。 |
| 连接中断，正在实际执行重连 | 连接已中断，正在重新连接。 | 等待读取原操作状态。 |
| 重连未成功，任务结论仍未知 | 连接已中断，暂时无法确认查询是否完成。 | 重新打开原会话查看状态。 |
| 登录失效 | 登录已过期，请重新登录。 | 使用现有登录入口。 |
| 数据权限不足 | 当前账号无权查看这项数据。 | 确认需要查询的范围或联系权限负责人。 |
| 选择已过期 | 选项已更新，请重新选择。 | 加载当前问题后再选择。 |
| 已有选择被正式受理 | 已按你的选择处理。 | 继续查看查询或剩余问题，不显示失败。 |
| 用户停止已被确认 | 已停止。 | 查看此前已取得的结果。 |
| 停止请求未得到确认 | 暂时无法确认是否已停止。 | 查看原操作状态。 |

“没有数据”必须来自成功的零行结果；表格空白、请求失败、权限拒绝和响应缺失都不能据此生成无数据提示。部分结果的说明必须同时呈现，不能用不完整的数据形成完整排名、汇总或比较结论。

### 3.2 只让用户处理自己能处理的事情

只有同时满足“属于用户业务输入、能指出具体问题、用户能够修正”时，才提示修改条件。模型工具参数、协议、任务引用、来源绑定、重复提案和执行许可错误，均由系统内部处理；即使对应 HTTP 422，也不能直接转成“请检查查询条件”。

内部错误不统一附加“请稍后重试”。已确认的短暂服务故障可以提示稍后查询；实现或参数组装错误使用简短未完成提示。原因未知时不猜测归因。

正常候选确认和业务能力说明继续使用具体业务语言。例如，需要用户区分两个指标口径时，说明两个口径的区别；确实不支持某种查询时，说明不支持的查询内容，不使用内部能力码。

### 3.3 对截图中后半句的处理

删除技术失败提示里固定附带的“可以重试本轮问题，无需重复已确认的条件”。是否能继承条件，由现有业务上下文和恢复路径决定。

用户下一次输入“重试”时，仍按既有上下文恢复逻辑处理；有唯一、有效的条件来源才能使用，缺少哪项就只询问哪项。提示优化不新增“续跑”“仅重试失败部分”等操作，也不改变现有准入与执行规则。

## 4 页面如何呈现

### 4.1 保留当前布局，分开答案与异常提示

截图位置继续作为本次操作的反馈位置。已有答案和结果表保持原位，失败说明通过独立的 `user_notice` 展示，不拼入业务答案正文。

| 内容 | 呈现方式 |
| --- | --- |
| 正常结果、业务解释 | 原答案与结果区。 |
| 需要确认的机构、指标或日期 | 原澄清卡。 |
| 本次查询未完成、状态未知、部分结果 | 当前助手消息内一条主要状态提示，与受影响结果相邻。 |
| 结果表读取、下载等局部操作失败 | 对应表格或按钮附近提示，保留查询本身的结论。 |
| 影响整个页面的登录失效 | 现有登录提示统一处理，避免每个并发请求复制一条。 |

无结果的内部失败只显示一句提示，结束加载，不留下空白答案框或仍在生成的假象。存在部分结果时，先保留可用结果，再在明显位置标注未完成项。用户无需展开执行过程才能知道结果不完整。

澄清、空结果、等待重连和主动停止使用普通状态样式；确认失败使用已有错误样式。提示含可见文字，不只依赖颜色。动态状态更新使用适当的 `role="status"`；需要立即注意的失败才使用警报语义，流式答案和心跳不逐字触发警报。[W3C 状态消息说明](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

### 4.2 同一操作一条主提示，允许更新

重复的快照、终态和请求异常更新同一处提示，不追加新的失败气泡，也不同时弹出相同内容的横幅或弹窗。局部读取失败在对应区域定位；只有影响整体结果使用时，才由主提示概括其影响。

提示随同一操作的权威状态更新：

1. 自动纠错或重试仍在进行时，保留简短进度；内部失败尝试不作为最终失败展示。
2. 浏览器断流时，先显示连接状态，复用 `observeAgentSession` 观察原操作，不重发用户问题。
3. 收到最终成功快照后，移除本地连接中断提示，显示正式结果。
4. 收到最终失败快照后，显示其用户提示；重复 `run_terminal` 不再增加第二条。
5. 单独的 `idle`、连接恢复或其他操作的事件，不能清除本操作的明确失败。
6. 历史回放从正式记录重建相同结论；本地连接状态不写入业务历史正文。

更新依据是操作归属和正式事实，不采用“第一条错误永远保留”或“后到事件一律覆盖”的规则。

### 4.3 操作入口与文案一致

“查看状态”复用原会话快照与观察接口；“重新加载”只读取原结果；“重新选择”加载当前问题。“重新登录”沿用现有认证流程。提示中的动作只在对应入口实际可用时出现。

本次保留现有提问入口。内部失败不增加一键重跑按钮；任务状态未知时优先查看原操作。服务短暂故障后重新提问属于新请求，不能称为恢复原操作。只读查询也会创建任务，因此连接丢失不能直接作为重复提交的依据。[Microsoft 重试模式](https://learn.microsoft.com/en-us/azure/architecture/patterns/retry)

## 5 实现分工与最小数据调整

### 5.1 三类信息分别服务各自读者

| 信息 | 服务对象 | 责任 |
| --- | --- | --- |
| `SemanticIssue`、原错误码、工具纠错信息 | 模型和宿主 | 保留准确失败原因及已有恢复指令，支持内部纠错。 |
| `user_notice`、澄清问题、正式结果 | 业务用户 | 只表达业务处境、结果影响和可用操作。 |
| 结构化日志与原生执行记录 | 开发与运维 | 定位失败阶段、具体原因和关联操作。 |

用户文案由宿主根据正式状态确定生成。模型继续理解业务问题、选择与分析内容，系统失败提示不增加模型改写调用。前端负责位置和更新，不从异常长文本重新判断业务完成情况。

用户主动追问“为什么失败”时，沿用现有只读解释路径：读取已有回执，说明能够确认的业务原因和是否取得结果，不自动重查。同步调整 `semantic-task/prompt.ts:8` 的 `FAILURE_EXPLANATION_CONTRACT` 与 `docs/pi-semantic-task/protocol.md` 中的失败解释约定，避免模型把读到的 `issues.message` 原样复述给用户；可公开原因与内部诊断仍分开。

### 5.2 只增加一份公开提示

在现有 Agent HTTP 错误、助手消息投影和终态数据中，按需要增加可选字段：

```ts
interface UserNotice {
  message: string;
  tone: "info" | "warning" | "error";
}
// user_notice?: UserNotice
```

业务状态、结果引用、问题版本和操作身份继续使用现有字段，不再复制进提示对象。按钮由所在页面已有上下文决定，不增加恢复策略或动作编排协议。

前端 `AgentApiError` 与 `ApiError` 保留结构化 `code`、`requestId` 和可选 `userNotice`；`message` 只承担异常描述，不再默认视为可展示文案。后端已有 `ErrorResponse` 保持 `code/message/request_id/details`，Agent 的 `BackendApiError` 补齐请求关联信息即可。

前端只展示服务端明确提供的 `user_notice`，或根据已知错误码、HTTP 状态和当前操作生成的固定提示。纯浏览器断连属于前端可确认的连接事实，由前端生成连接提示。非 JSON 响应、异常原文和任意中文 `message` 不进入业务答案。

### 5.3 宿主统一生成，投影统一使用

在 Agent 服务增加一个小型公开提示函数，集中处理第 3 节中的异常映射。输入直接使用现有运行结果、业务完成情况和正式结果引用；输出 `UserNotice | undefined`。已确认结束、没有可交付结果且没有更具体公开原因的内部错误使用“没能完成这次查询。”，原始原因仍保留。

当前 `TOOL_LIMIT_ANSWER`、`EVIDENCE_BLOCKED_ANSWER` 等固定文本还参与内部相等判断。内部原因标识继续区分，先在公开投影处映射为用户提示；不能把这些常量都改成同一句话后，继续用它们判断不同拦截分支。

具体接入如下：

1. **工具层保留内部诊断。** `errorResult` 分开模型可读信息与公开提示，不再将同一参数复制到 `public_answer`；422 字段路径继续供模型纠错。`semanticPublicAnswer` 只组装用户可处理的业务说明、正式问题和受理信息，不再拼接全部 `issues.message`。
2. **宿主收尾依据真实业务结论。** 重复参数失败、工具限额和证据交付失败进入统一公开提示。`SEMANTIC_NO_PROGRESS` 与最初拒绝原因都保留。原生操作 `completed` 只表示操作已结束，不能据此覆盖业务失败或待澄清结论。401 与 403 分开处理，避免把登录失效映射为数据权限不足。
3. **保持结束条件独立。** 当前 `harnessHost.ts:653` 用公开答案是否存在决定 `terminate`。移出系统失败正文后，应继续按既有终结状态与 `continuation` 决定是否结束，不能因答案为空重新进入模型循环，也不能把待内部修正的状态提前结束。模型 `content` 保留其需要的结构化纠错信息。
4. **正式回执与运行结论可回放。** 业务终结提示随现有最终工具 `details` 保存；模型或原生执行异常从对应正式错误记录投影。仅在最终 HTTP/SSE 响应发生、没有可持久化业务记录的拒绝，按请求响应展示。提示不另建存储。
5. **统一页面投影。** `sessionProjection` 与路由终态使用同一生成函数，初次 SSE、观察流、GET 历史共享映射。只有提示、没有答案时，也输出带 `user_notice` 的助手消息，允许 `text` 为空；前端不能以无正文为由丢掉它。`run_terminal` 更新当前消息，不再让前端用另一套原文规则补一句失败。

`browserToolDetails` 中的诊断说明与业务展示数据也应分开：保留前端实际消费的结果引用、状态、条件、问题和受理回执，停止把内部问题描述当作公开答案。`semantic_task` 包装中的待确认问题与受理记录必须继续传到前端，避免提示清理破坏现有点击链路。

### 5.4 前端维护提示，不修改答案

`DisplayMessage` 增加独立的 `userNotice`，`withFailureNotice` 的“追加正文、锁定第一次提示”逻辑改为更新此字段。保持 `response.answer`、`answer_blocks` 和结果表原值；确实需要标明不完整时，用状态提示表达。

保留服务端已有 `entry_id`，实时更新使用当前请求与操作关联；历史重建使用原条目关联。前端现有随机 `id` 可以继续用于组件，不承担错误归属。连接重试与最终业务提示共用当前消息的展示位置，终态快照可以替换本地临时提示。

历史中的结构化失败按错误码和已知失败记录重新投影，存储原文保持原样。兼容处理仅针对可识别的失败记录和既有固定失败模板，不对所有正常回答做全局关键词删除。

## 6 系统日志保留什么

日志记录具体原因，提示记录用户能理解的影响。两者通过既有请求、会话、操作和任务标识关联，不把内部错误码、参数路径、SQL、模型网关响应展示给用户。

| 位置 | 继续保留或补齐的诊断信息 |
| --- | --- |
| Agent 接纳与执行收尾 | `request_id`、`session_id`、已取得的 `operation_id`、错误码、失败阶段、原始内部原因、最终业务结论。 |
| 语义与工具失败 | 原拒绝码、`SEMANTIC_NO_PROGRESS` 等终止原因、已有任务引用和纠错经过。 |
| 后端请求与查询执行 | 现有 `request_id`、`trace_id`、任务与结果引用、失败节点、异常类型和定位信息。 |

后端已有 `core/errors.py`、`core/request_context.py` 和 `core/logging.py`；Agent 已有 JSON 关联日志。沿用其格式和脱敏约定，只补齐本次错误转换处丢失的关联信息与原因。例如 `routes.ts` 的通用异常出口和 `semantic-task/tools.ts` 的异常转换应留下可关联的失败记录，再返回短提示。

自动恢复中的尝试与最终失败沿用既有日志级别约定。用户界面去掉技术说明，不能连带删除内部错误、吞掉异常或把失败记录改成成功；也不为“保留详细日志”额外输出原始业务数据、凭据或完整第三方响应。

现有执行过程可保留“正在查询、正在整理结果、未完成”等用户可理解的阶段。具体参数错误继续留在内部记录，用户不用打开调试面板排查自己的提问。

## 8 验收场景

验收关注用户最终看到的内容、实际状态与原操作是否一致，不以错误码数量减少作为完成标准。

| 编号 | 场景 | 预期结果 |
| --- | --- | --- |
| U1 | 用户补充日期，内部参数连续校验失败且没有正式结果，覆盖截图场景。 | 仅显示“没能完成这次查询。”；无工具、参数、批次、协议等术语，无“无需重复条件”承诺；日志保留实际拒绝码和终止原因。 |
| U2 | 工具调用限额、证据交付失败、未知内部异常分别结束，均无可交付结果。 | 使用同一简短未完成提示；内部原因仍可区分；原终止行为不变。 |
| U3 | 内部参数校验先失败，模型在既有循环中纠正后完成。 | 展示正式结果，用户界面没有残留的失败正文或额外错误弹窗；模型仍获得所需字段级纠错信息。 |
| U4 | 真正缺少日期；另测开始日期晚于结束日期。 | 前者询问日期，后者指出日期关系；均保留其他已确定条件，不显示内部处理失败。 |
| U5 | 两个目标只完成一个；另测全部数据可见、说明生成失败。 | 前者明确已完成与未完成项；后者提示说明未完成。两者保留表格与回答块，不混为整轮无结果。 |
| U6 | 成功零行；另测结果读取失败导致表格空白。 | 前者显示无数据，后者显示加载失败并读取原结果；不能相互转换。 |
| U7 | SSE 断流，观察原操作后恢复成功；另测重连耗尽仍无结论。 | 前者连接提示更新为结果，后者保持状态未知；都不自动再次发送用户问题。 |
| U8 | 同一失败先后经快照、终态、异常和刷新进入页面。 | 同一处一条主提示；无逐次追加，刷新前后结论一致。 |
| U9 | 明确失败后收到 `idle`；另测旧操作事件在新操作期间到达。 | 既有失败不被空闲事件清除，旧事件不修改新操作提示；同操作正式成功结果可以替换临时未知状态。 |
| U10 | 登录失效 401；另测有登录身份但数据权限不足 403。 | 分别提示重新登录和权限不足；并发 401 不复制多条登录提示。 |
| U11 | 选择已失效、选择已受理、受理状态未知分别发生。 | 分别引导重新选择、显示已处理、查看状态；不统一提示选择失败，也不自动重发未知提交。 |
| U12 | 用户停止成功；另测停止请求未确认。 | 分别显示已停止和停止未知，保留已有结果，不能仅凭浏览器中止宣称后台已停止。 |
| U13 | 返回中文内部异常、未识别错误码或代理 HTML 正文。 | 页面使用对应处境的固定提示，不透传原文；排障记录仍可关联具体原因。 |
| U14 | 一次查询成功，随后下载失败或结果表加载失败。 | 就近提示失败；成功查询不变成失败，不重复向聊天追加系统错误。 |
| U15 | 正常澄清、多问题选择和已有直接结果交付经过新投影。 | 问题、选项身份、受理记录及结果引用保持可用；不因精简 `semantic_task` 而丢失点击反馈。 |
| U16 | 把系统失败移出 `semanticPublicAnswer` 正文。 | 原本应结束的操作仍结束；待模型修正的操作继续既有循环，不出现空白挂起或新增重试循环。 |
| U17 | 用户在失败后问“为什么”，没有要求重新查询。 | 说明可确认的公开原因和结果状态，不复述内部参数说明，不新建任务或发起 SQL。 |

测试优先扩展现有 `agent-service/specs/semantic-task/host.spec.ts`、`specs/routes.test.ts`、`specs/directAnswerProjection.spec.ts`、`specs/questionProjection.spec.ts`，以及前端 `specs/lib/queryErrors.spec.ts`、`specs/lib/agentApi.spec.ts`、`specs/components/chat/BackendNextChatPanel.spec.ts`。公共提示映射用少量代表性错误覆盖，不复制所有错误码生成重复测试。

开发完成后先运行改动相关用例及类型检查，再做截图场景、断流恢复、刷新历史和已有结果保留的页面验收。Agent 使用现有 `npm test -- <相关测试文件>`、`npm run typecheck`；前端同样使用已有脚本并执行 `npm run build`。如实际修改后端错误信封，追加 `backend-next/tests/test_error_envelope.py`。最后执行 `git diff --check`。

## 9 设计依据

业务输入问题应指出可修正的位置；用户无法处理的服务问题应说明影响及有效下一步。依据为 [GOV.UK Error message](https://design-system.service.gov.uk/components/error-message/)。本方案将其应用于澄清与系统失败的分工，保留有效输入。

面向开发、管理员和最终用户的信息可以分开；用户提示应采用其能够理解的术语，避免已知原因也被一个笼统错误掩盖。依据为 [Microsoft Error Message Guidelines](https://learn.microsoft.com/en-us/windows/win32/debug/error-message-guidelines)。本方案只合并用户无法区分、也无不同操作的内部失败，登录、权限、空结果与部分完成仍分别表达。

动态状态应能被辅助技术感知，同时避免无必要地中断用户。依据为 [W3C Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)。连接失败不等于业务执行失败，重新发送前应区分原操作状态与重复执行，依据为 [Microsoft Retry pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/retry)。
