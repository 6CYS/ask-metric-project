向量检索在这里怎样参与？

指标目录先做文字检索；没有精确命中且 embedding 功能启用时，可以计算语义相似度，补充近似推荐。本次未检查运行开关，不能说当前请求一定使用了向量检索。

这个路径没有调用专门的 reranker 模型；按匹配规则或相似度排序，不等于已经接入“模型重排”。

第 1 / 8 步 · 问题进入 Agent

分词、文字检索、向量检索、重排，各放在哪里？

这些是检索中可以采用的方法，不是每次提问都必须走一遍的步骤。文字与向量可以各自召回候选，也可以配合使用。

先补一个关键概念：Embedding 是什么？

Embedding（向量化）把文字转换成一串表示其含义特征的数字。这串数字叫“向量”，主要用于计算相似性；它不是银行指标值，也不是模型生成的回答。

你的问题

紫金银行的经营状况如何？

↓ Embedding 模型

问题的数字表示（向量）

候选资料

指标名称、说明等目录文本

↓ 使用相互兼容的向量模型

各条资料的数字表示（向量）

两边比较相似程度 → 找出候选 → 再核对定义与口径

比如“赚钱能力”和“盈利能力”用词不同，向量检索可能把它们联系起来。但“净利润”和“净资产收益率”不是同一个指标，相似不能代替口径判断。

文字检索根据相同词语、名称、别名或编码等找候选，再按匹配规则评分。第 02 步知识召回；第 04 步指标检索。两条路径均已使用

知识有标题、正文、用途权重；指标有名称、别名、编码等匹配。两者采用的具体检索规则不同。

向量检索把问题和资料转成表达含义的数字表示，按相似程度找内容；词不一样也可能相关。召回候选的另一种方法，不是查业务数值。指标目录有可选推荐

重排先得到候选，再重新评估与当前问题的相关性，让更合适的候选排在前面。候选召回之后，进入上下文之前。两条路径未接专门重排模型

RAG找到相关资料，把它提供给模型，让模型据此生成回答。跨越检索、资料装配与回答生成。已有这种工作方式

① 模型怎样处理你的问题

大模型 / LLM：负责理解与生成文字

大语言模型（Large Language Model）根据输入的文字和资料，生成后续文字，也可以输出工具请求。

放到问数里：理解“经营状况如何”想了解什么，选择调查方向，再把工具结果组织成回答。它不会因为名字叫“大模型”，就自动知道你数据库里最新的数据。

第 04 步：选择下一步第 07 步：生成回答

Agent：把模型、工具和执行状态组织起来

可以把 Agent 理解成围绕目标开展工作的程序：调用模型，根据模型提出的请求调用工具，再把结果交回模型继续处理。

例子：模型说“查紫金的不良率”，Agent 将请求交给查询工具。工具负责实际执行；Agent 不是另一张指标表，也不一定代表另一个大模型。

第 01 步：Agent 接收问题第 06 步：工具循环

提示词 / Prompt：告诉模型这次怎样处理

提示词是给模型看的任务说明、规则或要求，例如“先给业务结论，并说明数据日期”。用户问题也是模型输入的一部分。

不要混淆：写一句“只能查询有权限的机构”，不能代替后端权限检查；写一句“回答准确”，也不能补齐缺失的业务数据。

第 03 步：处理规则与资料包

上下文 / Context：模型这一次能看到的资料

包括当前问题、提供给模型的历史、相关知识、工具说明及工具结果。它是本次输入范围，不是模型天然拥有的永久记忆。

例子：先问紫金，再问“江南呢”，程序需要带入相关历史，模型才有依据判断哪些条件应延续。数据库保存了历史，不等于每次都全部发给模型。

第 03 步：上下文内容第 08 步：继续追问

Token：模型读写文字使用的计量单位

模型会按自身的编码规则把文字转成 Token 序列。一个 Token 不固定等于一个汉字、一个单词或一个字节。不同模型的切法可能不同。

放到问数里：问题、知识、历史和工具结果都会占用输入空间，回答也有输出长度。上下文窗口有上限，因此不能把全部一万多个指标无差别塞进去。

Token 多通常意味着处理内容更多，但响应慢还受模型、服务等待、输出长度和调用次数影响，不能只按字数判断。

意图与填槽：想做什么，以及需要哪些条件

意图是用户要做的事，例如查当前值、比较两家银行或分析变化；填槽是把指标、机构、日期等查询条件组织成明确字段。

例子：“紫金和江南谁的利润高”需要比较两家机构，并对齐利润口径和统计期。理解意图后仍需要明确执行条件；缺日期是否追问，要看可用上下文和已确认的默认规则。

第 04 步：确定查询条件

② 后台怎样找相关资料

分词 / 切片：把文字变成可匹配的单位

词典分词可能把“经营状况”识别成词；当前知识检索的两字切片会得到“经营”“营状”“状况”，其中有些并不是完整词语。

区别：这是知识检索的文字处理；Token 是模型自身读写输入的编码单位，两者不是同一套规则。切片也不会让发给模型的原问题变成碎片。

第 02 步：实际切法

召回：先找出可能相关的候选

从很多资料中找出可能有用的一批，就叫召回。可以根据文字、关联编码、语义向量等寻找。

例子：问经营状况，召回“经营质量”知识；再发现不良率等候选指标。召回成功只代表找到了候选，仍需判断是否适用，并非已经答对。

知识召回指标召回

Embedding / 向量：用数字表示文字的含义特征

Embedding 把文字转换成一串数字，这串数字叫向量。它帮助计算机比较内容是否相近。

例子：“赚钱能力”和“盈利能力”可能在向量空间里比较接近。通常用相同或兼容模型编码问题与资料；不同模型的向量不能随意混着比较。

记住：向量数字不是利润数值，相似度也不是答案正确率。

看 Embedding 图解

向量检索 / 向量库：利用相似性找资料

向量检索是比较问题向量和资料向量，寻找相近内容；向量库或向量索引用于存储、索引并加速这类搜索。

可以用专门的数据库，也可以利用已有数据库或内存索引等实现。做 RAG 不代表必须新增一套向量数据库。

当前代码：指标目录有可选向量推荐，知识检索没有接入；是否开启、效果如何，需要分别核实。

第 04 步：向量推荐的边界

Top K / 阈值：取多少条，以及什么条件才保留

Top K是按排名取前 K 个候选，例如取前 3 条；阈值是保留候选的条件，例如某种分数达到设定值。

Top K 是数量限制，不是“这 K 条都正确”；阈值也不是质量保证。不同检索方式的分数不能简单互相比大小。

当前知识检索：最多 3 条，还受到文字命中、指标关联和正文总长度限制，可能不足 3 条。指标向量推荐不能套用知识检索的数量规则。

第 02 步：实际筛选规则

重排 / Rerank：在候选里再判断谁更相关

已经召回一批候选后，再结合问题重新评估相关性，把更合适的放前面。可以采用规则，也可以使用专门的重排模型。

边界：候选里根本没有的资料，单靠重排补不回来。重排也不等于核验业务数值。

当前代码：已有评分、排序与筛选；知识和指标目录这两条路径均没有调用专门的 reranker 模型。

RAG：找资料、给模型、让模型据此回答

RAG 全称 Retrieval-Augmented Generation，中文是“检索增强生成”。它是一种组织回答的方法，不是单独某个模型的名字。

例子：先找经营分析知识，再把知识和问题一起交给模型，让它有业务资料可参考。只检索但不把结果用于回答，还没有形成这段完整配合。

不要混淆：RAG 可以用文字检索，不要求一定有 Embedding；把知识加入上下文，也不等于重新训练模型。

③ 怎样真正查到、用好数据

工具调用 / Tool Calling：模型提请求，程序执行

工具是程序开放给模型使用的能力。模型按照工具说明提供名称和参数，程序检查参数、权限并执行，再返回结果。

例子：metric_search 找指标目录，metric_query 查询业务数值。工具名不同，承担的任务不同；模型不会绕过程序直接登录数据库。

第 04 步：工具请求第 05 步：实际执行

SQL / Text-to-SQL：用什么方式表达数据库查询

SQL是操作关系型数据库的语言；问数通常使用其中读取数据的查询能力。Text-to-SQL指把自然语言问题转换为 SQL 查询。

问数也可以先把问题转成明确条件，再由程序构造 SQL。当前这条指标工具路径就是把正式指标、机构、日期等交给后端查询适配器，不等于让模型任意写 SQL 并执行。

第 05 步：查询落在哪里

指标口径 / 元数据：说明这个数到底代表什么

元数据是描述数据的资料，比如名称、编码、单位、更新时间和来源；口径说明业务含义、计算方式、统计范围和期间。

例子：净利润与利润总额、期末余额与日均余额不能因名字相近就混用。还要知道金额单位、百分比表示方式、单月值还是累计值。

这些说明帮助选指标和解释结果；实际数值仍要查询。业务知识可以解释“怎样分析”，但不能取代正式口径。

第 04 步：看目录与口径

事实与来源引用：这句话依据哪次真实结果

事实是查询或有依据的计算结果；来源引用把回答中的内容关联到这些结果，方便核对指标、机构、日期、单位和计算过程。

例子：说紫金利润下降，需要能对上相应期间的利润数据或计算结果。引用存在，不代表“因为客户流失”这个原因也得到证明。

第 06 步：结果进入上下文第 07 步：核对依据

多轮追问 / 会话状态：继承哪些条件、改变哪些条件

会话状态记录前面讨论的目标、机构、指标、期间和可用结果。新问题到来时，需要判断哪些继续有效，哪些已被用户改掉。

例子：“江南的呢”可能是切换机构；“和江南比呢”需要保留紫金、加入江南并对齐条件；“紫金的贷款质量呢”则可能切换业务主题。

保存历史文字只是基础，不能简单把上一轮全部条件机械沿用。

第 08 步：追问从哪里继续

指标关系 / 知识图谱：把对象之间的关系记录下来

知识图谱用“对象 + 关系”组织信息，例如知识关联指标、指标依赖其他指标计算、机构隶属关系。业务知识分类只是分组，和记录对象关系不是一回事。

例子：“经营质量”关联不良率，只说明这个指标可能有分析价值；不代表它能解释所有经营问题，更不直接证明因果。

记录组成关系后，要做贡献或归因计算，仍需对齐期间与口径，取得实际数据，核对总分关系和计算结果。

④ 为什么仍可能答错或变慢

幻觉：说得像事实，却没有可靠依据

模型可能生成看似合理但错误、虚构或无法由现有资料支持的内容，这类现象常被称为“幻觉”。

例子：只查到利润下降，却直接断定是某类客户流失导致。检索资料、真实查数和来源核对能降低风险，但 RAG 不保证每句话都正确。

第 07 步：核验能保护什么

流式 / SSE：让你逐步看到已经产生的内容

流式表示结果逐步发送；SSE是服务端向页面持续推送事件的一种方式。事件可以是进展、正文增量或最终结果。

页面显示“正在查询”，不等于展示模型完整的内部思考。流式能缩短看到首批内容的等待，但不必然缩短模型或数据库的总执行时间。

第 08 步：结果如何到页面

缓存：条件合适时，复用已经取得的结果

把某次取得或计算的内容暂时保存，下次条件一致时直接复用，减少重复工作。可以缓存目录、向量或一次请求里的检索结果。

边界：权限、资料版本、查询条件或数据更新时间变化后，旧结果可能不再适用。缓存不是把旧答案永久返回；也不能跨用户错误复用受限数据。

第 06 步：本轮检索复用

耗时 / 超时 / 重试：要分清慢在哪一段

一次问数可能包含多次模型请求、检索、数据库查询、计算和回答核验。总耗时来自实际执行路径，部分步骤可以并行，不能只凭界面的步骤数量相加。

超时表示在规定时间内没有完成，不直接说明是网络、模型还是数据库问题；需要根据日志看停在哪段。重试会重新发请求，适合部分临时失败，也可能让总等待更久。

“没有查到数据”“请求失败”和“等待超时”是不同结果，不能统一当成缺数。

RAG 与微调：提供参考资料，不等于训练模型

RAG通常在请求时提供相关资料，不改变模型参数；微调则通过训练样本进一步调整模型参数，帮助它学习某类任务或行为。

放到项目里：后台维护知识，检索后给模型参考，不代表已经微调。改提示词、维护知识、配置指标关联，也是不同于训练的工作。

实时业务数值仍需要查询，不能指望训练一次就知道后续每天的新数据。

召回率 / 精确率 / 问数准确性：不是同一个指标

召回率关心“应该找到的相关资料找到了多少”；精确率关心“找到的资料里有多少相关”。计算它们需要明确样本和相关性标注。

问数最终还要看：指标、机构、日期和口径是否选对，数值和计算是否正确，回答是否完整且有依据。检索分数高、召回多、答案长，都不能代替这些检查。

比较两个版本，应尽量保持问题、数据、权限和模型配置一致，并一起记录答案质量与耗时。

读懂全流程，记住这四句话：

Embedding 是表示文字的方法；向量检索是使用这种表示找资料的方法。

召回得到候选，口径判断决定是否适用，数据库查询才给出实际业务数值。

RAG 让模型参考检索资料，Agent 则组织模型和工具继续完成任务。

有知识、有关联、有引用，都不等于已经证明结论；最终仍要核对业务事实。

沿着这个问题，再串一次

知识：告诉模型怎么看

“经营质量”等资料提供分析方向，关联的不良率、拨备覆盖率提供候选。命中一条资料不代表已经覆盖全部经营状况。

目录与数据：查什么、是多少

先核对正式指标和口径，再按紫金银行、实际统计期查询数值。目录里的定义与数据库里的事实是两种内容。

Agent 与模型：组织并回答

Agent 把知识、目录、工具结果交给模型；模型选择补查或组织结论，程序执行查询与必要核验。

模型能看到全部一万多个指标吗？

这条流程按需检索和提供候选，不是把整个指标库每次都发给模型。当前知识检索最多返回 3 条；新代码的关联候选最多先提供 30 项，目录检索另有分页。后台读取多少目录和模型最终收到多少内容，是不同问题。

知识关联了两个指标，是否每次都必须查两个？

关联给出优先候选。模型仍要结合当前问题、指标定义和口径选择；不适用时继续检索。用户只问定义时，可能不需要查数。当前源码正在接通这种交付，实际效果还需要验收。

为什么不直接让模型给个结论？

模型可以组织语言，但它不知道你数据库里当前的业务值。要回答具体银行、具体期间的经营情况，就需要查真实数据，并保留相应依据。
