# 自主分析问答实录（ReAct 形态）

| 项    | 内容                                                      |
| ---- | ------------------------------------------------------- |
| 文档目的 | 用一个可逐字复核的完整回合，说明"自主规划"在系统里具体长什么样、每一步依据是什么、与固定流水线的差别在哪   |
| 编写日期 | 2026-10-14                                              |
| 对应方案 | 一套全时可见工具 + 逐步工具选择（ReAct）+ 带决策依据的回执 + 事实清单               |
| 证据边界 | 指标编码、正式名称、单位、口径、机构编码、数据日期为**真实目录事实**；数值为**合成为例**，不来自运行库 |

---

## 0. 阅读方式

- 第 3 节是本文档主体：一个回合的逐步实录。每步分四段——模型决策依据、调用、回执、**为什么不是别的选择**。
- "为什么不是别的选择"是判断自主性的关键。如果每步的备选都可以任意替换而不影响结果，说明那不是规划，是流水线。
- 第 6 节给出与固定流水线的正面对照，第 8 节给出缺数改道变体。

## 1. 证据边界（先声明，避免误读）

**真实的部分**（来自 2026-10-14 只读核查，见 `docs/verification/autonomy-20261013/data-preflight-summary.md`）：

- 指标编码、正式名称、单位、统计口径：来自当前启用目录
- 机构编码与名称：来自核查列出的数据存在性样本
- 数据覆盖日期：`2026-01-31` 至 `2026-07-31`，共 7 个月末，61 个机构
- 目录 `单位` 为 `元` 的指标，展示换算由回执给出，模型不自行换算

**合成的部分**：

- 文中的全部业务数值。标注为"合成"处即为示意，**不来自运行库，也不得当作验收结论**
- `2026-09` 无数据的判断是真实的（数据止于 `2026-07-31`），但具体某机构某日的返回值是合成的

**一个需要注意的真实口径事实**：`docs/verification/autonomy-20261013/implementation-and-validation.md` 记录，单位为 `%` 的"较年初增幅"指标，其原始存储值为 `0.005484`，当时明确**没有**将其解释为比率或扩大 100 倍。因此本文档中所有 `%` 单位指标一律**给原始存储值**，不乘 100，不由模型重算。

## 2. 场景设定

- 当前日历日期：`2026-10-14`（Asia/Shanghai）
- 用户提问（原文，不改写）：
  > 苏州农商行上个月存款情况怎么样？
- 本轮可用工具（全时可见，顺序由模型决定）：
  | 工具                        | 何时用（这段描述就是意图识别）             |
  | ------------------------- | --------------------------- |
  | `resolve_business_turn`   | 用户给的是业务说法，要变成正式编码或确认口径      |
  | `catalog`                 | 不确定看什么指标；查某基础指标有哪些口径、某主题含什么 |
  | `data_availability`       | 要知道哪些指标 × 机构 × 日期确有数据       |
  | `metric_query_structured` | 编码与日期已定，取数值、排名、位次           |
  | `metric_calculate`        | 需要两个数之间的关系（差、率、占比、合计）       |
  | `read`                    | 取回本会话历史结果                   |
  | `business_skill_read`     | 需要业务判断方法                    |
  | `conversation_reply`      | 与业务数据无关的普通回答                |
- 服务端保留的硬闸门（不由模型决定）：正式编码、权限裁剪、SQL 构建、口径换算、受控计算、事实编号。

## 3. 逐步实录

### 第 1 步：确认真实机构可查

**模型决策依据**：问题里有明确的机构说法"苏州农商行"。整条链路后续所有取数都挂在这个机构上，先把它落实，避免后面白跑。

**调用**

```json
{"tool": "resolve_business_turn", "arguments": {"organizations": "苏州农商行", "sourceText": "苏州农商行"}}
```

**回执**（节选，编码与名称为真实值）

```json
{
  "status": "READY",
  "resolved": {
    "organizations": {
      "codes": ["070667800"],
      "names": ["江苏苏州农村商业银行股份有限公司"],
      "basis": "lexical",
      "alternativeCandidates": 0
    }
  }
}
```

**为什么不是别的选择**

- 不先调 `catalog`：机构不确定的话，主题探索的结果无法确定挂在哪家机构上。
- 不要求用户补全"苏州农商行"的正式全称：名称到正式编码的映射是服务端职责，用户用简称是正常的。
- 备选数 0，不需要澄清——这正是"错误可恢复的决策不值得用一层专职组件去保证"的体现。

### 第 3 步：确认真实数据落在哪一天（本回合的关键转折）

**模型决策依据**：用户说"上个月"。当前是 `2026-10-14`，按字面"上个月"应是 `2026-09`。但这一条还没有任何数据依据，先核实。

**调用**

```json
{"tool": "data_availability",
 "arguments": {
   "dimension": "dates",
   "match": "all",
   "org_codes": ["070667800"],
   "metric_codes": ["ORG_VRS_DEPT_BAL", "ORG_PSON_DEPT_BAL", "ORG_PSON_TMDST_BAL", "ORG_PSON_DEDMDPT_BAL"]
 }}
```

**回执**（日期为真实覆盖情况）

```json
{
  "status": "succeeded",
  "request": {"start": "2026-01-01", "end": "2026-10-14", "org_codes": ["070667800"]},
  "common_dates": ["2026-01-31", "2026-02-28", "2026-03-31", "2026-04-30",
                   "2026-05-31", "2026-06-30", "2026-07-31"],
  "coverage": {
    "requested_months": ["2026-09"],
    "no_data_months": ["2026-09"],
    "latest_common_date": "2026-07-31"
  }
}
```

**模型在这一步的决策（自主性的实质）**

`2026-09` 无数据，最近共同可用时点是 `2026-07-31`。此时有三种可能行为：

| 可能行为                     | 是否采纳   | 理由                                              |
| ------------------------ | ------ | ----------------------------------------------- |
| 停止并反问"没有 9 月数据，请确认要看哪个月" | 否      | 已有唯一合理的最近可用时点，反问属于把工程问题推给用户                     |
| 静默改用 7 月，不说明             | 否      | 用户问的是 9 月，答的是 7 月，口径位移必须披露                      |
| **按 7 月继续，并在正文写明口径差异**   | **采纳** | 用户要的是"存款情况"，最近可用口径能满足目标；同时把"问的是 9 月、答的是 7 月"讲清楚 |

这与 `business-analysis` skill 中"当期无数据时说明最近可用时点，不用更早期间充当当期"的规则一致，也与该 skill"已能回答用户目标时收尾，不为求全继续扩大范围"的取向一致。

**为什么不是别的选择**

- **不提前假设 9 月有数据**：这是本方案相对 10-13 失败方案最实际的改动——那次的失败之一就是模型在没有覆盖事实的情况下生成计划。
- **不在此处放弃**：缺数不是失败，是改道依据。回执里的 `coverage.no_data_months` 就是给这个判断用的。

### 第 5 步：看到数据后决定下钻（本回合自主性的核心）

**模型决策依据**：回执显示个人存款 `1389.00 亿元`，在各项存款 `2150.60 亿元` 中占相当大比重；个人定期 `1042.00 亿元`，占个人存款的约四分之三；个人存款较年初增幅 `0.0949`。

**这一步没有任何前置规则告诉它"要看个人定期"。** 它是读到第 4 步的实际数据后决定的：总量结构里个人存款这块最大，个人存款里定期这块最大，所以变化主要来源大概率在个人定期。

**调用**（下钻个人定期的时间序列）

```json
{"tool": "metric_query_structured",
 "arguments": {
   "metric_codes": ["ORG_PSON_TMDST_BAL", "ORG_PSON_TMDST_BAL_CMPRLATMO"],
   "org_codes": ["070667800"],
   "start": "2026-06-30", "end": "2026-07-31",
   "selection": "exact",
   "operation": {"kind": "value"}
 }}
```

**回执**（数值为合成）

```json
{
  "status": "succeeded",
  "facts": [
    {"fact_id": "fact:synth-0147:1:value", "code": "ORG_PSON_TMDST_BAL_CMPRLATMO",
     "metric": "个人定期存款余额较上月", "unit": "元", "date": "2026-07-31",
     "value": 12400000000, "value_synthetic": true}
  ]

```

**为什么这一步是分水岭**

| 设问          | 编译器方案（画像预定） | 本方案（ReAct）          |
| ----------- | ----------- | ------------------- |
| 谁决定下钻个人定期   | 画像里写好的第 N 步 | **模型在第 4 步读到占比后决定** |
| 换一家对公主导的机构  | 仍然下钻个人定期    | 会改去下钻对公             |
| 序列是否随数据形态变化 | 不变          | 变                   |

**判据**：同一问题、换一家机构，工具序列应当不同。若永远走出同一串序列，说明还是流水线，只是换了名字。这条是本设计的核心验收依据。

### 第 6 步：需要关系量的地方走正式计算

**模型决策依据**：回答"存款情况"要说清结构（个人存款占比、个人定期在个人存款中的占比）。占比是**两个数之间的关系**，不在正文里自行推算。

**调用**

```json
{"tool": "metric_calculate",
 "arguments": {
   "expressions": [{"name": "pson_share", "label": "个人存款占各项存款比",
                    "expression": "b/a", "display": "decimal"}],
   "bindings": {"a": {"fact_id": "fact:synth-0142:1:value"},
                "b": {"fact_id": "fact:synth-0142:3:value"}},
   "scope_policy": "same_org_date"
 }}
```

**回执**

```json
{
  "status": "succeeded",
  "calculation_id": "calc:synth-0142:1",
  "results": [{"name": "pson_share", "value": 0.6459, "value_synthetic": true}],
  "inputs": ["fact:synth-0142:1:value", "fact:synth-0142:3:value"]
}
```


**为什么不是别的选择**

- **占比走 `metric_calculate` 而非模型心算**：心算即便正确也不合规。10-13 审计实测到过一次——候选在追问回答里写了"较上次增加 20 亿元"，算术与合成事实一致，但**没有 `calculate` 回执**，该项被明确列为治理契约未验收。
- **`scope_policy` 用 `same_org_date`**：两个事实同机构同日，与既有 `capabilities.ts` 的枚举一致。

---

### 第 7 步：收尾判断

**模型决策依据**：用户问的是"情况怎么样"——已能回答"规模多少、在怎么变、变化主要来自哪里"。**比较总体不是用户提的目标**。

**决策**

- 不做横向排名：用户没提"跟同业比"。若要主动给出，需先确定合法比较总体，而比较总体必须有用户表达、可信历史或已登记规则的依据，不能自行扩大。
- 不继续扩大范围：`business-analysis` skill 的规则是"已能回答用户目标时收尾，不为求全继续扩大范围"。

**为什么不是别的选择**

- **不主动跑一遍 ranking**：省一步，也避免在没有合法总体依据的情况下扩大范围。
- **不省略口径披露**：问的是 9 月、答的是 7 月，这个位移必须写进正文。

---

### 第 8 步：事实清单核对后成文

**宿主侧确定性核对**（不消耗模型往返，不是独立反思轮次）

本轮授权数字清单：

| 来源   | 内容                                                      |
| ---- | ------------------------------------------------------- |
| 查询回执 | `fact:synth-0142:1:value` = 215060000000 元（各项存款余额当日数）   |
| 查询回执 | `fact:synth-0142:2:value` = 183.0 亿元（各项存款余额较上月）         |
| 查询回执 | `fact:synth-0142:3:value` = 138900000000 元（个人存款余额当日数）   |
| 查询回执 | `fact:synth-0142:4:value` = 0.0949（个人存款余额较年初增幅，单位 %）    |
| 查询回执 | `fact:synth-0142:5:value` = 104200000000 元（个人定期存款余额当日数） |
| 查询回执 | `fact:synth-0142:6:value` = 34700000000 元（个人活期存款余额当日数）  |
| 查询回执 | `fact:synth-0147:1:value` = 12400000000 元（个人定期存款余额较上月）  |
| 计算结果 | `calc:synth-0142:1` = 0.6459（个人存款占各项存款比）                |

核对规则：正文中出现的每个数值，必须能指到上表某一行。清单外的数值直接拦下并触发修正。**定性表述不受此限**，但需能在数据上指回某个事实。

**正文（示意）**

## 6. 变体一：缺数改道（真实缺口）

**真实事实**（已按 `data-preflight.json` 逐码核对）：240 个有值编码中，**225 个覆盖全部 7 个月末**（`2026-01-31` 至 `2026-07-31`），**15 个只覆盖 2 个月末**（仅 `2026-03-31` 与 `2026-04-30`）。

这 15 个编码**全部属于"个人活期存款余额"这一族**的派生口径：

```

ORG_PSON_DEDMDPT_BAL_CMPRLATMO             个人活期存款余额较上月
ORG_PSON_DEDMDPT_BAL_CMPRLATMO_INCRRNG     个人活期存款余额较上月增幅
ORG_PSON_DEDMDPT_BAL_CMPRPVSQRT            个人活期存款余额较上季
ORG_PSON_DEDMDPT_BAL_CMPRPVSQRT_INCRRNG    个人活期存款余额较上季增幅
ORG_PSON_DEDMDPT_BAL_CMP_SAMEPRD           个人活期存款余额较同期
ORG_PSON_DEDMDPT_BAL_CMP_SAMEPRD_INCRRNG   个人活期存款余额较同期增幅
ORG_PSON_DEDMDPT_BAL_CMP_SAMEPRD_TERMEND   个人活期存款余额较同期期末

ORG_PSON_DEDMDPT_BAL_EXPNCATG_MEANVL       个人活期存款余额拓展类均值
ORG_PSON_DEDMDPT_BAL_GRWT_CLASS_MEANVL     个人活期存款余额成长类均值
ORG_PSON_DEDMDPT_BAL_WHLPROV_MEANVL        个人活期存款余额维护类均值
```

注意：**"个人活期存款余额当日数"（`ORG_PSON_DEDMDPT_BAL`）本身是覆盖 7 个月的**。缺口只在它的比较口径与分类均值上。这意味着一个很自然的追问会直接踩中缺口。

**变体问法**："苏州农商行 7 月个人活期存款比上月怎么样？"

模型会先取 `ORG_PSON_DEDMDPT_BAL`（当日数，有值），再取 `ORG_PSON_DEDMDPT_BAL_CMPRLATMO`（较上月）——后者在 `2026-07-31` **无数据**。回执：

```json
{"coverage": {"requested_dates": ["2026-06-30", "2026-07-31"],
              "no_data_dates": ["2026-06-30", "2026-07-31"]},
 "facts": [{"code": "ORG_PSON_DEDMDPT_BAL", "date": "2026-07-31", "value": 34700000000}]}
```

即：当日数拿到了，较上月口径整段缺失（该口径仅有 `2026-03-31`、`2026-04-30` 两点）。

**期望行为**（三种，均为正当，取决于目标）：

1. 换用同期可用的等价口径（如目录中另有"较年初"口径已覆盖），并在正文说明替换关系
2. 退回该指标最近有数时点，写明时点差异
3. 明确说明该项在目标时点无数据，不静默用更早期间冒充

**禁止行为**：把空值当零、用更早期间结果冒充当期、改用不相关的其它指标充数。

## 7. 变体二：口径歧义

**问法**："苏州农商行存款余额多少？"

用户只给了基础指标。目录中同一基础指标下有"当日数""较年初""较上月""较上月增幅"等多个口径。此时应走系统已有的候选确认机制（`FIELD_CONFIRMATION_DESCRIPTION` 契约），**不默认当日数**——`metric-query` skill 明确"用户只说基础指标时，由系统候选请用户选择统计口径，不默认当日数或某种增幅"。

## 11. 未验证项（如实声明）

1. **本文档是设计实录，不是运行结果。** 工具序列、回执字段、`related`/`coverage` 均为设计目标，当前代码尚未实现，未跑过真实模型。
2. **数值全部为合成**，机构与日期的覆盖事实来自 2026-10-14 只读核查。
3. **上限 24、澄清锁定是否为真实瓶颈，尚无运行时可证的多步轨迹**，只有代码结构证据。应先离线构造 6–8 步轨迹验证，再决定改动幅度。
4. **Flash 类模型的逐步工具选择是否稳定，需实测。** 10-13 的失败中，流超时与错误回执过于泛化占了相当比重，不全是规划能力问题；因此 P0 的纠错回执与错误码计数应排在真实模型验证之前。
5. **真实的构成关系尚未确认**：指标树的上下级排列不证明下级可加总为上级；"含协定/不含协定"共用 22 个编码的问题未解决。因此本文档第 5、6 步的"结构占比"只用**同基础指标下已确认的并列口径**（定期/活期），未做跨层级贡献分解。
