# Ask Metric 两个月功能实施计划

> 产品经理视角的菜单功能、八周排期、数仓数据需求、验收场景和官方平台参考已整理为 [Excel 工作簿](/Users/deng/Documents/02_开发/04_AI/zbws/outputs/01a1775d-43b1-7ad2-99d8-a082bd08cc68/Ask-Metric菜单功能清单与两个月计划.xlsx)。本文件保留功能与技术工作的补充说明；菜单是稳定操作入口，客户流水归因等属于问数场景，不单设菜单。

> 实施人员：获得具体实施授权后，使用 superpowers:subagent-driven-development 或 superpowers:executing-plans 按工作包推进。本文只安排范围、排期和验收，不授权自动提交、推送或部署；执行状态统一回写既有融合待办。

**目标：** 两名开发在业务和数据同事配合下，完成首批业务范围的可靠问数、现有管理功能补齐、一组有依据的贡献分析及最小反馈复测流程，形成可交接的试点版本。

**架构：** 保留Vue页面、TypeScript/Pi会话与工具循环、Python/FastAPI权限和查询计算服务。理解与调查由模型和工具协作完成，程序保持对象、来源、权限、单位和计算边界；不新增Agent框架、通用审核系统或配置中心。

**技术栈：** Vue / TypeScript / ECharts；Node.js / Pi；Python / FastAPI / SQLAlchemy / SQLGlot / Decimal；现有数据库适配及部署脚本。

**范围依据：** [功能清单与两个月范围](../../Ask-Metric功能清单-两个月交付范围-2026-10-27.md)、[现有能力评估](../specs/2026-10-27-intelligent-metric-maturity-assessment.md)、[数据准备清单](../../问数数据准备清单-2026-10-27.md)。基线为`develop-ws@0d86941`及第1周核准的后续改动。

## 1. 人力、周期与承诺边界

- 用户已确认：**两名开发，业务/数据同事配合**。建议开发A主要负责Agent/查询计算，开发B主要负责管理后台/前端；交叉复核，不形成只能由一个人维护的模块。
- 两个月按**8个实施周**安排，起始日尚未指定。具体日期在开工时映射；额外日历时间留给发布窗口、假期及外部确认，不预先塞入新功能。
- 按每人每周5个工作日，名义容量为`2×8×5＝80人日`。排定工作为64人日，**包含开发、自测、代码整理、联调、复核和交付文档**；另留16人日用于数据延迟、缺陷和外部服务异常。
- 每周A、B各安排4人日，另各留1人日缓冲。若实际休假、兼职或行内发布窗口减少容量，按真实可用人日重排，不能依靠加班把范围写满。
- 建议业务/数据每周共同参加一次演示和口径确认，问题记录到对应功能编号；未确认事项列责任人和日期。该协作频率为排期建议。
- “必做”是计划目标，不是无条件工期保证。第1周核验工作量，若预计超过64人日或数据不成立，先删除选做项，再缩减主题/分析深度或调整日期；不能降低权限、事实正确性和验收标准。

## 2. 全局约束

- 保留现有架构与已批准的真实数据范围，默认参考MFWS已提交的`jjccb-release`；不混用其他分支实现。
- 实际验收使用真实业务数据、真实模型和实际调用链；技术单元测试与业务验收分开记录。
- 原文明确条件与已确认上下文优先；账号机构和最新有效日只用于允许的缺省情况。
- 先定位首次偏离；删除或合并无依据、重复和误伤的校验，保留权限、归属、来源、单位和计算保护。
- 不用原句白名单、机构特例或越来越多的否定词规则修语义问题；不把知识或旧案例当作当前事实。
- 不新增完整知识图谱、任意SQL/代码执行平台、微服务拆分或多Agent编排；本期只补有明确场景的工具能力。
- 正文流式保持关闭；保留已有真实进展、取消与重连。界面仅验证桌面，不自行重新设计整个平台。
- 不自动提交、推送或修改他人未提交工作。每批实施前核对另一窗口已完成范围与文件归属。

## 6. 验收样例和检查重点

第1周建议建立**不少于24组核准业务场景，其中至少8组包含连续追问**；这是本期工作量建议，不是已经收集的数量。保留一部分不同表达和跨主题问题到第7周再测试，不能只反复调通原句。

| 场景类别 | 必查内容 | 负责周 / 功能 |
| --- | --- | --- |
| 明确查值与缺省条件 | 正式指标、账号机构、真实有效日；明确日期和机构绝不被默认值覆盖 | 第2—3周 / F02、F13—F17 |
| 替换机构与追加比较 | “江南的呢”与“再和江南比较”产生不同目标集合，并正确对齐指标与期间 | 第3周 / F03 |
| 换主题、纠正和旧历史回指 | 利润转贷款质量不带错指标；明确纠正覆盖旧条件；较早回指能找到授权记录 | 第3周 / F03、F08 |
| 比较、趋势、排名 | 基期真实、频率一致；缺期不补零；Top N不是全量贡献；不能把多种基期拼成趋势 | 第3、5周 / F04、F21 |
| 长调查与交付边界 | 调查不会超出可交付范围仍不断取数；证据缺失可有界补查，正文格式问题局部恢复 | 第2、6周 / F05、F07 |
| 组成关系与贡献 | 互斥/完整/同期间，核对总分与残差；净变化为零时比率未定义；贡献超过100%按定义解释 | 第4—5周 / F20—F21 |
| 正常数字与错误结论 | 名称/日期/列表中的数字正常展示；假来源、错单位/数值、无依据因果不能当成结果 | 第2、6周 / F06、F07 |
| 实时与历史恢复 | 刷新、重连、重读、停止状态一致；历史重看不重复提问和计费；必要权限重新核验 | 第5周 / F08、F27 |
| 管理变化生效 | 目录停用不被同步无说明地覆盖；数据集启停影响执行；清楚区分后端与Agent配置 | 第2—4周 / F12、F16、F25—F26 |
| 知识、反馈与权限 | 不适用知识不当本行事实；反馈归属可核对；无权者不能借历史/反馈/导出读数据 | 第4、6—8周 / F18—F19、F23、F27 |

比较MFWS时固定已提交的`jjccb-release`、模型/思考设置、允许数据范围和可比统计期；不同版本取得不同数据时先解释差异，不能只凭回答长短评分。评估正确性、问题覆盖、依据、自然程度与耗时，确认改进来自哪一段能力。

发布门槛：关键支持场景逐项由业务核准；对象/期间/数值/单位/来源及权限不存在已知阻塞错误；新增功能可操作、数据缺口有边界、关键追问能重复通过。测试通过数量、模型生成成功率和用户点赞不能代替这些标准。支持范围外问题单列，不用大量“无法回答”抬高正确率。

性能：第1周记录模型等待、工具/SQL、交付处理及用户端总耗时，第3周确认试点并发与响应目标，第7周在同模型配额和真实数据下测P50/P95及失败率。没有完成目标环境测量，不承诺具体秒数或并发能力；模型服务等待不能只靠调大超时处理。

| 第8周结束 | 核准场景、权限、恢复、交付材料满足已约定门槛 | 不宣布整体完成；形成可交付范围和阻塞清单，再决定后续日期 |

## 8. 两个月明确不同时铺开的内容

F29—F36属于后续路线图：多数据源自助接入、任意客户/流水分析、完整模板报告中心、分享订阅/预警、复杂知识导入和检索平台、完整岗位审批/审计中心、全行ETL/血缘及大规模高可用。

若领导明确把模板报告或客户明细列为两个月的硬交付，必须提供真实样本和数据，并替换等量的本期工作或增加资源/周期，不能直接叠加。功能全景保留，首期范围以本计划和功能清单为准。
