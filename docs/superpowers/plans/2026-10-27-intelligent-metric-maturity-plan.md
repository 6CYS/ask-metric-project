# Ask Metric 智能问数平台建设计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans when implementation is authorized. 按独立工作包实施；本次只交付评估与计划，没有开始业务代码修改。

**Goal:** 在业务确认的数据范围内，建设可持续使用和维护的行内智能问数平台：不仅能正确回答，还能管理数据与指标、维护知识与配置、沉淀分析结果、处理反馈、验证版本效果并可靠运行。

**Architecture:** 保留 Vue 前端、Pi 原生会话、FastAPI 正式目录/权限/SQL/计算服务。模型负责理解、选证据与组织表达，程序负责身份、对象、来源、单位、计算与执行边界；收敛既有校验，不另建通用审核或图谱平台。

**Tech Stack:** Vue 3 / TypeScript / ECharts；Node.js / Pi；Python / FastAPI / SQLAlchemy / SQLGlot / Decimal；现有 GoldenDB/MySQL/Inceptor 接入与离线部署脚本。

**Spec:** [成熟度评估与范围](../specs/2026-10-27-intelligent-metric-maturity-assessment.md)。执行前阅读本文件、评估及最新项目 AGENTS.md。

基线：`develop-ws@0d86941`，2026-10-27。本计划是按本次用户要求形成的候选工作包，不自动取代原[融合待办](../../Ask-Metric融合待办清单-2026-10-26.md)；采纳后由该台账记录实施状态。下列任务均未因写入文档而完成。

本计划的具体输入分成两份：[平台菜单与操作清单](../../平台功能清单-菜单与操作-2026-10-27.md)明确现有及建议按钮，[问数数据准备清单](../../问数数据准备清单-2026-10-27.md)明确资料准备、业务范围和数据验收。两线并行，在同一个业务场景上共同验收，不能只验页面或只验数据交付。

本轮修订补齐平台建设范围。原 W0–W6 保留为问数链路专项，不能再把它们当作完整平台计划。以下 T0–T9 是平台工作包编号，并非优先级，也不是十个新系统或十个新菜单。

## 平台工作包与阶段

### 建设边界

建议首期面向单个银行内多机构、多个批准业务主题；先把当前指标数据完成一条可维护、可验收的完整流程，再以第二个真实数据集验证扩展。该边界是规划建议，需在实施启动时与业务负责人确认。

平台职责覆盖：业务人员问数/复用结果，数据负责人维护资产和口径，专家维护知识和分析方法，运营人员处理反馈与复测，管理员/运维管理授权、配置、运行和发布。岗位可兼任，职责和处理责任不能缺席。

| 工作包 | 要交付的能力 | 复用与实施边界 | 可检查的完成条件 |
| --- | --- | --- | --- |
| T0 范围与现状基线 | 首批业务主题、数据范围、用户角色、实际产出、上游系统清单、真实问数基线 | 复用 W0；不默认业务想要任意数据库问答或大型 BI | 每个关键场景有负责人、数据来源、授权范围和验收方法；外部依赖标明已确认/未知 |
| T1 数据源与可执行数据集 | 接入资产、连通状态、唯一执行配置、字段/语义映射、启停生效 | 复用已有连接和查询适配器；先接通当前数据集，按需要加第二个，不先做自由 Join/跨库引擎 | 维护配置后实际查询读取一致；停用影响新查询；错误映射失败可见；新增数据集不靠复制整套代码 |
| T2 指标、知识与数据治理 | 来源权威、维护责任、发布状态/快照、退役、正式关系、知识出处与质量状态 | 复用目录同步、CRUD、语义 schema、W3/W5；优先消费行内指标、ETL、质量、血缘 | 已发布口径和源版本可回看；本地停用不被无意覆盖；知识/关系适用且可追溯；缺数与过期状态明确 |
| T3 身份、权限与审计 | 账号生命周期、资源操作矩阵、数据分类、导出政策、管理事件与审计归档 | 复用 SSO、机构授权、历史/导出再鉴权；职责分离和列权限按真实数据需要扩展 | 调岗/停用/撤权在检索、执行、历史、导出一致；管理与导出事件按约定可追查 |
| T4 模型与配置生效治理 | 组件配置来源、生效时点、运行版本、模型配置变更记录与回退 | 复用后端提示词版本发布/回滚、Nacos；Agent 主提示词可继续源码管理 | 管理员能知道改了什么、影响哪条链、何时生效；每次验收绑定代码/模型/提示词/知识/语义版本 |
| T5 问数与分析交付 | 稳定多轮、准确期间、受控计算、关系归因、自然正文和图表 | 复用 W1–W4；先修首次偏离，再补已批准分析；不以词语补丁拼能力 | 一类问题的正确/失败路径均验收；来源容量不会导致查完无法交付；图文表一致 |
| T6 反馈、评测与运营 | 用户纠错入口、处理状态/责任、复测、样例库和版本对照 | 借鉴 MFWS 反馈；复用现有语料/脚本，先轻量记录与生成报告，不先造评测平台 | 一条真实反馈能完成处理和复测；已核准样例比较实际条件、结果和耗时，错误案例不会直接变成知识 |
| T7 会话与分析资产、报告产品 | 服务端会话管理、结果导出/保存分析；按需求接模板报告任务 | 复用聊天和导出；借鉴 MFWS 的报告任务/模板/产物；分享、订阅另设权限和业务门槛 | 用户能找回并复用结果；来源/版本/权限可追溯；如做报告，可生成、取消、失败重试、下载并核对内容 |
| T8 观测、用量与容量 | 聚合错误/耗时/用量，Agent 跨会话准入，有界等待，告警责任 | 接行内日志/APM/网关；复用 usage 与工具审计；不把费用表零值当真实免费 | 约定负载下不无界占用；取消/失败有准确终态；告警可被收到并处置；用量未知与零可区分 |
| T9 部署、恢复与持续交付 | 环境/版本一致、自动拉起、数据保留和备份恢复、发布门禁 | 复用离线包、健康、升级/回退和迁移；确认外部 CI/备份，单写部署边界明确 | 当前版本在目标环境验收；恢复包含会话/配置/数据而不只是程序回退；未验证 HA 不声称具备 |

### 阶段安排

| 阶段 | 本阶段实际要做 | 退出条件 |
| --- | --- | --- |
| 阶段一：明确边界和形成可验收试点 | T0；T5 现有链路问题；T1 现有数据集真实生效与页面承诺核对；T2/T3/T4 确认权威源、权限和配置归属；T6 最小反馈处理；T8/T9 基础容量与恢复准备 | 核心业务能正确完成；数据/账号/配置变更不会不明原因覆盖；问题有人处理；目标环境有基本运行、权限和恢复证据 |
| 阶段二：平台化管理与业务资产 | T1 可执行模型；T2 发布与语义/知识治理；T3 必要岗位分权；T4 配置版本关联；T6 真实样例回归；T7 会话查找、统一结果导出和保存分析 | 日常新增指标/知识、数据变化和用户反馈不再主要依靠改代码、查临时脚本或人工猜状态；变更可以验证并追溯 |
| 阶段三：按场景扩展业务交付 | 第二个批准数据集；已确认的关系归因；如周期报告是核心产出，落地 T7 的一个模板及任务流程；按需增加分享/订阅 | 新场景有真实数据与责任人，完整走权限、查询、交付、反馈和回归；不会为每种问法复制专用流程 |
| 阶段四：按使用规模强化 | T8 的分组用量/预算、负载和告警；T9 的可用性/存储演进；实际需要的文档批量维护、看板和预警 | 达到事先约定的并发、等待与恢复目标，变更和故障可运营；平台扩展有使用数据支持 |

身份和数据授权、必要审计、资源准入及基本备份恢复是推广前门槛，不能等待问数全部修完才开始。阶段四只深化规模化能力，并非把基础保障推迟到最后。周期报告如已确定是首期交付目标，应将一个报告模板和对应任务流程前移，其他功能顺序不因此全部提前。

### 各工作包的最小实施内容

**T0：把产品范围和外部依赖明确下来。**

- [ ] 列出“谁在什么工作里问什么、最后拿什么结果”，保留查询、分析、周期报告的区别；首批场景沿用 W0，补一份真实业务报告样本（如果需要报告）。
- [ ] 列出行内 IAM、指标/元数据、质量、ETL、BI、网关、日志/监控、CI、备份/工单能力与接入方式；未知项不当作已有。
- [ ] 每项能力标明自建、扩展或对接，以及业务/开发/运营负责人；不以菜单数量衡量成熟度，不给没有工作量依据的交付日期。

**T1：先把“数据集可维护”与“数据集可执行”统一。**

涉及 `api/dependencies.py`、`infrastructure/db/session.py`、`infrastructure/query/sql_builder.py`、`api/routes/catalogs.py`、数据集模型和 `DatasetsView.vue`。

- [ ] 复现现有数据集更改/停用与实际查询关系。先确定现有配置权威，去掉页面没有执行依据的承诺；没有接通前不得宣称支持按数据集问数。
- [ ] 复用受治理查询合同，将数据源、事实映射、允许的指标/维度、启用状态绑定到可解析的数据集配置；兼容已有记录与运行引用，迁移和回退要明确。
- [ ] 接入状态使用真实连通与必要元数据检查；凭据保留服务端秘密引用，不回传前端。数据库实际只读权限单独验收，`SELECT 1` 不能代替。
- [ ] 当前模型通过后，用一个真实、已批准的第二数据集验证扩展。如仍只允许指标×机构×日期，要明确声明范围，不假称任意客户/渠道分析。

**T2：维护、同步和发布形成一致规则。**

涉及 `application/catalog_sync.py`、目录模型/API、`metric_semantics.py`、`business_knowledge.py`、配置及现有页面；结合 W3/W5。

- [ ] 明确哪些字段由正式源维护、哪些由本地补充，定义本地停用、源停用/缺席、版本变化的处理；先复现同步 `enabled=True` 覆盖本地停用的路径。
- [ ] 建立最小资产发布记录：来源资产/版本、责任人、口径单位、状态、生效范围、变更理由和可核对快照。上游已有审批则复用批准结果，不复制一套多级工作流。
- [ ] 数据质量状态包含实际统计期、适用更新频率、已知缺口和责任方；尽量引用上游质量/批次/血缘，不在本项目重写全行血缘和 ETL。
- [ ] 正式关系和知识沿 W3/W5 接入发现、执行与出处。来源/版本放在管理及追溯信息，业务回答只展示必要内容；不强迫所有普通知识填大量字段。

**T3：核对现有权限，补实际资源边界。**

涉及 `auth_service.py`、`integration_identity.py`、`ports.py`、`task_service.py`、身份同步脚本、Agent 会话路由与工具审计。

- [ ] 明确上游身份与本地停用优先级；核查同步缺席用户不自动停用、SSO 影子用户可重新启用的设计是否符合行内规则，不直接贴漏洞标签。
- [ ] 对用户/管理员及确需拆分的岗位列资源操作矩阵；对数据集、指标、明细列分类，已有聚合指标同权时不预造复杂策略。
- [ ] 核对检索、取数、历史、导出、未来保存分析/分享的访问一致性。独立导出权限和分享接收者校验按批准政策落实，不依赖隐藏按钮。
- [ ] 明确模型可接收的问题、目录、知识和真实结果范围及部署/传输边界；按数据分类提供最小必要内容和脱敏。对实际知识/文档输入验证指令注入边界，参考资料不能改变授权、任意选源或执行写操作；不另造通用审核系统。
- [ ] 补管理变更、授权、导出、审计访问等必要事件，接入行内审计归档；不把本人查询日志当作全平台审计台。

**T4：让维护者知道配置到底是否生效。**

涉及 `api/routes/model_config.py`、`infrastructure/model/configuration.py`、`agent-service/src/nacosConfig.ts`、`inquiry/runtime.ts`、`harnessHost.ts`、`LlmView.vue`。

- [ ] 列“组件—配置项—来源—生效时点—版本—回退方式”，标明 Agent 启动配置、源码主提示词与后端页面提示词各自作用；先修复误导的管理边界。
- [ ] 复用已存在的提示词版本/发布/回滚。给模型配置变更和整次发布补版本关联，不为一张统一页面再建配置中心。
- [ ] 真实运行和验收记录能够定位生效代码、模型标识、提示词/知识/语义版本；日志不存密钥，资料内容按既有隐私边界保存。
- [ ] 每次更换模型或发布相关配置先运行受影响的回归，生产使用已确认环境；不默认增加多模型智能路由或自动切换。

**T5：沿已有 W1–W4 实施，作为平台的一部分。**

调查容量、上下文、日期、校验、正式关系和图表都保留原专项约束。数据集/指标版本改变时，应追加与该变更直接相关的来源和兼容检查；不把新平台概念塞进自然回答。

**T6：让真实反馈能转成可验证的改进。**

当前未发现业务反馈持久化和管理路由，实施时需补最小数据记录/API，关联已授权的会话消息、反馈原因、处理状态、责任人及版本；复用现有 DB 迁移和管理风格。

- [ ] 先提供“结果不对/没回答问题/表达或图表问题”等轻量反馈与必要说明，提交时校验消息归属；不得复制所有敏感正文到另一份无权限记录。
- [ ] 管理侧能核对原目标、查询条件、来源、版本和处理结果；由责任人确认修复或解释，不把点赞率直接等同准确率。
- [ ] 借鉴 MFWS `chat_server.py` 的反馈处理和转案例。转入知识、示例或评测前审核，错误回答不能自动成为标准答案。
- [ ] 复用已有语料/审计脚本构成版本比较：执行条件、业务事实、权限、缺数披露、自然表达/图表、耗时分别评分；工程隔离测试与真实业务验收分开。
- [ ] 保留一组未被直接当作运行时示例使用的验收问法，避免只对已经优化过的原句打分。先生成文件报告，确有多人维护需求再做评测管理页。

**T7：从聊天结果走向可复用的业务产物。**

涉及现有会话路由、`BackendNextChatPanel.vue`、`ChatResultContent.vue`、结果导出。新增分析资产或报告任务时需使用正式持久化、迁移和归属校验。

- [ ] 首先补服务端会话改名/查找和普通结果的清晰导出入口，复用已有导出鉴权；查找不跨用户泄露。
- [ ] 保存分析记录原问题、机构期间、来源与版本、正文/图表及生成时间，明确它是历史快照；重新运行重新鉴权并生成新结果，不能悄悄替换旧证据。
- [ ] 周期报告有真实需求时，选择一个批准模板，借鉴 MFWS `reporting` 的持久任务、模板快照、租约、取消、失败重试和 Word 交付；数据执行继续走 Ask 的正式接口。
- [ ] 先核对业务有没有现有 BI/报表平台。分享、看板、订阅、阈值预警按实际场景接入，明确接收者权限、统计期和失败通知；不因菜单完整而全做。

**T8：资源消耗、告警和使用效果有管理依据。**

涉及 Agent `modelUsage.ts`、`harnessHost.ts`、`toolAudit.ts`、运行配置，以及后端日志/请求关联；对接行内观测/模型网关。

- [ ] 使用现有记录聚合请求成功/部分完成/失败、模型和查询耗时、活跃操作及 token，用关联号去重；成功执行率、业务准确率、用户满意度分别定义。
- [ ] 当前 Agent 只有同会话串行不足以证明全局容量可控；按实际承载量补跨会话/用户准入与有界等待或明确拒绝，先不引入队列中间件。
- [ ] 取消验收到实际执行边界，特别是断开客户端不保证 Inceptor 服务端查询停止；明确超时/中断仍在运行时的处理责任。
- [ ] 模型价格和 usage 缺失标未知；已有模型费用零值不作为账单。按真实网关账单或费率版本核算后再设置预算告警/超额策略。
- [ ] 将可用性、错误率、耗时、存储/连接资源的必要告警接到现有值守渠道，验证一次发生—通知—处理—恢复；不能只落一个 alert.log 就算告警完成。

**T9：验证数据恢复与当前版本交付。**

沿用 W6 现有打包、检查和回退。补齐应用库、Agent JSONL、模型/提示词历史、知识/语义配置的保留与恢复范围；秘密的恢复交由既有安全托管机制。

- [ ] 明确单写试点能否满足目标，验证锁、异常退出、自动拉起、恢复后历史和在途请求状态；只有高可用要求明确才选择相应存储/路由演进。

### 首批业务场景

| 场景 | 提问/动作示例 | 核对重点 |
| --- | --- | --- |
| 简单查值 | 紫金的存款余额有多少 | 正式指标、明确机构、实际数据日、单位，不强制变经营分析 |
| 默认范围 | 我行存款情况如何 | 默认机构来源明确；最新期按实际覆盖确定；范围日期只交代一次 |
| 业务概念 | 紫金最近贷款质量如何 | 指标选择有依据；没有阈值不凭不良率数值断言“较低/可控” |
| 指标切换 | 存款有多少 → 那贷款呢 | 保留合适机构/期间，切换指标；不复读存款 |
| 比较和原因 | 紫金存款余额 → 同比环比呢，为什么 | 正式比较基期正确；变化与原因分开；缺原因证据不编造 |
| 机构范围变化 | 紫金与民丰对比 → 再看江南/改看江南 | 区分追加和替换，不默认回账号机构 |
| 较早回指 | 四轮后再看前面那家/那个指标 | 能定位授权历史；数值重读，不串用最后一次来源 |
| 指定期缺数 | 七月末/八月末查询 | 目标期缺数与参考期分开；不把8月27日改称月末 |
| 区间与时点 | 今年三季度贷款质量如何 | 一天缺数不等于整季无数；只有期内某日也不能称完整季度表现 |
| 经营多目标 | 存款、贷款和收益怎么样 | 不以存贷款代替整体经营；可回答/未完成方面明确 |
| 图表追问 | 存款情况 → 画结构图；机构对比 → 柱图 | 复用真结果；组成未核实不强行饼图；图文表同单位同统计期 |
| 归因和能力边界 | 哪些机构拖下来 → 哪些客户转出 | 支持的变化/贡献与客户原因分别处理，不能重复旧机构报告当客户答案 |

撤权、报告容量、服务超时、重复请求、断线、取消和知识版本变化通过针对性技术用例配合桌面操作验证，不要求业务人员反复手工制造故障。上述问题可使用实际目录中的同类指标/机构替换，必须保留替换记录，不能用替换掩盖某个机构的真实缺数。

**验收：** 一位未参与改动的人能依据清单复核“问的是什么、查的是什么、回答是否有依据”；结果与当前待测代码配套。W0 不以全部题目通过为前提，真实失败是后续工作依据。
