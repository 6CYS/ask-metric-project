# 意图理解优化实施计划

**目标：** 在现有 Ask Metric 链路内准确区分查数、口径解释、分析与历史续问，减少无必要的条件追问。

**依据：** 用户已确认先融合理解与追问，并选择“账号所属机构＋最新有效数据日”；本轮明确要求先完成意图部分，保持简单和代码质量。

**架构：** 复用现有语义提议协议、目录和会话状态。借鉴 jjccb-release 的目的识别、知识检索及上下文优先规则，不新增 Agent、分类器、业务表或依赖。沿用正在修改的工作区，保留同事配置和既有改动，不提交 Git。

## 实施与验证

- [x] 普通查数：收尾既有默认条件改造，复验“换指标且日期不变→无数据→明确重新查最新→仅换机构”的连续问题。明确历史日期、未知机构、用户拒绝默认值仍受原有约束。
- [x] 口径知识：`catalogs.py` 给确定性命中及近似建议附带已维护的说明、口径；Agent 类型兼容扩展，`catalog.ts`/`metricCatalogSearch.ts` 明示用途和证据边界。路由测试先复现字段缺失，再验证透传、空定义与原排序兼容。
- [x] 目的分流：`semantic-task/prompt.ts` 的两种运行提示词使用共用决策段；只问定义先查目录并解释，不补取数条件；单纯查数不升级分析；混合问题保留两部分义务。同步 `metric-query/SKILL.md`、`turnContract.ts` 的相关工具说明。

## 本轮边界

- 保留真实歧义和权限校验，不为减少追问自动选择统计口径或未知机构。
- 口径解释是独立目的，也允许作为取数中的插问；解释不清除此前工作目标。
- 排序、计算、分析不能因缺项默认而丢失原始业务目标。
- 百分比编码、复杂计算、归因报告和页面重排不并入本轮。
- 验证结论只覆盖实际检查的行为，不以单次模型成功宣称所有表达均正确。
