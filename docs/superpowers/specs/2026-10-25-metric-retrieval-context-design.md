# Ask Metric 指标检索与上下文优化方案

日期：2026-10-25。状态：设计建议，尚未实施。

建议保留 Ask Metric 已有的目录检索、受控查询和业务状态账本，吸收 mfws 对候选资料与详细定义分开处理的思路。先修正资料投影和历史选择中的具体问题，再根据实际对照决定是否增加详情读取步骤。第一批不新增菜单、数据库表、向量库、重排服务或记忆系统，不替换查询与报告链路。

## 1. 范围与证据

- Ask Metric：本地 `develop`，HEAD 为 `7efde3a178dfa47b54c2b8d37c52b13a7f518eb4`，以本次读取的工作区实现为准。工作区另有报告表达、图表和配置改动，本方案不修改或纳入这些内容。
- mfws：只读取 `jjccb-release@846a49b03555a8f647f93d96684363892e8cef06` 的已提交源码，不切换参考仓库分支。下文 mfws 行号属于该提交。
- 证据包括源码、已有测试、已有真实会话的目录回执，以及不连接服务的内存隔离复现。隔离输入只验证程序分支，不代表真实业务数据验收。
- 本次没有新增模型请求、数据库查询或业务代码改动。回执字节数、字符预算估算与模型实际输入 token 分开记录；不据此承诺响应时间改善。

要解决的是：指标多时，模型仍能找到合适的正式指标、读到足够的口径、继承已确认条件，并减少重复材料。候选数量少、上下文短，都不能代替这些要求。

## 2. 两个工程实际怎么做

| 环节 | Ask Metric 当前实现 | mfws jjccb-release 当前实现 | 取舍 |
| --- | --- | --- | --- |
| 指标来源 | 正式启用目录；名称、别名、说明、口径等在后端维护 | 内置指标资产与启用第三方源快照 | 保留 Ask Metric 正式目录，不复制一套指标台账 |
| 指标检索 | 普通目录按 exact、contains、lexical 排序；可选 embedding 只提供近似建议。分析目录另有主题分组与分页 | 全字段精确匹配优先，再用 BM25 补候选；不是向量检索 | 不凭架构名称换算法，先用真实问题判断哪里漏召回或排错 |
| 普通问数识别 | `metric_candidates.py` 另有完整名称、基础指标与口径组合、拼音和纠错识别；模糊召回与正式采用分开 | 模型主要根据指标工具结果理解、选择并组织后续工具调用 | 不能把目录搜索等同于整个意图理解，也不能拆掉现有确定性校验 |
| 搜索返回 | 普通目录主候选默认 10、最多 50，另有近似建议；分析目录每关键词默认 12、最多 30，一次最多 4 个关键词。候选带完整说明/口径 | `search_metrics` 默认只给来源、Key、绑定 ID/名称等摘要；`get_metric` 返回完整资料 | 借鉴按需要给资料，但第一批保留消歧所需的完整定义，不强制多一次读取 |
| 多轮上下文 | 原生 Session、结构化任务/目标/条件、历史引用和权限复核；聊天记录是发送视图的一部分 | Web 每轮提交新消息，checkpoint 保留历史，DataFrame 单独保存；定义复用、条件保留主要依赖提示词和框架 | 保留 Ask Metric 账本，不改成只靠聊天摘要记住业务条件 |
| 知识进入模型 | Skill 目录常驻，正文按需读；已读正文有版本判断和重复投影处理；主题知识按主题读取 | 初始化注入配置知识、案例知识和方法；每轮另召回 BM25 Top 3 业务知识 | 不照搬常驻全文加逐轮资料的组合，不把知识多等同于理解好 |

“全量目录在后端参与搜索”和“全量目录作为 Chat 模型上下文”不同。如果启用 embedding，目录资料还可能发送给该检索模型并缓存向量；这也应与每轮发送给回答模型的内容分开统计。

mfws 有两个不宜照搬的细节：搜索虽然声明 `top_k` 上限，但全字段精确命中分支没有最终切片；详情返回也没有独立总长度预算。另外，先读来源、搜索、读详情和跨轮复用的次序主要是提示词约定，不是强制状态协议。不能把它当成已解决全部上下文问题的模板。

## 3. 已找到的具体问题

### 3.1 相同候选资料被重复发送

普通指标工具同时返回 `items` 和 `exact_matches`，后者是前者中精确命中对象的完整副本。因此同一条说明和口径可能在一次回执里出现两遍。统一 `catalog` 入口继续保留两份，现有发送投影没有删除它们。

分析目录按多个关键词分别返回描述对象，同一指标可能在不同结果组反复展开。已有真实会话的只读统计如下：

| 既有会话记录 | 某次 analysis_catalog 回执正文 | 指标描述出现次数 | 不同指标编码数 |
| --- | ---: | ---: | ---: |
| 存款下降到机构追问的 I 组 | 74,241 字节 | 120 | 80 |
| 个人与对公存款的 P 组 | 38,651 字节 | 48 | 22 |

来源：`.runtime/local/report-consolidation-20261025/collected.json` 指向的原生会话记录；统计去掉了日志重复保存的同一工具调用。它说明存在重复展开，但不同关键词的命中关系仍有意义。同编码也不保证定义或匹配状态相同，不能直接按编码删掉候选。上述数字不是最终网络请求大小、token 或可节省的比例。

### 3.2 精简视图反而丢掉了口径限制

后端 `MetricSemantics.descriptor()` 生成 `limitations` 和 `semantic_status`，包含“缺少正式定义”“百分比编码未审核”“统计频率未审核”等边界。

`catalogBindingView()` 对具有正式绑定的描述对象采用字段白名单，这两个字段不在白名单内，因此没有进入这条分析目录的模型正文。服务端相关校验仍然存在；问题是模型规划时看不到本来已有的明确限制，不能据此声称后端允许越权或错误计算。

### 3.3 历史在精简之前就被预算裁掉

当前大致顺序是：按原正文选历史 → 复核选中历史的权限 → 精简历史成功结果。最近历史最多保留 3 轮、估算预算 4,000，本轮不裁剪。

隔离复现中，同一历史成功回执的预算估算由原始约 19,495 降为投影后约 230；当前顺序已经先把整轮移除了，只剩本轮用户消息。按投影成本选择则可以保留上一轮完整的用户消息、调用和回执。这里的数字是现有字符启发式估算，不是模型实测 token。

业务账本没有因此丢失，但模型会失去原本可以保留的近邻原问和来源线索，可能需要额外回读。不能把它直接归因为所有重复读取或模型超时的唯一原因。

### 3.4 部分目标撤权后，待答问题没有同步过滤

`projectPlan()` 把整计划的开放问题放入 `task.pending_questions`。`permissionFilteredContext()` 过滤目标和历史引用，但原样保留任务中的待答问题。

隔离复现中，同一计划的 A、B 两个目标，B 撤权后只剩 A 目标，B 的待答问题仍在发送视图里。该结果会进入本轮状态，也可通过上下文读取工具返回。另外，`targets[].conditions[field].candidates` 还有一份候选展示；机构未确认、scope 为空时，仅隐藏待答问题仍可能留下这份候选。此处确认的是发送视图的过滤遗漏；本次没有发现或验证生产泄露，执行前的权限校验也仍在。

### 3.5 普通目录检索对可选 embedding 的依赖与分析入口不一致

分析目录会在精确命中时直接返回，并在可选语义推荐服务失败时保留词法结果、说明推荐不可用。普通目录搜索则先请求 embedding，再进行确定性排序，没有在该路由捕获同类可选服务错误。

这使普通目录在启用 embedding 后，可能因为额外服务等待或失败，影响原本可以返回的确定性结果。它是源码确认的条件性风险；本次没有证明现场启用了 embedding，也没有证据将此前 Chat 模型等待响应头的超时归因于此。

## 4. 推荐的最小改动

按以下顺序实施，各步可独立验证和回退。当前文件仅确定方案，不执行这些改动。

### 第一步 先补齐模型应该看到和不该看到的信息

1. 在 `analysis/bindings.ts` 的既有模型字段投影中保留 `limitations`、`semantic_status`。不扩展已批准语义，不把 `catalog_only` 当成已审核知识。
2. 在 `semantic-task/contextMemory.ts` 让任务的待答问题随获准的任务/目标过滤，复用入场快照已有的机构候选权限核对。旧题承接答案继续遵守已有发布证明和版本规则，不把发布证明改成本轮新题交付的前置条件。
3. 机构尚未确认时，不能因目标 scope 为空就跳过候选权限检查。任一候选失权时，本次发送视图同时隐藏该目标及其待答题，消除条件候选副本的旁路，其他有权目标保留。运行状态、`business_context_read` 和入场快照采用相同授权判断；不删除持久化目标、不改原题编号，也不能因隐藏目标把未完成任务改为完成。需重新解析的目标沿现有恢复流程处理。暂时无法复核权限时保持明确失败，不伪装成“无候选”。

生产改动集中在两个现有模块；执行工具、数据模型和查询逻辑保持现有契约。

### 第二步 在模型发送副本中去除完全相同的展开

1. 在 `modelContext.ts` 增加目录回执的轻量投影，由 `harnessHost.ts` 的现有发送链路接入。普通目录完整定义在 `items` 保留一次，完全相同的 `exact_matches` 改成编码索引或省略；差异对象原样保留。
2. 同一条分析回执中，多关键词命中的重复完整定义只展开一次。各关键词的候选列表、匹配类型、得分、分页和是否截断信息保留；后续相同条目用明确的本回执内引用指向首次完整定义。
3. 合并判断比较完整定义内容和绑定版本，不能只比较编码。分析目录可利用当前回执 `details.binding_map` 中短引用对应的原始签名识别版本；普通目录没有版本字段，因此只在同一回执内、完整定义内容一致时去重，不跨回执复用。近似建议不能因为与正式候选同编码就获得正式绑定；不能复用另一个关键词的得分或匹配结论。无法确认相同的对象直接保留。
4. 第一批只做同一回执内部的无损去重，不增加跨轮缓存，不机械截断口径，不减少候选覆盖，不改后端 API 或持久化回执。未知格式、失败回执、冲突内容保守保留。

“本回执内引用”只在这一条模型正文中有效，不存入业务账本、不跨回执解析。建议引用首次条目的结果组和条目位置，避免另造全局 ID。与原来完整输出做同问题对照；如果模型识别引用反而增加往返，仅保留普通精确副本去重，暂缓跨关键词定义折叠。

### 第三步 按发送成本选择历史，再对原始来源验权

调整 `workingMessages()` 的预算输入与 `harnessHost.ts` 的装配顺序：

1. 对历史生成只读的成本视图，包含现有成功结果精简和第二步目录投影。只用于预算，尚不发送模型。
2. 按成本视图选择完整回合，但拿回对应的原始消息，保留所有权限来源和 `details`。
3. 对选中的原始回合执行既有 `safeWorkingHistory()`，再生成最终发送副本。
4. 业务 Skill 的可见正文与重复处理以最终选中、已授权的历史重新计算，不能因预算试算里出现过正文，就在最终消息中只留下失效引用。

继续保留“最近连续最多 3 轮、历史预算 4,000、本轮不裁”的现有规则，不扩大预算或改用模型自由摘要。工具调用与回执保持配对，原始历史不变；权限复核只针对选中的有限历史，不对所有旧会话做无界远程校验。

历史目录第一批仍按完整回合保留，不新建指标记忆仓库。继续通过已有任务账本继承已确认指标、机构和日期；定义变更后仍走当前目录版本与绑定校验，旧回执不是最新定义的保证。

### 第四步 补齐普通目录的可选检索失败路径

在后端 `api/routes/catalogs.py` 先获取确定性结果。正式编码或完整正式名称命中时，直接提供完整的确定性候选，不为附加推荐等待 embedding；短别名命中或多义候选不自动当作唯一指标采用。

需要近似补充时复用现有向量缓存和模型服务。只对已识别的可选模型不可用、无效响应做降级，保留确定性结果，并明确区分推荐未启用、不可用、已完成，以及正式身份命中无需推荐。供应商 HTTP 401/403 也会被包装成 `ModelServiceUnavailable`，必须检查其 `status_code` 后排除，不能照搬宽泛的异常捕获。鉴权失败、请求取消和未知程序错误不能被泛化为正常空结果。

同步补充 `agent-service/src/backendClient.ts` 的 `MetricSearchResponse` 状态类型，并在 `tools/metricCatalogSearch.ts` 显式透传该状态；否则后端返回了状态，工具重建正文时仍会将它丢掉。统一 `catalog` 沿原有转发路径保留它。这是既有响应的兼容扩展，旧后端未返回状态时按“未知”处理，不猜成成功。不新建检索服务，不切换模型。

此步按启用/关闭两种配置做隔离测试；真实效果验收只使用当前实际配置，不为证明收益而临时开启另一服务。

## 5. 暂不采用的方案

| 方案 | 可能的价值 | 当前不优先的原因 |
| --- | --- | --- |
| 全部改为“名称摘要 → 模型选择 → 再读完整定义” | 很长的定义较多时可能减少输入 | 名称不足以消歧，容易先选错；可能增加模型轮次。先完成无损精简并量出仍然很大的部分 |
| 迁移 mfws BM25 或新增向量库、重排服务 | 真实召回不准时可能改善候选 | Ask Metric 已有多种确定性和可选语义检索；目前证据主要指向投影、重复和上下文顺序，不足以支持替换 |
| 增加跨轮指标全文缓存或新记忆 Agent | 可能减少重复资料读取 | 需要处理更新、失权、多目标和引用失效；现有账本、绑定和 Skill 机制应先复用 |
| 新增知识维护菜单并把术语写进系统提示词 | 能提供维护入口 | 菜单不控制每次发送量；全量注入会放大问题。本方案只涉及检索和上下文 |

如果无损精简后仍由长定义占据主要输入，再评估可选的详情读取：保留简短但足够消歧的口径，明确标记省略内容，使用稳定编码和版本取完整定义；“解释口径”问题直接读全文。该能力不作为第一批前置依赖。

| 可选检索服务 | `backend-next/src/ask_metric/api/routes/catalogs.py`、`agent-service/src/backendClient.ts`、`src/tools/metricCatalogSearch.ts`；后端 `verification/test_catalog_knowledge.py` 与 Agent `tests/catalogKnowledge.test.ts` | 正式身份命中不依赖 embedding；降级状态经过直接工具和统一 catalog 都到达模型；旧响应状态未知；不吞 HTTP 401/403、取消或未知错误 |

实现时先补这些行为测试，再跑受影响的现有目录、上下文和查询恢复测试，以及 Agent 类型检查/构建、对应 Python 检查。第一批不改前端，不因此扩展到全站 UI 或报告生成重构。

真实验收使用同一份现有 `ads_lake` 数据、同一账号/权限、同一 Chat 模型配置，在新建测试会话比较修改前后：

| 场景 | 原话或操作 | 通过条件 |
| --- | --- | --- |
| 原三轮回归 | “我们行存款怎么少了？”→“能看出是哪些机构拖下来的吗？”→“能看出哪些客户把钱转走了吗？” | 指标、实际日期、机构范围连贯；客户能力缺口如实说明；不重复交付旧报告 |
| 同名口径 | “看看存款。”→“我说的是日均，别用时点余额。” | 有对应正式指标才采用；别名歧义仍保留澄清能力，不因压缩丢掉限定词 |
| 单纯定义 | 选现有真实指标询问口径，再问与另一真实口径的区别 | 完整定义可读取；缺说明明确说缺，不要求无关机构/日期，不发起取数 |
| 多指标比较 | “个人存款和对公存款最近表现怎么样？余额和比上个月的变化一起看看。” | 不漏指标、不把余额和增量混为一类；原有失败照实记录，不用上下文优化冒充已解决 |
| 只改一个条件 | “还是刚才那个指标，换成上个月。”再换一个已授权机构 | 只改变用户指定条件，保留其余已确认条件和来源 |
| 多关键词与后续页 | 在现有目录选存在重叠候选、且确有多页结果的查询 | 候选覆盖与原结果一致；`has_more` 仍有效；不把第一页当全部 |
| 长结果后继续问 | 在已有真实多机构结果后追问“还是刚才的日期，换个人存款看看。” | 原问、必要条件和引用仍可访问；不得拿裁剪前的原始行当新取数结果 |
| 关闭后重开 | 重开同一真实测试会话继续追问 | 状态从原有持久化恢复；不依赖新建的临时内存缓存 |

定义更新、部分撤权和故障注入先用隔离契约测试验证，不为验收擅自修改共享正式目录或用户权限；有专用测试环境时再做端到端复验。

每个真实案例记录：预期/实际指标与口径、机构日期、候选覆盖、目录及历史读取次数、模型调用次数、最终 payload 字节、provider 返回的 input/cache token、各阶段及总耗时。沿用已有 `modelPayloadDiagnostics.ts`、model usage 和调用耗时记录，不新增监控平台，不记录完整业务数据到诊断日志。

硬性门槛是语义正确、来源与权限不退步、已确认条件不断链；相同内容去重后的目录正文应更小。耗时比较应分开看本地处理、工具和模型等待，不承诺固定百分比。若出现调用次数增加或错误率上升，定位并撤回对应投影步骤，不靠加长提示词抵消。
