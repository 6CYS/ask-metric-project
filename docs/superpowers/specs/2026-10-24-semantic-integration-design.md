# Ask Metric 业务理解融合：目标与阶段计划

日期：2026-10-24

状态：用户已授权实施，首批代码和真实验收正在推进；完成项与未通过项见[验收清单](../../业务理解融合验收清单-2026-10-24.md)。尚未满足第7节全部完成标准。

## 1. 最终目标

保留 Ask Metric 的页面、会话、指标体系和取数能力，吸收 mfws `jjccb-release` 中有效的业务知识利用、指标查证和上下文处理能力，让业务人员用自然语言提问，得到条件正确、依据明确的指标答案，并能自然继续追问。

以实际问数效果为交付标准，不以复制了多少代码、增加了多少提示词或测试数量作为融合完成的依据。

## 2. 本期必须交付什么

| 业务体验 | 完成时应看到的行为 |
| --- | --- |
| 听懂自然说法 | 正式名称、已确认简称和自然业务表达能找到相同含义的指标；涉及不同口径时能区分，不能只看名称接近。 |
| 用得上业务知识 | 有正式资料时，实际检索到相关定义和规则并用于选择指标；资料不足时明确说明缺口。 |
| 少问无必要的问题 | 沿用已确认的“账号所属机构＋该指标最新有效数据日”；已有条件不重复询问，真正影响结果的歧义仍要问。 |
| 连续追问接得住 | 只改本轮要求变化的条件；插问口径、重显结果后仍能继续原查询或原澄清。 |
| 查对并说明白 | 指标、机构、日期、单位和数值符合原问题；答案直接说明结果，避免内部字段和工具术语。 |

这一期覆盖指标问数、指标口径解释及其连续追问。涉及原因的问题应识别分析目的并保留比较对象；归因算法、贡献计算和完整分析报告的正确性另列后续阶段，不将“成功路由到分析”算作归因完成。

## 3. 现状与真正缺口

### 已有基础，不能重复算作本期新增成果

- Ask Metric 已有单 Agent、指标目录、业务 Skill、任务账本、权限校验、工具反馈和有上限的恢复流程。
- 前一轮完成了默认机构与日期、意图提示词、目录说明透传和数值与口径组合交付。这是局部改进，不代表 mfws 业务理解能力已融合。
- 前一轮真实接口有通过记录，但登录后的桌面流程未复验；分析案例曾超时，部分纯口径答案仍较慢、包含技术字段。

### 实施前核实的接入点

- mfws `jjccb-release@846a49b` 的 `agent.py:generate_system_md` 会加载领域知识、错题知识和示例；`chat_server.py` 会按问题召回相关领域知识详情；指标工具提供搜索和完整定义读取。
- 实施前 Ask 普通目录检索有向量近似推荐，恢复路径使用的 `MetricSemantics.search` 没有传入同一套向量分数；两条路径的检索能力不一致。
- 实施前 Ask 向量文本包含名称、别名和 `description`，没有包含已维护的 `explanation`。资料被保存、参与检索、真正进入模型上下文是三件事，需要分别验证。
- mfws 另有模板案例预渲染 SQL 和反问强度分类机制；不直接迁入这两条路径。当前问题不需要第二套 SQL 或每问必经的新分类器。

这些是源码事实，尚不能证明某项修改会提升多少准确率；须用相同问题和真实链路确认。

## 4. 最小实施方案

维持一个 Agent、一套正式会话状态和现有受控查询入口。增强以下实际链路：

用户原问题与可信历史 → 按需检索相关指标和业务知识 → 读取完整口径 → 提交原有语义提案 → 正式绑定与校验 → 查询或必要澄清 → 根据反馈定向修正。

### 知识如何迁移

- 指标专属名称、别名、说明和统计口径优先使用现有指标维护能力，通用方法优先使用现有业务 Skill。
- 先整理 mfws 相关资料与 Ask 实际指标的对应清单，记录来源、适用指标、已有内容及冲突。不能把其他主题、示例或相似名称当成 `ads_lake` 的正式口径。
- 已有正式资料能够证明适用的可以复用；有冲突或来源不足的保留为待确认资料，不覆盖现有值、不写成业务事实。
- 我负责核对代码和资料；确需业务判断时，只向用户或业务负责人提出具体的口径问题，不要求用户选择技术架构。
- 运行时仍按需读取，不整库塞入提示词。案例先作为解释规则来源和验证材料；是否需要运行时案例检索，由实际失败证据决定，不作为首期必建平台。

### 检索与修正如何衔接

- 普通检索和恢复检索复用已有召回能力，相关说明参与发现，完整口径参与判断。
- 语义近似只产生候选。核对完整定义和正式身份后，沿用现有引用、目录版本与权限校验执行，不能把相似度当成用户确认。
- 复用现有恢复预算和冻结条件；只修正未确定的解释，不能为了成功查询改掉用户已确认的机构、日期或操作。
- 简单、已明确的问题直接走原查询；知识读取和修正按需发生，不要求每轮增加模型分类或检索。

## 5. 阶段计划与交付物

| 阶段 | 实际工作 | 交付物与结束条件 |
| --- | --- | --- |
| M0：固定范围和基线 | 复用已完成的探索与真实记录，整理首批业务问题；核对所需正式知识和源数据；记录实际代码、模型及目录状态。 | 一份问题及预期行为清单、一份知识适用清单。每个缺口有代码或资料依据，结束后进入实现，不反复做同一轮探索。 |
| M1：做通一条真实业务链 | 接通相关知识、指标召回和正式绑定，完成“自然问法→查数→解释口径→修改条件”的全过程。 | 实际代码与适用知识改动、回归测试、真实调用证据；至少一条依赖已核实业务含义的链路通过，不能只有精确名称查询成功。 |
| M2：覆盖首批常见问法 | 扩展到同义说法、真实歧义、纠正条件、混合请求和多轮续问；只修复这些问题暴露的缺口。 | 首批验收矩阵的结果、原始失败及修复记录；必要追问准确，无依据的默认和条件漂移为零。 |
| M3：桌面验收与交付 | 在真实模型、3309/ads_lake 和实际登录页面完成关键流程；对照源值，检查历史恢复及响应耗时。 | 版本与变更清单、验收报告、已知限制和回退说明；用户可以直接在页面试用。未验证或失败项明确保留。 |

M0 → M1 → M2 → M3 顺序执行。M1 必须产生真实可用的代码与业务链路；M2、M3 不重新开启无关优化。暂不承诺未经基线支持的工期或响应秒数，每阶段报告实际结果与下一步。

## 6. 首批验收范围

建议固定 **12 个单轮用例＋4 组多轮用例，每组至少 3 轮**，至少 24 轮。数量用于控制首批范围，不代表统计意义上的准确率；正式名称和预期值在 M0 按现有目录确定。

单轮覆盖：完整条件查值、缺机构日期、已确认别名、需业务定义才能识别的自然问法、相近但不同口径、纯口径解释、查值加解释、明确历史日期无数据、未知指标或机构、明确排序、明确计算目的、资料不足时说明缺口。

多轮覆盖：

1. 查数 → 只换指标且日期不变 → 明确改查最新。
2. 查数 → 插问口径 → 只换机构。
3. 产生真实歧义 → 插问候选口径 → 回答原澄清继续原任务。
4. 查数 → 更正条件 → 重开历史会话继续修改条件并取数。

已知明确定义缺失的问题必须保留。它们用于验收“诚实说明缺口”；不能以这种通过代替“读取真实知识并解决业务表达”的成功。

## 7. 完成标准

- 固定清单的预期行为全部符合；至少包含一条有正式知识依据的自然问法链路。资料欠缺项应单独标识，不能偷偷删掉难例或补造资料。
- 每次执行的指标、机构、日期策略、实际日期、单位和值均可对照正式目录和源数据；无越权、无静默放宽条件、无编造口径。
- 预先标为“无需追问”的用例不产生业务上多余的追问；标为“必须澄清”的用例不擅自选择。
- 三类核心新行为——知识驱动的指标识别、澄清恢复、插问后继续查询——各完整复验一次；首次失败如实保留，修复后再复验，不能选择性呈现成功记录。
- 验证未直接放进提示词的同义表达，避免只对原句或样例有效。测试桩只用于隔离回归，不能冒充业务验收。
- 同条件比较改前改后的正确性、无必要追问、重复工具调用、总耗时和超时；简单查询不增加固定的前置模型调用。有性能退化须说明原因并处理，不能只报告成功率。
- 相关测试、类型检查和构建通过；登录后的桌面流程实际通过。接口通过不等于页面验收完成。
- “完成”仅覆盖这份首期范围，不宣称所有自然语言、复杂计算及归因均达到 mfws 的效果。

## 8. 工程约束和责任

- 保留当前前端体验、权限边界和受控 SQL；不新建第二套 Agent、会话、知识库平台或任意 SQL/Python 执行路径，不新增运行依赖。
- 参考 mfws 已提交 `jjccb-release`，不切换或覆盖其工作区。迁移资产注明出处及适用范围。
- 保留 Ask 当前用户和同事的改动，不把已有改动全部计入本任务。默认不提交、不推送、不发布。
- 实际验收使用用户指定的真实模型与 `3309 / ads_lake`；不改写业务源数据，不使用演示账号或演示数据替代。
- 优先复用既有目录和 Skill 的维护、加载和版本处理；不复制多份正式口径。知识更新后核对实际生效版本，不能只验证文件保存成功。
- 用户负责业务目标和必要的口径确认；我负责代码判断、方案拆分、实施、测试与证据整理。
