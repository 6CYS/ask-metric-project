## 1. 本轮目的与结论边界

本轮围绕真实数据验证 Ask Metric 的问题理解、连续追问、计算和业务归因，为后续借鉴 `jjccb-release` 提供具体依据。用户进一步指出：“没有涉及到机构和日期，就容易反问客户，不是很友好。”这项体验反馈已纳入重点分析。

原定基线为 **15 轮问答、5 个新会话**，全部实际通过页面提交并取得结束记录；其中有连续追问和澄清回复，不是 15 个相互独立的业务场景。针对用户的新反馈另完成 2 轮定向补测，合计 **17 轮、7 个会话**，见第 4 节。

当前最需要处理的事项：

1. **统一缺项处理策略。** 基础查值缺机构或日期就追问，经营分析却允许账号机构和最新可用数据日；用户体验随内部入口改变。应先区分用户目标、继承上下文、应用经过确认的默认策略，再判断是否必须追问。
2. **修正百分比尺度契约。** 本例增幅小数比例被直接添加 `%`，结果与同指标余额、变化额的数学关系相差约 100 倍。
3. **提高计算提案与反馈修正的稳定性。** 一道余额比例题和一道两机构贡献题都有可核实的源数据，但均被提案或校验问题阻断。
4. **补齐并提供正式指标口径。** 目录能找到名称、单位和别名，不代表能回答“单笔还是客户合计”；本例资料缺失时没有编造定义，但消耗了 7 次模型调用。
5. **让分析文字与证据一致。** 补测的分析答案把“余额增加、比率也上升”写成“方向相反”。数值绑定成功并不代表业务结论正确。

普通问数的日期、机构、指标继承，以及否定原候选后改选机构，本轮均有成功证据。不能将上述问题概括成“Ask Metric 没有语义理解”，也不能据这些样例认定 `jjccb-release` 的整体效果更好。

本轮仅执行验证、源码定位和文档整理，**没有修改产品代码、提示词、知识目录或运行配置**。没有实施融合、提交或推送。

## 5. 已定位的问题与改造建议

### 5.1 缺项追问：应调整上层业务策略

**事实：** 普通新查询的 Prompt 明确禁止从账号机构或今天猜条件；宿主要求机构、指标和日期全部解析，缺失就生成 `FIELD_REQUIRED`。Q07 的追问是现有策略执行结果，并非模型临时决定要反问。

续问已有可信来源时，系统能继承条件，A、B、C 都有实证。经营分析另有默认账号机构、最新实际数据日的策略。口径解释则可以没有机构和日期，Q15 已验证。因此，“没有机构日期就必须问”不是所有任务都适用的约束，也不是确定性 SQL 构建方式必然造成的交互。

建议统一为以下决策顺序，**属于建议，尚未实施或批准具体默认政策**：

1. **先判断用户要什么。** 定义解释、方法咨询、查看旧结果不应套用新取数的必填检查。
2. **本轮明确条件优先。** 用户明确改动、清除或否定时，不能用默认值覆盖。
3. **明确续问继承已确认条件。** 有多个合理历史来源时再问，不能任取最近一条。
4. **无上下文的新查值使用经过业务确认的默认策略。** 可讨论采用用户选择的工作机构或已确认的账号默认机构；未指定日期的时点指标，可讨论先查最新可用数据。回答自然说明所用机构和实际截至日，允许下一轮改动。
5. **剩下的实质歧义才追问。** 只问会改变答案的条件，并用目录及覆盖信息提供易理解的选择；避免要求用户重述整题或填写内部字段。

必须保留的边界：

- 登录归属、可访问机构集合、用户本次想查的范围是三件事；管理员拥有全行权限不等于每次都想看全省汇总。用户本次反馈不等于同意自动全省或今天。
- “最新数据”不是系统今天；明确历史日期不能自动换成最新。余额、发生额、期间累计值的默认时间规则也不能相同。
- 已有覆盖接口能在明确指标、机构后返回最新有记录日期，但有记录不一定有有效数值。默认规则需要检查目标值能否实际使用，不能只取最大日期就宣称有数。
- 多指标、多机构的最新日期可能不同。比较时需要共同可比日期，或明确披露各自截至日，不静默混成同一时点。
- 不应把所有简单查询改成复杂分析来绕过必填检查；应在共同的条件解析层表达默认值来源与选择依据，保留权限校验和实际执行证据。

### 5.2 百分比：取到原值不等于展示语义正确

源增幅 `-0.04819246446223732` 与下面的数学比例一致：

```text
变化额 /（当日余额 − 变化额）
= -14918224926.553833 /（294636911815.6948 + 14918224926.553833）
≈ -0.0481924644622373254
```

这里的分母是用于一致性核对的反推值，不是已查到的上期历史事实。该比例对应约 `-4.8192464462%`，而正文是 `-0.048%`。

SQL 仅将原值转换为 `DECIMAL(38,10)`；基础回答 `_format_value` 假定 `%` 的原值已经是百分数，直接加 `%`。分析链已有 `ratio / percent / 未确认` 三种处理，基础链未沿用。因此建议建立并传递统一的数值编码契约，未知时明确披露。**不能把全部 `%` 指标统一乘以 100。**

定位：[取值转换](/Users/deng/Documents/02_开发/04_AI/zbws/ask-metric-v0.2-analysis-enhanced-windows/backend-next/src/ask_metric/infrastructure/query/sql_builder.py:682)、[基础回答](/Users/deng/Documents/02_开发/04_AI/zbws/ask-metric-v0.2-analysis-enhanced-windows/backend-next/src/ask_metric/application/result_answering.py:444)、[分析已有尺度处理](/Users/deng/Documents/02_开发/04_AI/zbws/ask-metric-v0.2-analysis-enhanced-windows/backend-next/src/ask_metric/application/analysis_execution.py:99)。已用本次源值直接调用现有格式化函数复现，不依赖模型再次生成。

### 5.3 计算与贡献：来源存在，提案却没有稳定到达执行

**Q10 的路径：** 两份真实历史结果引用正确；第一次公式未将步骤名称加引号，产生公式语法错误；第二次加了反引号，却保留 `* 100`。当前协议要求业务常量出现在用户原句，百分比应使用支持的 `percent(算式)`。随后无进展检测只按错误码等字段判断，未区分这两类不同的 `CALCULATION_NOT_DETERMINED` 诊断，提前终止。

**Q13 的路径：** 首次只交查询，遗漏计算目标；随后依次出现错误的 calculation 字段位置、把查询来源直接转计算、把说明和赋值塞进表达式、同一 target 同时填写 query 与 operations 等问题。最后两次完全重复不合法结构，才触发无进展结束。这里的重复终止有依据，不能与 Q10 的过早合并错误混为一谈。`query.objective` 已提供合法的来源命名位置，不能说系统完全无法表达该计算。

建议：明确比例与贡献计算的合法提案示例、减少模型需要组合的协议分支；对不同计算错误给结构化子类型和定向修复提示。真正重复无进展仍应停止。贡献方法可借鉴 jjccb 的完整范围、分项合计与总量核对，但继续使用正式结果绑定和受控计算，不开放手工重抄业务数值来绕过校验。

### 5.6 分析表达：准确引用数字仍可能得出矛盾结论

Q16 正文将“不良余额与不良率在较年初口径下方向相反”解释成“余额增加、比率也上升”。这是直接矛盾：这两个方向相同；正文给出的较同期则是余额增加、比率下降，才是方向相反。该问题已进入最终页面，不能因为报告工具返回成功就视为业务分析通过。

现有报告工具会绑定数字引用，并检查一部分方向与因果表述。本次第一次报告提案因直接写入业务数字被拒绝，模型改用证据引用后成功；然而错误的方向文字仍然保留。源码针对“不良余额和不良率均上升/下降”等句式已有校验，但没有覆盖本例“方向相反”的矛盾表达。

此外，正文用对公占比大、同比及较年初增幅高，推断其为增长的“核心力量”；现有核验事实却明确提示增幅差“不代表增量贡献”，组成闭合结果为空且个人贷款未绑定。该表述超出了本轮已核验的部分分项比较。“稳步扩张”“持续扩张”也不能仅由三个不同基期的正增长证明，仍缺连续时间证据。

建议让比较期间、指标方向和结论关联到结构化事实，再生成业务文字，并回放此例验证。不能只增加更多近义词正则就认定语义校验完整。应区分时点比较、连续趋势、部分分项比较和完整贡献，避免将有限证据扩大为更强结论。

定位：[现有方向检查](/Users/deng/Documents/02_开发/04_AI/zbws/ask-metric-v0.2-analysis-enhanced-windows/agent-service/src/tools/businessReport.ts:300)。
