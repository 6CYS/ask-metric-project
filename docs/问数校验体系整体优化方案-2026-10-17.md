# 问数校验体系整体梳理与优化方案

## 1. 背景与目标

2026-10-17 会话 `01a14a5e-…` 第三轮"去掉江阴查询，查询 6 月末的数据"失败：24 次工具调用全部被拒、45.7s 后以"工具调用限额"结束，无任何结果。排查结论不是某一处规则写错，而是**校验体系整体形态的问题**：同一句用户原话被 5 个层次各自重新解释一遍，任一层口径不同即死锁；模型只能换写法反复重试，最终靠预算兜底。

本文档做两件事：

1. 梳理现有校验的分层、规则量与结构性缺陷；
2. 给出目标模型、规则分层、退出机制、收敛路径与验收矩阵。

目标不是"再补一条规则"，而是让**同一业务意图的不同说法得到同一结果**，并且**失败时能说清原因、不靠燃烧工具预算结束**。

## 2. 现状：校验分层与规则量

| 层 | 位置 | 主要职责 | 典型码 |
| --- | --- | --- | --- |
| A 字段解析 | `agent-service/src/semantic-task/service.ts`（`resolveField` 约 L840–L1100）、`backend-next/.../field_resolution.py` | 单个字段值能否对上目录、能否在本轮原文/继承中找到依据 | `ENTITY_SOURCE_NOT_ESTABLISHED`、`ENTITY_NOT_DETERMINED`、`MODEL_FIELD_NOT_ALIGNED` |
| B 帧/任务构建 | `service.ts`（coverage/transition 约 L430–L520）、`transition.ts` | 条件是否齐、变更是否可解释、集合是否闭合 | `GOAL_OBLIGATION_UNCOVERED`、`SUBJECT_NOT_IN_TARGET`、`TRANSITION_ADMISSION_REQUIRED` |
| C 计划与准入 | `planService.ts`、`backend-next/.../business_context.py#admit_semantic_plan` | 步骤、引用、权限、来源对账 | `PLAN_NOT_ADMITTED`、`REFERENCE_INVALID`、`TRANSITION_SOURCE_UNGROUNDED` |
| D 跨轮状态迁移 | `backend-next/.../semantic_transition.py#validate_transition` | before/after 与操作账本一致、权限、口径 | `BASE_MISMATCH`、`SCOPE_DENIED`、`ACTION_INVALID` |
| E 目标义务对账 | `semantic_transition.py#verify_transition_fragment` | 原句实体是否都进入执行目标 | `PLAN_TARGETS_INCOMPLETE`、`PLAN_TARGET_BINDING_CONFLICT` |
| F 运行时/协议 | `harnessHost.ts`、`questions.ts`、`feedback.ts`、`replyGuard.ts` | 工具预算、重复、澄清、回答、证据 | `SEMANTIC_NO_PROGRESS`、`TOOL_LIMIT_ANSWER` |

分散在各层的校验码：agent 侧约 **110** 个、后端约 **66** 个（去重后仍远超可维护范围），其中绝大多数靠 `remediation: "pi"` 回给模型自我修正。

## 3. 结构性缺陷

### D1 同一句话被多次重新解释，且判据不同

"去掉江阴"在三个层次被解释成三件事：

- A 层：`value` 的每个成员必须在本轮原文有依据；
- D 层：操作账本要能解释 before→after；
- E 层：原文提及的机构必须落在 `after.org_codes` 或被某个变更"移除"。

三者分别基于**原文子串**、**版本差分**、**提及集合**，互不共享语义。江阴上一轮已排除，于是在 E 层既绑不上、也移不掉；模型改去重述集合，又在 A 层被判"无本轮依据"。这不是规则写错，是**没有单一事实源**。

### D2 "重述"与"继承"被当成两种来源，且互斥

系统一边要求"未变化字段省略即继承"，一边在别处要求"完整重提机构集合"。一旦模型不得不重述，重述值就被判成"没有根据的新值"。现有的等值继承只在一个很窄的分支里生效（`service.ts` L1036–L1039，要求后端返回空 `source_codes` 数组），实际运行中不成立。

### D3 错误码描述"哪里不对"，不描述"能不能修、该怎么修"

- 所有问题挤在 `remediation` 一个维度（`pi` / `user` / `stop`），`pi` 同时承担"格式可自动归一"和"业务上根本无解"两类情况；
- 同一问题在不同码里文案互相矛盾（"省略本字段" vs "完整重提原称谓集合"）；
- 部分包装码（如 `TRANSITION_ADMISSION_REQUIRED`）会把真实原因盖掉，模型只能盲试。

### D4 无进展判定是语法级的

`toolRecovery.ts#repeatedToolFailure` 以"参数哈希 + 失败文本"做指纹。本次失败中模型每次都换一个 `target_ref`，参数永远不同 → 判定为"仍在进展"，于是一路重试到 24 次上限。真正的不变量应该是"**阻塞原因集合**没有变化"，而不是"参数没变"。

### D5 缺少"确认/幂等"语义

"去掉江阴"在状态已经排除江阴时是**幂等确认**，业务上应当直接应答"江阴本就未包含"。现在的模型只会把它当新义务，于是产生了一个无法满足的约束。

## 4. 目标模型

### 4.1 核心原则

1. **状态即事实**：只有一份已签发状态（admitted frame）。每轮提交的是**增量**，不是对全部条件的再证明。
2. **增量才校验**：只有本轮声明变更的字段才需要来源与合法性证明；未变化字段自动继承，不参与任何"重新证明"。
3. **义务最小化**：本轮义务 = 增量涉及的字段 + 原文中"首次出现且与当前状态不一致"的实体。与当前状态一致的提及（如再次"去掉江阴"）视为确认，不产生义务。
4. **证据三选一（OR，不是 AND）**：值合法当且仅当 ① 本轮原文可解释；② 与已签发状态该字段值相等（继承）；③ 来自签发引用。任一成立即可。
5. **处置先于码**：每个问题必须声明处置类别，宿主按处置决策，而不是按码逐个枚举。

### 4.2 规则分层

| 层 | 含义 | 处置 | 是否消耗重试 |
| --- | --- | --- | --- |
| L1 硬不变量 | 权限、只读、口径冲突、越权范围、数据冲突 | 立即结束，返回固定用户话术 | 否 |
| L2 可规范化 | 动作写法、字段省略、等值重述、引用格式、顺序差异 | 宿主自动归一后继续 | 不计入无进展 |
| L3 需用户输入 | 真歧义、缺字段、需要确认对应关系 | 生成一次文字追问 | 否 |
| L4 需模型修正 | 确实可据回执自行修正的提案错误 | 回模型，且必须带**可执行**修正指令 | 是，计入原因指纹 |

硬性约束：**任何检查在实现时必须显式声明属于 L1–L4**；默认不允许是 L4（新增检查默认 L1/L3）。

### 4.3 无进展终止

- 指纹 = `(阻塞原因码集合, 字段, 状态版本)`，与参数、`target_ref` 无关；
- 同一指纹连续出现 2 次 → 判定无进展，转 L1/L3 话术结束本轮，并在回执中保留实际拒绝原因；
- 与 24 次工具预算解耦：预算是最后兜底，不再是主要退出方式。

### 4.4 对外语义收敛

对外（用户可见、前端可见）只保留 8 类：

`权限` / `范围` / `口径` / `来源不确定` / `格式` / `歧义待确认` / `能力不支持` / `系统或数据异常`

细分码继续保留，但只进日志与审计；每条细分码必须在规则登记表中登记"所属大类 + 处置 + 用户话术"。

## 5. 分阶段实施

### P0 语义统一（本次故障的直接修复）

| 改动 | 位置 | 说明 |
| --- | --- | --- |
| 等值即继承 | `service.ts` `resolveField` 组织/指标分支 | `set` 的值与已签发状态该字段完全相等时，一律按继承处理，不再要求本轮原文依据；不依赖后端是否返回空 `source_codes` |
| 已满足提及不构成义务 | `semantic_transition.py#verify_transition_fragment` | 原句机构若已在 `transition.before` 之外（已排除），视为已满足；同时要求 `changes` 记录 `subject`，让"本轮声明的排除意图"可作为解释依据 |
| 幂等排除 | `service.ts` L1055–L1069 | `exclude` 一个不在集合中的成员：若该成员在本轮原文出现且当前状态确实不含它，按 no-op 成功返回，不再抛 `SUBJECT_NOT_IN_TARGET` |
| 回执纠正 | 上述三处的文案 | 删除"完整重提原称谓集合"这类不可执行的指引，改为"已是该状态，仅需变更 X" |

### P1 退出机制

| 改动 | 位置 |
| --- | --- |
| issue 增加 `disposition` 字段（L1–L4） | `semantic-task/store.ts`、`feedback.ts`、两侧所有抛出点 |

### P2 收敛与防回潮

| 改动 | 位置 |
| --- | --- |
| 对外 8 类映射表 | 新增 `semantic-task/disposition.ts` |

发布注意：P0 改动了跨服务契约（transition `subject`、义务判定），**agent 与后端必须配套发布**；旧 agent + 新后端时后端需对缺失 `subject` 走旧路径，保留一个版本的兼容。

## 6. 验收矩阵

同一意图的多种说法，必须在同一会话状态下得到**同一结果**；反向用例必须**一次追问结束**而不是循环。

| 编号 | 说法 | 期望 |
| --- | --- | --- |
| M1 | "去掉江阴查询" → "6 月末呢" | 直接返回 2026-06-30 两家结果 |
| M2 | "去掉江阴查询" → "把江阴去掉，看 6 月末" | 同上；江阴已排除，按幂等确认 |
| M3 | "去掉江阴查询" → "只看无锡和启东 6 月末" | 同上；重述集合按继承 |
| M4 | "去掉江阴查询" → "江阴除外，日期改 6 月 30 日" | 同上 |
| M5 | 同上状态 → "去掉江阴，再查 6 月末"（连续两次同义） | 第二次为幂等，不新增义务、不报错 |
| M6 | 3 家 → "去掉江阴" → "去掉苏州"（苏州本不在集合） | 一次追问"苏州本不在本次范围，是否仅…"，不循环 |
| M7 | 3 家 → "去掉江阴" → "查 6 月末" → "7 月末" | 日期连续切换，机构集合稳定 |
| M8 | 任意轮次重复同一无解请求 3 次 | 第 2 次起终止并给出明确原因，工具调用 ≤ 5 |

另需回归：现有 A1–A8（见《问数澄清与多轮续接修复方案》）不得回退；同一轮内工具调用分布应保持"正常意图 1–3 次"的量级。

## 7. 风险与边界

- **放宽来源校验不等于放宽权限与口径**：L1 类（权限、只读、口径冲突、越权）不参与本次放宽。
- **等值继承只对"与已签发状态完全相等"生效**，部分重叠仍需按本轮原文解释，避免把"改了其中一家"误判成继承。
- 语义收敛会改变回执文案与码表，需要同步 `docs/external-api.md` 中与错误码相关的说明；前端当前只依赖少数码（`AUTH_REQUIRED`、`PERMISSION_DENIED`），受影响可控。
