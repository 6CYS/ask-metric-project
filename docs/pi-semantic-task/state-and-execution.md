# Pi 语义任务状态与执行设计

版本 2 的状态职责、执行约束与当前实现边界。当前运行入口、通用多轮上下文和兼容限制见[实现说明](implementation-multiturn-context.md)；文中的概念模型不表示新增了同名数据库表或独立状态机，也不替代实际验收。

Pi 继续管理唯一的 Agent 会话、消息、模型调用和工具循环。语义任务、目标、步骤及证据保存为同一原生 Session 中的领域值，宿主负责校验与事务更新。现有 Frame 保留为已确认步骤的编译快照，不能单独代表用户的完整任务。

## 公开输入与内部状态的边界

业务入口的必填根字段为 `protocol_version: 2`、`intent`、`targets`；可选 `context_action: resume/defer/abandon` 明确处理已保存的目标澄清，缺省不恢复原修改。`intent` 使用 `prepare`、`query`、`analyze`、`availability`、`calculate` 或 `reuse`；初始输入和修改均使用目标内的 `operations`，动作统一为 `set`、`add`、`replace`、`exclude`、`clear`、`confirm`，业务值使用字符串。`add` 明确追加能力支持的集合成员并保留原成员；不能把追加或来源选择藏在 `set` 的业务字符串中。

每个目标独立选择来源：`{kind: "new"}` 从空条件新建，`{kind: "current"}` 继续唯一入场目标，或 `{kind: "reference", task_ref, target_ref}` 引用宿主签发的任务及目标引用。`new` 不自动继承旧机构、日期或指标。没有全局 `base`、`null` 来源或自然语言历史定位参数。多目标修改由同一 Pi 根据上下文选择一个或多个具体引用；宿主校验引用的 Session、目标归属、版本与最新状态。

`current` 只有在宿主上下文能够明确定位唯一目标时才成立。当前任务含多个可能目标且没有唯一目标焦点时，返回需要明确引用的诊断，让 Pi 读取上下文并选择 `reference`；不能默认第一项、最后一项或整批目标。`task_ref` 与 `target_ref` 是同一 Session 中保存映射的不透明定位引用，不是授权令牌，不沿用旧许可，也不保证当前权限或执行状态仍然有效。

`prepare` 和 `reuse` 可以提交空 `operations`。`prepare` 保留或读取已知条件与未决项，不因条件恰好完整而发出取数；`reuse` 只读取已经定位、仍适用且通过当前权限复核的正式证据，不与条件变更合并成一次操作。新目标空提案不能凭结构合法获得执行许可；已有目标的空变更是否可以继续查询或分析，仍由本轮意图、完整性和执行许可判定。

上述输入是语义提议，不直接授权执行。同一 Pi 解释业务歧义并提出目标和变化，宿主只做规范化、来源绑定、契约校验及执行编译。宿主不能用固定词表猜出用户没有选择的口径，模型也不负责填写内部完整 DSL、状态版本、权限信息或执行许可。

## 入场快照与目标澄清

`NativeSemanticTaskStore.admit` 在同一 Session 事务中冻结本轮 `SemanticTurn.context`，保存入场计划、来源任务及待明确输入。模型收到对应 `admitted_context`，包含确认条件、未决项和 Frame 来源。同轮焦点变化不能改变该基线，重试也不能按新的最近任务重新选择来源。

跨用户回合的 `query/prepare` 从声明来源派生新计划，待补目标也不原地改写旧计划。中间草案与 `needs_interpretation` 不切换业务焦点；`ready/prepared/needs_user` 或正式成功状态才成为焦点。默认 `runtimeContext` 只投影焦点计划，历史仍由上下文工具全量分页读取，避免把错误草案平铺成当前业务条件。

Pi 能确定目标就直接提交 `resolve_business_turn`。只有结合上下文仍存在多个合理解释时，才调用 `clarify_business_turn(question, alternatives)`；备选为宿主签发的 `task_ref/target_ref/label` 配对，至少两项且互不重复。宿主保存 `SemanticClarification`，在下一轮 `admitted_context.pending_clarification` 投影，不执行任何备选分支。

用户补答后，Pi 明确选择处理方式：`resume` 配合已保存备选的 `reference` 恢复原修改；`defer` 保留原待明确输入；`abandon` 放弃原修改。缺省不恢复，仅选择同一引用也不触发恢复。`reuse` 不能与 `resume` 合并；暂看原结果时使用 `defer`。需要再次追问时，澄清工具可显式 `resume` 组合此前原句和本轮补答，或用 `abandon` 从当前输入重新建立澄清。新建目标始终只绑定本轮条件。

这些决策由 Pi 完成，宿主不通过追加、清空、话题切换或代词关键词选择作用范围。引用或动作错误反馈 Pi 修正，真正缺少业务条件或用户选择才返回 `needs_user`。

## 接纳消息时先保存用户目标

本节的 `GoalContract` 是来源与义务职责名称。当前数据保存在 `SemanticTurn`、`SemanticPlan.requirements`、字段及 `pendingChanges` 中，不另建同名模型或第二套历史。

宿主在 admission 接纳原始用户消息时，先在同一原生 Session 中登记 `GoalContract`：保存原始消息引用、用户回合与身份、当前上下文可用的可信历史义务及来源引用，以及尚待解释的本轮目标。已经明确续接的义务登记为待保留；归属尚未明确时保存未绑定候选，待同一 Pi 解释并选择引用，登记本身不默认继承旧焦点。原文沿用原生消息记录，不另建消息历史。首次模型提案之前就建立这一来源边界；登记失败时不能签发业务执行许可。

Pi 提交的 `targets` 是对用户目标的解释与实现提案，不能自行定义完整义务全集。宿主把提案与 admission 保存的原文、既有目标义务及独立可确定的硬约束对账，补充未覆盖义务或记录具体冲突。没有提及某个已知义务，不等于用户撤销了它；也不能因为模型只提交一组就把完整性分母改成一组。

可独立对账的依据包括正式目录提及及其候选、明确数量、可确定的日期边界与机构指标日期绑定，以及来源任务中仍有效的已确认义务。宿主保存这些依据及其确定程度，核验正向目标、替换来源、排除对象和比较对象的角色；不能把原文中全部目录提及都当作正向目标，也不能把模型未选择的提及自动编译成排除。

例如原文明确要求“查询指标甲和指标乙”，正式目录已经确定甲、乙及其正向查询角色，而 Pi 只提交甲时，乙必须留在任务的未决义务中，明确复合请求不能取得半份执行许可。相反，“把甲换成乙”中甲是替换来源，不能要求继续查询甲；排除成立仍需核验来源状态和完整用户变更，不能由模型选择结果反推。

任意自然语言的全部含义不能由宿主形式证明。无法从现有证据确定语义时，宿主保留原文和未绑定提案，向同一 Pi 返回具体尚未解释的关系，让其继续解释或查证；只有存在会影响答案的实质歧义或用户尚未作出的选择时才询问用户。目录空匹配本身不拒绝全部表达，也不把它自动判成用户没有指标目标。任务 ledger 提供追踪和硬约束校验，不构成语义正确性的自我证明；大于 95% 的目标依赖独立完整任务验收。

缩减或撤销原目标只能依据新的用户明确变更，并保留变更与原义务的关联。Pi 为修复参数而删除 `targets`、降低数量、缩短日期或把冲突目标改称非必要，不产生缩减授权。

## 状态分别表达什么

| 状态 | 回答的问题 | 不能据此推断的结论 |
| --- | --- | --- |
| 原生 operation 状态 | 本轮 Pi 运行是否仍在执行，或已经结束 | `completed` 不表示业务任务完成 |
| 任务目标与完成状态 | 用户要求的哪些目标已经取得足够证据，哪些尚未满足 | 一个查询成功不表示整个分析目标已完成 |
| 步骤状态 | 当前步骤处于待解析、可执行、在途还是已有正式结果 | 步骤可执行不表示已经发出查询 |
| 本轮停止原因 | 为什么本轮交付答案、澄清、拒绝或未完成说明后停止 | 正常交付澄清不能标为查询成功 |

任务可以跨多个用户回合存在；一次原生 operation 也可以执行同一任务的多个步骤。澄清交付后，原生 operation 可以正常结束，而任务仍等待用户输入。运行因传输中断或纠错预算耗尽而结束时，任务不能自动完成。

## 同一 Session 中的领域值

以下为内部概念模型，不是要求模型填写的完整工具参数。实际工具只提交本轮语义提案和明确引用，宿主生成标识、版本、依赖、编译参数和执行许可。

| 领域值 | 必要内容 | 写入责任 |
| --- | --- | --- |
| `SemanticTask` | `taskId`、状态版本、协议绑定、用户目标、目标义务、当前提案、步骤索引、完成判定 | 宿主按校验结果更新 |
| `GoalContract` | admission 保存的原始消息引用、历史已知义务、用户希望得到的答案、明确范围和约束、未解释部分 | 宿主先登记来源与已知义务，再对账 Pi 解释 |
| `TargetRequirement` | 独立目标标识、机构与指标及日期之间的绑定、必要输出、未决条件、满足该目标的证据引用 | 宿主保留完整目标集合 |
| `ChangeProposal` | 本轮待解释的新值或修改、证据引用、解析状态、影响的目标与步骤 | 参数错误也保留有效提案及未决变化 |
| `Step` | `stepId`、步骤版本、目的、依赖、输入引用、输出约定、执行状态 | 模型可以提议下一步，宿主确定可执行性 |
| `EvidenceReceipt` | 来源工具或后端任务、查询范围、统计日期、版本、结果引用、完整性和权限关联 | 正式工具或后端回执产生 |
| `ExecutionPermit` | 任务与步骤版本、编译快照摘要、依赖摘要、执行身份、权限范围、幂等命令关联 | 仅宿主签发和消费 |
| `TurnDisposition` | 原生 operation 引用、运行状态、答案交付状态、停止原因及当时任务完成状态 | 宿主投影到页面和审计 |

状态存储复用原生 Session 的事务能力，不另建 Agent 记忆库、第二条消息历史或独立规划循环。领域值可按任务和步骤分键保存，但一次状态转换涉及的任务、步骤、许可和命令登记必须原子提交。Session 的存储版本、任务语义版本、步骤版本和协议版本各自独立，不能用同一个计数代替。

### 工具反馈与持久化边界

工具反馈及其下一步使用[反馈与引用契约](feedback.md)，反馈状态不等同于任务或步骤内部状态。`invalid_input` 中的 `task_status=unbound` 只表示形状错误尚未绑定任务；它不是已持久化 `SemanticTask` 的状态，也不证明业务条件已经保存。admission 已记录原始用户消息和 GoalContract 来源，不意味着失败工具调用已经创建了可继承任务。已保存任务中的待解释提案按相应任务引用反馈，不能标成 `unbound`。

`ready` 反馈必须对应实际已保存且未失效的许可；`succeeded` 仅证明当前步骤已有正式成功回执。反馈中的 `conditions` 只含可信已确认条件，未决表达位于 `pending`；`continuation` 仍由同一 Pi 工具循环或宿主许可接续入口消费，不建立第二条循环。

### 目标绑定与未决提案

`TargetRequirement` 保留用户明确表达的绑定。例如“甲行六月存款、乙行七月贷款”是两组目标，不能展平成两个机构、两个月份、两个指标的笛卡尔积。字段引用、来源、数量和输出要求都归属到相应目标；共享条件使用明确引用，不靠复制文本维持一致。

提案的解析状态至少区分 `unresolved`、`resolved`、`needs_confirmation`、`invalid_calendar`、`unsupported_expression` 和 `conflict`。合法原文暂未被解析器支持，不等同于用户提供了无效日期；模型参数形状错误也不等同于业务含义缺失。

时间业务值仍是字符串。Pi 解释用户要求的是滚动范围、自然年、独立时点还是分析衍生期间；宿主根据统一业务日期、时区和明确的日历规则完成计算、边界规范化与合法性校验，并保存计算基准。存在“最近五个完整年度”与“向前滚动五年”等多解时，由同一 Pi 继续解释或询问用户，宿主不能用取数便利性选择其中一种。时间区间与取最新一期、完整序列或离散时点的选择分别绑定，不能把范围自动缩成月末或最新日期。

用户本轮真实提出的新值即使尚未解析成功，也必须留在待决提案中并阻断相应目标。省略待修字段不表示撤销新值，不能因此继承旧值。模型填入而没有本轮或可信来源依据的值属于 Pi 参数错误，不能建立用户未决义务；反馈修正后省略该错误字段可恢复冻结基线。两类来源须区分，不能用同一种“保留”规则让模型占位值永久污染任务。

完整目标变更期间，日期仍未明确时，已规范的指标子状态及其来源继续保存；后续替换指标、补日期时不能重新要求已被替换的旧指标。必要字段未齐备之前不签发可消费的执行许可。

### 证据与来源

本轮原文、历史字段、目录事实和执行结果是不同的来源类型。宿主内部绑定本轮原文证据引用，保留原始跨度及完整上下文；公开入口不要求模型重复抄写 `source_text` 或填写跨度。模型的语义改写不是原始用户证据，也不能把历史内容转成本轮用户输入。否定、转折、数量和候选接受仍须结合完整回复及字段归属判断。

继承已确认字段不要求用户重复给出名称或日期。引用映射绑定任务身份，以及目标身份、签发时语义修订和条件快照。继续当前任务时，`target_ref` 必须匹配当前修订；不匹配返回 `REFERENCE_REVISION_CONFLICT`，让 Pi 重新读取上下文，不能静默套用旧快照或覆盖新值。

历史任务条件作为不可变来源快照导入新任务，不修改旧任务。导入仍要核验来源操作的最新在途或未知状态；显式引用旧 READY 不能绕过这一门禁。多个合理来源时保存歧义，不能选最近一次或用数量凑齐来源。使用历史机构或结果前，仍执行当前权限复核。

引用映射从原生 Session 恢复，不因模型压缩或进程重启自动失效，也没有任意的分钟级有效期。跨 Session、错误配对或未签发引用返回 `REFERENCE_INVALID`；按会话保留策略清理、来源撤销或记录损坏后返回 `REFERENCE_UNAVAILABLE`；当前权限不足返回 `PERMISSION_DENIED`。均不得回退到最近目标或扩大范围，生命周期细则以[反馈与引用契约](feedback.md)为准。

证据回执保留结果实际覆盖的机构、指标、日期、粒度、单位和截断情况。执行成功但只返回部分数据时，应记录部分覆盖，不能仅因 HTTP 成功或存在一行结果就满足全部目标。正式“无数据”结论只有在查询范围与完整性足以支持该结论时，才可以作为该目标的回答。

指标来源区分 `user_explicit` 用户显式目标与 `analysis_selected` 分析选取，来源标签由宿主内部生成。用户显式指标要逐项完成目录身份与覆盖核验，不能用已查到的其他指标替代。分析目标允许 Pi 依据目录、Skill 和已有证据选择正式指标；宿主保存目录回执、选择与分析目的的关联及依赖，再核验身份、范围和权限，不要求所选指标名称出现在用户原句。分析选取也不能反过来覆盖或删掉用户已经点名的指标目标。

## 任务和步骤如何推进

任务的业务状态采用 `active`、`waiting_input`、`waiting_dependency`、`completed`、`stopped`；当前目标状态为 `draft`、`blocked`、`ready`、`executing`、`succeeded`、`failed`、`unknown`，计划步骤另有 `waiting_dependency`。完成程度为 `unmet`、`partial`、`full`。状态转换由宿主依据领域值和正式回执决定，模型的“已经完成”文字不产生状态转换。

| 事件 | 宿主处理 | 任务或步骤结果 |
| --- | --- | --- |
| 用户提出新目标或修改条件 | 保存完整提案，绑定原文与来源，校验目标覆盖 | 未决部分进入等待；已知条件保留 |
| 条件与来源全部满足当前执行要求 | 编译步骤输入，复核依赖及权限，签发许可 | 对应步骤成为 READY |
| 许可被消费 | 原子登记在途状态和幂等命令，再调用工具或后端 | 步骤成为 EXECUTING |
| 后端返回正式终态 | 保存不可变结果引用、覆盖信息和失败类型 | 步骤成功或失败，随后重新判断目标覆盖 |
| 用户修复条件或新证据改变判断 | 更新语义版本，失效受影响的编译快照和后继步骤 | 有效证据保留，必要步骤重新解析 |
| 缺少用户选择 | 保存已知条件及规范候选，生成具体澄清 | 任务等待输入，本轮停止 |
| 运行异常或纠错耗尽 | 保留任务及在途关联，说明未完成部分 | 不将任务或未知执行结果标为成功 |

当前步骤可以是目录发现、可用性查询、指标取值、受治理计算或结果组织等已注册能力。任务语义可以扩展为趋势、比较、覆盖检查、异常线索、解释目标及复合目标；扩展语义类型不自动扩展后端执行能力。未实现的能力必须保留用户目标并明确受阻，不能降级成普通取值后宣称完成。

### 明确复合请求和开放分析请求

明确复合请求需要先保留全部目标，并核验其绑定和必要条件。一个目标缺少指标、日期或机构时，可以进行有依据的目录与来源解析，但不能擅自执行其他目标的半份取数。全部必要条件已确认后，可将目标编译成多个步骤按依赖执行；其中一个步骤失败时保留已取得证据，任务仍不完整。用户明确接受先处理一部分时，记录对应授权后再执行该部分。

开放分析请求可以根据已取得证据逐步提出下一步，无需在首次请求中冻结完整计划。宿主维护当前已知目标义务和依赖；某个探索步骤具备可信输入、权限及与用户目标一致的目的时，可以获准执行。后续重规划可以替换尚未执行的假设和步骤，但不能删掉用户明确要求的目标、抹去已发生的执行或把未决业务选择当成默认值。

同一任务可以同时包含明确目标和探索目标。开放计划不削弱明确目标的完整性要求，完整性要求也不禁止为解析或分析进行必要探索。

## 跨轮状态对账与 Frame

初始独立查询继续核验原始目录覆盖、机构日期指标绑定与全部必要条件。跨轮变更则从冻结来源生成宿主内部 `SemanticTransition`：`before` 是旧完整查询范围，`changes` 保存实际规范化的字段动作及各自 `before/after`，步骤 `spec` 是最终 `after`。Pi 不填写这些结构或来源签名。

后端 `/api/v1/business-context/admit-plan` 先验证来源回执与旧 `before` 的身份、会话和完整范围，再核对字段动作链及最终 `after`，复核当前目录、日历、权限和本轮显式条件。替换、排除中出现的旧身份由变更账本解释，不重新变成必须查询的正向目标；未被来源或变更解释的本轮条件仍阻断执行。

`context_sources` 只提供未修改的可信旧范围，用于解释用户同时提到的原结果。其 `changes` 必须为空，不能扩大待执行 `steps`；后端仅为真正的执行步骤签发新票。状态对账证明动作与规范结果一致，不能形式证明 Pi 的自然语言判断正确。

Frame 继续承担执行快照职责。修改已编译目标时生成新 Frame，保留 `parentFrameId` 和 `delta.baseReference`，`delta.fieldChanges` 标出实际变化字段；完整集合动作保留在任务的 `transition.changes`。旧 Frame、正式结果及其引用保持不变，执行仍须经过整批准入、步骤许可与消费时复核。

没有完整范围的待补目标不能伪造 `before` 或裸用 `after` 签票；保留原始义务、已确认子状态、真实候选与来源，条件齐备后再核验。旧无票 Frame 的兼容路径只复核既有指标覆盖，不能宣称其等价于完整范围签名。详见[兼容与切换边界](implementation-multiturn-context.md#兼容升级与回退)。

## 执行许可不变量

执行许可是宿主内部记录，模型只提交目标语义与宿主签发的来源引用，不能填写权限指纹、执行身份、幂等键或后端结构化参数。签发和消费许可分别核验以下条件：

1. 当前原生 operation 绑定正确的协议、用户、Session 和任务；工具调用属于该协议的唯一参数格式。
2. 当前目标和步骤版本与许可一致，所有必需输入有可信来源，未决新值和明确数量约束均已落实。
3. 当前执行组已与 admission 原文及可信历史义务独立对账，全部可确定目标已经覆盖，未解释的必要义务仍阻断执行；跨字段组合、机构日期指标绑定、计算依赖及证据范围均通过校验。不能仅以 Pi 本次提交的 targets 计算完整性。
4. 历史来源的最新状态可用；参数修复不跳过用户真实未决字段。未获准提案可由 Pi 完整纠正来源并重新核验；已获准或执行的来源不能借重组被覆盖。
5. 执行身份与当前权限有效；许可绑定的范围与本次编译范围一致，后端仍在实际执行时鉴权。
6. 编译快照及依赖摘要未改变，命令幂等关联唯一，不能以同一幂等键提交不同输入。

许可签发不替代消费时复核，消费时复核也不替代后端权限与数据契约。Frame 中的 READY 标记只是编译结果，不能凭旧标记、模型文字或客户端字段绕过许可。

### 修复及依赖失效

机构、指标、日期、取数方式、比较总体、计算输入或用户目标发生有效变更时，宿主按依赖图失效相关步骤、编译快照与派生证据。修复一项不能自动改写其他尚未确认的业务选择。历史绑定、用户明确数量以及新增未决成员随同一提案继续保留。

阶段初始实现可以在任务语义版本改变时失效该任务全部未消费许可，再为未受影响的步骤重新核发；这不要求重跑输入和权限仍有效的已成功查询。已保存证据保持不可变，并带有原版本和依赖范围；只有证据仍适用于修订后的目标时，才能再次用于完成判定。

参数格式纠正与业务条件变化应分开。仅修复同一证据引用的格式且没有改变语义输入时，不创建新的业务目标或重复查询；改变语义值则必须进入版本与依赖校验。

## 幂等执行和中断恢复

第一次发送前，宿主在同一事务中消费许可、登记步骤 EXECUTING、保存后端幂等命令与关联信息。网络调用发生在事务提交之后。同一步骤同一输入的传输重试使用原命令关联，不能因新模型调用、刷新页面或重新签发许可而换键。业务输入变化后生成新步骤版本和新命令，保留与旧执行的关联。

超时、断连或进程重启造成结果未知时，先按已登记命令回查后端。仍在途、暂时查不到或在保护时间内返回不存在时，保留未知状态，不能把它当成已失败并生成另一笔执行。读取页面、历史或状态的接口只做回查，不主动发起新的业务查询。

原生 operation 仍承接原授权时，可在其 Pi 工具循环中按同一命令继续恢复。原 operation 已结束后，新回合重新发送需要有用户恢复意图，并再次通过来源、版本和权限门禁。后端正式结果到达后，只完成对应步骤；旧请求的迟到结果不能夺取新任务焦点，也不能把新版本标成已完成。

任务、步骤、许可和命令登记复用同一 Session 事务及版本检查。并发冲突须重新读取状态再判定，不能静默覆盖另一回合的修改。部署单写控制继续有效；若将来支持多实例并发写，需先更换相应存储和互斥契约。

## 完成与停止分别判定

任务完成要求与 admission 原文和可信历史对账后的全部仍有效明确目标义务有相匹配的正式证据，分析结论的依赖也已满足。部分成功、数据截断、来源不明、权限拒绝和未决选择不能冒充完整完成。用户接受部分结果时仍须保留原请求、接受范围及未完成义务；当前完成枚举为 `unmet/partial/full`，不生成未实现的 `partial_accepted` 状态。ledger 中已经满足的比例不能替代对原始完整任务的独立验收，也不能靠删减义务提高完成率。

本轮停止原因至少区分答案已交付、等待用户、用户取消、能力不支持、权限拒绝、参数纠错无进展、工具预算耗尽、模型传输中断和执行结果未知。页面同时展示运行、答案交付与任务完成状态；不再把 `completed` 直接映射成业务成功，也不把解析不支持统称为用户条件无效。

## 与当前实现的连接点

| 当前模块 | 当前职责 |
| --- | --- |
| `semantic-task/store.ts` 和原生 Session | 保存计划、任务、入场快照、引用、待明确输入和版本；复用 Session 事务 |
| `semantic-task/protocol.ts`、`prompt.ts`、`tools.ts` | 投影 V2 参数与唯一 Pi 工具循环；目标明确直接解析，真歧义调用目标澄清工具 |
| `semantic-task/planService.ts` | 按 Pi 显式来源编排目标、接续澄清、维护依赖并请求整批准入 |
| `semantic-task/service.ts`、`transition.ts` | 规范字段、核验来源与集合动作、保存规范状态变更、编译 Frame 及复核步骤许可 |
| 后端 `business_context.py`、`semantic_transition.py` | 独立核对初始覆盖或跨轮 before/trace/after，复核目录权限并签发范围回执 |
| `business-context/store.ts`、`adapters.ts` 及受治理执行器 | 保留不可变 Frame、命令关联与正式结果，继续经后端鉴权执行 |
| `harnessHost.ts`、会话投影及前端 | 向同一 Pi 提供冻结上下文，接续获准步骤并投影任务、证据和未完成状态 |
