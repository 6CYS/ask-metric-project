# 问数与多轮上下文实现

研发契约见[问数与多轮上下文重构研发说明](../问数与多轮上下文重构研发说明.md)，本文件说明实际运行入口。

## 调用链

`用户消息 + 入场快照 → Pi 结构化条件或增量动作 → 统一绑定和更新 → Task.target.fields → Frame → Backend → 正式结果`

沿用同一 Pi 原生 Session、模型和工具循环。`resolve_business_turn` 使用版本 2 协议；Plan 只组织目标与依赖，Task 保存规范字段、候选和未决变更，Frame 保存执行快照及结果关联。

| 模块 | 职责 |
| --- | --- |
| `protocol.ts`、`tools.ts` | 工具入口按唯一 Schema 处理参数形状及字段动作组合 |
| `structuredQuery.ts` | 把完整 `query` 转成现有字段更新；排序和排名保留结构化操作，不再解析描述文案 |
| `actionBinding.ts` | 共享本轮事实与字段解析；更新前补齐确定条件、绑定集合动作及跨目标字段复制 |
| `sourceGuard.ts` | 绑定唯一续补来源、查询序号与历史目标；真实多义时保存修改意图和备选来源 |
| `service.ts` | 应用一次字段更新，保存真实缺项与候选，编译最终条件并签发任务执行许可 |
| `planService.ts` | 组织步骤、计算依赖和正式完成状态；不维护另一份覆盖或准入结论 |
| Backend | 接收规范化 `BasicQuerySpec`，控制目录、权限、SQL、执行幂等和正式结果 |

新查询的 `query` 同时表达机构、指标、时间、取数方式和操作，真实缺项为 `null`；续问、补答和历史修改使用 `operations`。两种输入共用 Task 状态和执行器，缺项均进入同一问题处理流程。

## 来源与状态

每轮接纳时冻结 `SemanticTurn.context`；工具重提、历史读取和其它任务的焦点变化不修改本轮基线。字段动作保存于 `SemanticTurn.operations`，当前条件保存于 `SemanticTask.target.fields`，未决修改保存于 `pendingChanges`。

真正独立的 `new` 从空条件开始，`current` 续接唯一入场目标，`reference` 选择同 Session 签发的来源。模型误选 `new` 时，唯一待补、明确保留其他条件或明确的增量续问直接归一为可信来源；明确不沿用时不继承。

查询序号按业务历史索引定位。跨多笔历史的“那一笔”有多个合理对象时，保存原修改及备选引用并追问，不能由模型任取当前一笔。历史读取不触发 SQL；明确选择旧目标继续操作时派生新计划，旧计划和结果保持原样。

`admit` 冻结基线与 `runtimeContext` 的当前任务均取 `focus.business`；`discussion/display` 只记录讨论和展示。回读历史不能让两处使用不同的“当前任务”，无来源限定的字段续问仍接工作任务。

## 动作与缺项

- `set` 替换整个字段集合，`add` 取并集，`exclude` 取差集，`replace` 替换指定成员，`clear` 保留字段缺项。
- `copy` 从签发来源复制已确定的字段；两笔目标交换日期等联动动作也绑定为字段复制。
- 字段保存最终正式集合，动作原文留在轮记录中。排除过的成员不再成为正向义务，重复排除不误删剩余集合。
- 机构、指标和日期在各目标内绑定。完整独立片段构造对应目标，不能把全局集合相同当作配对正确。
- 可以唯一确定的漏填直接补齐或归一；用户没有提供的信息才进入 `FIELD_REQUIRED`，真实歧义保留候选等待确认。

缺指标、缺机构、缺日期和多个缺项均逐轮累积有效条件；补齐后按完整条件查询。用户真实提出的未知新值持续未决，不能回退旧值执行；模型额外改写用户未要求修改的字段不成为新条件。指标口径和相近名称仍由目录确定。

时间沿用既有 `modelCalendar → model_value` 通道及确定性日历解析；已有本轮日历事实直接复用。日期缺失不补今天，无数据不换成最近有数日期。未变化的指标、机构、日期保留正式身份及来源。

时间尚未换算时仍保存完整表达；模型只摘取一个端点时，在绑定阶段恢复该表达。可以确定的完整日历直接归一；尚无完整换算时不执行缩小后的日期，补齐后仍使用同一字段入口，不增加更新后的日期对账。

结构化条件与增量动作共用首次缺项归一：指标名中的“当日数”不提供日期；没有日期依据时保存真实缺项，有可信旧日期且本轮未改日期时继承。日期候选回复直接交给已保存候选的选择逻辑，不作为新日期重新要求原文。

## 问题与历史续接

已发布字段问题通过 `answers` 引用 `question_id/version/option_id`；点选、序号和名称均绑定实际候选，否认不视作接受。可信点击先确定本题答案；被覆盖的模型复述仅作审计，不再次校验其摘录。修改其它字段不会确认未答候选，也不会丢掉未决修改。

目标歧义保存为 `pending_clarification`。`context_action=resume` 结合原修改和补答继续；`defer` 暂缓，`abandon` 放弃。字段问题与目标定位问题分别保留各自绑定。

## 执行与重复调用

最终必需条件齐备后编译 Frame，任务许可绑定 operation、修订、frameId、条件摘要和消费状态。消费时复核当前权限、版本与在途状态，Backend 执行规范化条件。

条件等值且已有成功结果时复用原结果；明确重新查询产生新执行；同请求 ID 返回原操作；结果未知只回查原命令。无数据必须来自实际查询的零行结果。

同轮事实与字段绑定结果复用，执行前权限复核保持独立。同一失败是否有进展只比较根因、正式条件和候选；换引用或改错误文案不增加进展。

## 已清理路径

`groupAdmission`、`Plan.admitted`、`SemanticPlan.requirements/checks`、更新后原句正向覆盖、来源对齐打回、日期范围二次对账及业务层重复动作形状错误已清理。`transition.ts`、后端 `semantic_transition.py`、`analysis_selection.py`、`/admit-plan` 及来源票据不再参与运行，没有恢复旧准入的开关。

`querySpec.ts` 只从已确定字段投影规范化查询。Frame 以最终 `fields` 表达条件，通过 `parentFrameId/delta.baseReference` 保留来源；完整集合动作保存在工作状态中，不再组装第二份变更证明。

## 发布与验证

Agent 与 Backend 配套发布；Backend 查询接口只接受当前规范化字段。原生 Session、历史 Frame 和结果继续可读；旧记录中的覆盖字段不再用于准入或完成判定。在途执行按原执行 ID 结算，不重放查询。

验证分别记录静态检查、单元及宿主链、真实 Python 契约、真实模型合成数据、业务数据库和页面结果。验收核对每轮保存状态、候选、实际查询条件、执行次数及正式回答，不能只检查追问文案。
