# Ask Metric 功能清单与两个月交付范围

> 产品经理视角的菜单功能、八周排期、数仓数据需求、验收场景和官方平台参考已整理为 [Excel 工作簿](/Users/deng/Documents/02_开发/04_AI/zbws/outputs/01a1775d-43b1-7ad2-99d8-a082bd08cc68/Ask-Metric菜单功能清单与两个月计划.xlsx)。本文件保留功能与技术工作的补充说明；菜单是稳定操作入口，客户流水归因等属于问数场景，不单设菜单。

日期：2026-10-27。人员条件：两名开发，业务和数据同事配合。配套阅读：[两个月实施计划](superpowers/plans/2026-10-27-ask-metric-two-month-plan.md)。

两个月的目标是交付一个可供业务试用、能够维护和复测的智能问数版本：保留 Ask Metric 的平台与权限数据基础，吸收 mfws `jjccb-release` 的业务理解、连续对话、按需调查、计算和自然回答方式。首批建议覆盖存款与贷款质量；具体机构、指标、期间和分析深度在第1周按真实数据确定。

本期同时安排功能完善、数据准备和必要的代码整理。完整平台能力列入清单，但不全部承诺在两个月内交付。

现有全量指标目录和检索能力继续保留；首批主题用于集中核准口径与验收效果，不通过硬编码把其他指标拒绝在外，也不承诺两个月逐项审核全部一万多个指标。

## 1. 范围和状态怎么理解

- **必做**：两个月的基础交付范围；包含现有功能的核实、修正和必要补齐，不代表全部从零开发。
- **条件必做**：本期分析目标，依赖业务确认和真实数据。依赖未满足时报告未完成，不用改名称、编数据或降格验收代替。
- **选做**：基础交付通过且有剩余容量时安排；不挤占联调、验收和缺陷修复。
- **后续**：保留在平台路线图，本期不默认实施。
- **已有基础**：源码存在实现，仍需要当前版本验收；**部分接通**：界面、接口与实际执行不完全一致；**待补齐**：未形成完整使用流程。

现状依据为 `develop-ws@0d86941` 及2026-10-27已核对的工作区。其他窗口的未提交修复应在第1周重新确认，不当作已经验收完成。本文是交付范围方案，不修改现有功能状态。

## 4. 贯穿本期的代码质量要求

1. 新旧问数路径先核对调用方与兼容需求，再收敛共同职责；不为删文件破坏历史会话或结构化入口。
2. 报告核验聚焦对象、来源、量纲、精度与计算；删除已证实误伤的语义词法规则，不继续补原句白名单。
3. 实时结果和历史恢复复用共同转换，保留必要的进度/只读差异；关键状态与接口结构明确类型。
4. 随本期改动拆开职责过重的函数，避免工具反向依赖整个宿主；不安排全仓格式化或与业务无关的大重构。
5. 用同类问题的正常、拒绝和异常情况验证；本地桩只能验证代码，实际验收使用真实数据、模型和执行链。

## 6. 两个月后如何判断交付成立

- 业务人员能在首批批准范围内查值、比较、连续追问，看到一致的正文、图表与明细。
- 一组正式关系在数据门槛满足时完成发现、两期分解、核算与解释；未完成时单独标明，不宣称完整归因。
- 管理员能维护现有目录和知识、辨认生效配置；数据集已承诺的控制确实影响执行。
- 用户反馈有人处理，相关修复有复测依据；新版本能与基线比较。
- 权限、缺数、失败恢复及基本发布恢复有实际验收记录。
- 代码整理降低重复与职责混杂，保留兼容行为；不以文件数减少、测试数量或菜单数量代替业务效果。
