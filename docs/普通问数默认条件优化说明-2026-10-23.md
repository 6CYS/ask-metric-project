# 普通问数默认条件优化

本次围绕“业务用户没有说机构、日期就被反问”的问题改造。用户已确认：普通取值问题使用账号所属机构和该指标最新有效数据日，并在回答中说明。

## 行为约定

| 用户表达 | 处理方式 |
| --- | --- |
| “查各项贷款余额当日数” | 使用认证账号所属机构，查询截至业务日的最新有效值。 |
| 指定机构、没有日期 | 保留指定机构，按该机构与指标查询最新有效值。 |
| 指定日期、没有机构 | 仅补账号所属机构，不覆盖日期。 |
| “换指标，日期不变” | 继承上次实际查询日期；该日无数据就如实说明。 |
| “这个指标查最新” | 重新选择当前指标、机构的最新有效数据日。 |
| 机构未知、候选有歧义、账号机构不可用 | 保留必要澄清，不换成另一家机构。 |
| 明确清除或拒绝默认条件 | 不自动回填被清除或拒绝的条件。 |

最新有效日不是系统今天，也不是原始记录中最大的日期。取值仍使用现有正式指标、机构授权和数据清洗规则；未来数据、NULL 和现有规则识别的无效值不作为有效值，零值保留。

如果多项结果的最新日期不同，回答披露不同日期；如果没有结果，不生成实际日期。只有完整结果确定了一个实际日期，才将它固定为下一轮可继承的条件。无统一日期时，用户要求“日期不变”需要进一步明确；普通继续按最新策略查询仍可执行。

## 代码落点

路径相对工程根目录。

| 部分 | 主要文件 | 改动目的 |
| --- | --- | --- |
| 缺项处理 | `agent-service/src/semantic-task/service.ts` | 在现有查询门禁前补可信默认，保留显式条件、历史和歧义。 |
| 日期状态 | `agent-service/src/business-context/queryDates.ts`、`business-context/service.ts` | 使用后端完整日期证据固定实际时点，避免从样例行推断。 |
| 回答与恢复 | `business-context/resolutionNotice.ts`、`tools/businessContext.ts` | 当前回答、历史回看及中断恢复采用一致的范围和日期说明。 |
| 查询契约 | `agent-service/src/backendClient.ts`、`tools/structuredQuery.ts`、`backend-next/src/ask_metric/domain/basic_query.py` | 普通 value 支持 `time: {preset: "latest"}`，与 `selection: "latest"` 配对。 |
| 取数执行 | `backend-next/src/ask_metric/domain/query_execution.py`、`application/query_execution_service.py` | 复用现有 AS_OF 查询，业务日只作上界，返回真实日期证据。 |
| 运行提示词 | `agent-service/src/semantic-task/prompt.ts`、`enhancedAnalysisPrompt.ts`、相关业务 Skill | 同步默认政策，普通查值不因缺条件或“最新”扩写经营报告。 |

旧的明确日期请求保留原序列化形状，避免改变幂等指纹。`latest` 本次只开放给普通取值，不放松排名、比较与计算的口径要求。不新增服务、数据库表或运行依赖。

## 与两个工程融合的关系

这一轮吸收的是 `jjccb-release` 中明确条件优先、可信上下文继承、只澄清实质歧义，以及根据真实数据确定日期的处理思路。它们落在 Ask Metric 现有 Agent 与查询链路中，没有整套搬入另一套框架，也没有把受控 SQL 改成自由生成。

这是已确认首期范围中的一个具体改进。业务知识、案例检索、复杂意图和归因能力仍需根据真实问题逐项验证，不能以本次默认条件改造代表全部融合完成。此前实测中的百分比展示、复合计算和归因表述问题不在本次修改范围。
