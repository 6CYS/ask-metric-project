# 开发规约

适用范围：`agent-service` 的 TypeScript、`frontend-vue` 的 Vue/TypeScript、`backend-next` 的 Python，以及直接相关的检查脚本。规范随代码评审执行；自动检查只能覆盖其中可静态判断的部分。

项目已有且一致的约定优先；TypeScript 参考 Google TypeScript 通用条款，Python 以 PEP 8 为基础，Vue 遵循对应框架实践。工具版本和实际规则以锁文件、ESLint 配置、`tsconfig`、`pyproject.toml` 为准，不机械套用外部规范。

## 1. 模块和职责

- 先确认业务目标、调用方和现有公共实现，再决定修改位置。只为真实复用建立抽象，不新增无调用方的通用层。
- Pi 原生会话运行与我们的业务适配分开说明。业务预算、权限、查询、计算、交付的状态各有明确拥有者，避免多个钩子或工具分别维护同一状态。
- 前端负责展示与交互，不在展示层改机构名称、替换结果或修正业务计算。公共转换负责数据适配，不隐藏权限和查询语义。
- 相同职责优先复用一个实现；替换旧实现时核对入口、配置、历史协议及测试，完成迁移后退出旧路径。历史数据转换放在明确边界，不散布到业务流程。
- 正则用于明确格式的解析与规范化，不对整段自然语言作意图、事实或因果裁决。正式目录里的同义词、机构别名可以维护，通过统一目录解析使用。
- 同一改动不混入无关格式化、重命名、依赖升级或功能扩展。拆文件必须改善职责和依赖关系，行数减少本身不算完成。

## 2. TypeScript 与 Vue

- 变量和函数用 camelCase，类型与组件名用 PascalCase；沿用现有目录及组件文件命名，不为风格统一改动无关文件。名称表达业务含义，布尔值表达判断，避免无意义缩写和含糊的 `data`、`info` 层层传递。
- 保留现有 `strict` 和各包附加严格选项，不通过关闭类型检查迁就实现。
- 外部输入从 `unknown` 开始，在协议边界解析后进入明确类型。状态优先用有区分字段的联合类型，处理所有有效分支；不得把未知状态默认为成功。
- 不使用无依据的 `any`、非空断言或双重类型断言绕过校验。确需类型断言时应有可核对的外部契约或运行时检查。
- 每个 Promise 必须等待、返回给调用方或显式处理拒绝。仅加 `void` 不代表已处理失败；后台工作应说明生命周期并有错误出口。
- 明确超时、取消、重连、竞态和过期响应的处理。Vue 的监听、副作用与订阅按组件生命周期注册和清理，避免不必要的重复状态。
- 组件保持展示与业务协调边界。可以从 props 或其他状态推导的值，不再维护第二份可变副本；重排列表使用稳定 key。
- Vue 和 Node 分别使用自身适用的规则；不将 React 专属约定套入 Vue。公共 API 类型、序列化格式和调用方同步修改。
- 格式交给 Prettier；Agent 保留分号，Vue 保留现有无分号习惯。规则不与格式工具重复争用排版。

## 3. Python

- 函数、变量和模块用 snake_case，类用 PascalCase，常量用 UPPER_SNAKE_CASE；公共名称应与业务和接口语义一致，不创建同义但含义不同的类型。
- 保持包职责和依赖方向清楚，关键入口与跨模块接口提供参数、返回值类型。复杂数据优先复用已有明确结构，不在多层传递含义不明的字典。
- 静态类型检查与运行时输入校验各司其职。类型注解不能替代权限、数据来源或外部输入校验。
- 捕获能够处理的具体异常；必须使用宽捕获的协议边界应保留脱敏根因并返回明确失败。禁止空捕获、打印后假装成功或以默认值隐藏失败。
- 数据库事务、连接和会话有明确生命周期；异步路径不直接执行会长时间阻塞事件循环的操作；并发恢复要核对所有权和状态版本。
- 金额和精确业务计算继续使用 `Decimal`，明确单位、舍入与展示精度。展示换算不修改原始事实，不重复实现多套换算。
- 格式与导入排序使用 Ruff，保留 100 列和 `E/F/I/UP/B` 规则。mypy 先覆盖全部业务源码、按渐进模式检查，不能用全局忽略让类型错误消失。

## 4. 接口、错误与日志

- 机构、正式指标、期间、单位和来源身份应贯穿请求、执行、证据与交付；不能用“有权限”或“查询成功”代替目标一致性。
- 正常缺数、部分可用、参数错误、权限失败、外部服务异常分别表达。恢复针对原因且有预算，未知错误不能自动变成可重试参数错误。
- 业务正文、数据明细、内部上下文和诊断字段保持边界。日志保留请求关联和必要根因，不记录令牌、密码、完整敏感输入或响应。
- 业务知识提供解释和分析方法，正式指标目录维护口径，实时查询提供本轮事实；不得混用三者的职责。
- 修改协议或持久化结构时，核对调用方、历史数据、部署顺序及兼容/回退办法，不静默改变契约。

## 5. 测试与评审

- 修复缺陷先建立能暴露根因的回归，断言实际条件、来源、数值和状态，不只断言成功码或工具被调用。
- 测试按改动选择正常、拒绝和必要异常路径。只在模型、网络、数据库等真实边界隔离，不把被测逻辑全部替换成桩。
- 单元与契约测试可以用隔离样本；业务效果验收使用授权的真实数据和模型。报告分别说明隔离检查、历史记录和本次实际问答，不能互相替代。
- 前端交互修改核对桌面操作、失败状态及刷新恢复。性能对比记录代码、模型、配置、数据与缓存条件，避免把一次耗时当作稳定性能。
- 评审检查职责归属、重复实现、类型契约、错误与取消、兼容影响、有效测试及范围控制。注释解释原因和约束，原则上用中文；不重复代码，不保留对话流水和生成声明。

## 6. 环境与安装

- 本地开发检查使用 Node 22.13 以上的 22.x 或 24.x，本次验证为 24.14.0；ESLint 10 的要求比现有 Agent `engines >=22.12` 略高。本轮不更改生产运行声明，离线包锁定的 22.23.2 也满足检查工具要求。运行检查前执行 `node --version`；当前机器默认 shell 可能选择旧版本，不把旧版本下通过测试当作兼容性验证。
- Python 应用最低版本由 `backend-next/pyproject.toml` 的 3.11 决定；现有启动文档支持 3.11–3.13，离线包另锁定 3.12.14。本次本地验证为 3.11.15，不代表完成所有版本矩阵验证。
- 根 `pyproject.toml` 是现有未提交的空依赖项目元数据，声明 3.12；不能作为后端依赖安装依据。本轮保留该文件，安装与检查明确在 `backend-next` 执行，不在根目录执行不带项目路径的 `uv sync`。
- 两个 Node 包分别使用 `npm ci`；后端开发环境在 `backend-next` 使用 `uv sync --locked --extra dev --inexact`。`--inexact` 保留环境已有的额外包，但仍会按锁同步已锁依赖，因此不在运行中的共享环境随意同步。
- 新增或升级依赖先检查现有能力、官方兼容信息、许可证及运行成本，只更新必要依赖及锁文件。开发检查工具不加入生产运行依赖。

## 7. 本地检查入口

在仓库根目录执行；入口不修改源码、不安装依赖、不启动服务，不调用模型或业务数据库。会继续收集其他检查的结果，只要任意一项失败，最终退出码就是非零。

```sh
# 全部模块的 lint、类型与格式检查
python scripts/check_quality.py

# 按改动模块或检查类别执行
python scripts/check_quality.py --scope agent frontend --checks lint typecheck
python scripts/check_quality.py --scope backend --checks lint typecheck format

# 后端解释器不在默认 .venv 时明确指定
python scripts/check_quality.py --scope backend --backend-python /absolute/path/to/python

# 检查入口自身的回归
python -m unittest discover -s scripts -p test_check_quality.py
```

Node 包也可各自在目录内执行 `npm run lint`、`npm run typecheck`、`npm run format:check`。测试与构建继续使用原来的 `npm test`、`npm run build`，按受影响范围执行。

后端检查命令在 `backend-next` 执行：

```sh
python -m ruff check --config pyproject.toml src scripts verification alembic_goldendb conftest.py
python -m ruff format --check --config pyproject.toml src scripts verification alembic_goldendb conftest.py
python -m mypy --config-file pyproject.toml
```

统一入口另检查根目录的 `scripts/check_quality.py` 和其测试。mypy 默认检查 `src`，测试、运维脚本和迁移暂未纳入类型检查；lint/格式检查的覆盖范围更大，不把二者混称为全仓类型检查。

修改检查入口本身时，另执行 `python -m mypy --strict --config-file backend-next/pyproject.toml scripts/check_quality.py scripts/test_check_quality.py`。该入口使用 Python 标准库编排子进程，不另写静态分析规则。

用户已确认当前没有 CI，本阶段交付本地检查入口。后续接流水线直接调用相同命令，并保留其非零退出码，不另实现一套规则。

## 8. 历史问题与完成标准

- 初次检查暴露的历史告警保留在基线记录中。检查工具落地和代码质量达标分别记录；检查仍返回非零时，不宣称仓库全部通过。
- 新增检查配置、脚本及已整改模块应通过相应检查。现有告警按模块和影响分批清理，不要求本轮做全仓格式化，不自动更新忽略基线接受新错误。
- 确需局部例外时，在最小范围说明具体规则、原因和退出条件，并在评审中核对；禁止无依据的目录排除、全局忽略或大量类型断言。
- 正确性问题优先于排版。每批代码整改明确旧实现去留、实际验证、遗留范围和回归风险；通过检查与测试仍不能替代业务事实验收。
