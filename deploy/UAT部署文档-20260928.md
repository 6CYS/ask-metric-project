#### 1.3.1 同一环境新增服务器：复用原密钥和加密配置

**只是更换或增加服务器，仍属于同一 UAT 环境时，执行本节，跳过整个 1.4 节。** 全量安装应用不代表要重新生成密钥。原 `config-sm4-uat.key` 与原配置中的 `ENC[SM4:v1:...]` 必须配套使用。

在新服务器以 `appuser` 执行。下面假设旧服务器使用默认密钥路径；先核对旧 `backend.env` 的 `ASK_METRIC_CONFIG_SM4_KEY_FILE`，如有不同，同步修改 SCP 源路径。将 `<旧服务器IP>` 替换为实际地址：

```bash
CONFIG_ROOT=/home/appuser/ask-metric-config-uat
SM4_KEY_FILE=$CONFIG_ROOT/config-sm4-uat.key

mkdir -p "$CONFIG_ROOT"
chmod 700 "$CONFIG_ROOT"

# 已存在时不覆盖，先与旧服务器核对哈希。
if [ -e "$SM4_KEY_FILE" ]; then
  echo '密钥文件已存在，请先确认与同环境旧服务器一致'
else
  scp appuser@<旧服务器IP>:/home/appuser/ask-metric-config-uat/config-sm4-uat.key "$SM4_KEY_FILE"
fi
test -s "$SM4_KEY_FILE"
chmod 600 "$SM4_KEY_FILE"
sha256sum "$SM4_KEY_FILE"
```

在旧服务器执行以下命令，与新服务器输出的哈希比较；实际路径不同则相应修改。**哈希一致后再继续部署**，不一致时停止核对来源，不覆盖密钥或重做加密来绕过问题。

```bash
sha256sum /home/appuser/ask-metric-config-uat/config-sm4-uat.key
```

若不能使用 SCP，通过堡垒机的受控文件传输复制同一文件，再在新服务器设置 `chmod 600` 并比较哈希。不将密钥内容粘贴到聊天、文档或日志中，不放入部署压缩包。

通过同样的受控方式同步旧服务器的 `backend.env` 及其引用的实际运行配置文件。新服务器的 `backend.env` 中，密钥项指向复制后的实际路径：

```dotenv
ASK_METRIC_CONFIG_SM4_KEY_FILE='/home/appuser/ask-metric-config-uat/config-sm4-uat.key'
```

- 复用原应用库、查询库、Nacos、JWT、追问签名、SM2 私钥及模型密钥等已确认的配置；原 `ENC[SM4:v1:...]` 值直接使用，不重新加密，也不重新生成 JWT、追问密钥或 SM2 密钥对。
- 一并同步 `MODEL_CONFIG_PATH`、`PROMPT_CONFIG_PATH`、`SEMANTIC_CONFIG_PATH`、`QUERY_TEMPLATE_CONFIG_PATH`、`SQL_RESOURCE_DIR` 引用的文件或目录。现场模型文件即使叫 `model.json`，仍以实际配置路径为准，保留 `send_response_format=false`。
- 修改新节点的 `NACOS_INSTANCE_IP`、唯一的 `NACOS_INSTANCE_ID`、日志节点标识及绝对路径，尤其本次发布目录、虚拟环境和 `TEST_CENTER_BASELINE_PATH`；`MODEL_SECRET_ENV_PATH` 指向新服务器实际使用的 `backend.env`。
- 共享数据库已有完整主数据时跳过 1.8 节同步，不重复初始化数据库或创建账号。后续 1.5、1.6 节用于逐项核对，不整段覆盖已复制的现场配置；继续完成 1.7 节检查和启动验收。

以后只有新增或修改了明文配置值时，才使用这份原密钥重新加密该项，其他原密文保持不变：

```bash
"$PY" -m ask_metric encrypt-config --key-file "$SM4_KEY_FILE"
```

### 1.4 首次生成密钥并加密（仅新建独立环境）

本节会生成新的 SM4、SM2、JWT 和追问密钥。**同一环境不同服务器按 1.3.1 复用原密钥；原服务器增量升级按 2.3.1 保留原密钥，两种情况均不执行本节。**

```bash
SM4_KEY_FILE=$CONFIG_ROOT/config-sm4-uat.key
test ! -e "$SM4_KEY_FILE"
openssl rand -hex 16 > "$SM4_KEY_FILE"
chmod 600 "$SM4_KEY_FILE"
"$PY" "$RELEASE_ROOT/backend/runtime/scripts/generate_sm2_keypair.py" \
  --output-dir "$CONFIG_ROOT/private" --output sm2-uat.env
```

分别执行两次 `openssl rand -hex 48` 得到两个互不相同的 JWT、追问签名密钥。每次执行下面的命令隐藏输入一个明文值，取输出的完整 `ENC[SM4:v1:...]` 填到对应环境项：

```bash
"$PY" -m ask_metric encrypt-config --key-file "$SM4_KEY_FILE"
```

需要加密的项目为应用库 URL、查询库 URL、Nacos 密码、JWT、追问签名、SM2 私钥及启用功能的模型/管理密钥。SM2 私钥取刚生成的 `private/sm2-uat.env`；导入完成后按现场流程保管或清理临时明文材料。数据库 URL 整条加密，其明文格式为：

```text
mysql+pymysql://<账号>:<百分号编码后的密码>@<数据库IP>:<端口>/<库名>?charset=utf8mb4
```

URL 密码中的 `@`、`#`、`/` 等须百分号编码。应用库使用读写账号，数据湖使用数据库侧只读账号；不能复制其他环境的密文与主密钥。

### 2.7 启动新后端并发布同版前端

现场使用 start/stop 脚本时，先备份实际启停文件及公共函数到 `$BACKUP_ROOT`，再编辑脚本中的路径（拆分脚本两边一致）：

沿用现场已经验证的停止/启动入口；脚本方式与下面的 nohup 方式二选一，禁止重复启动。`release_root` 下面必须有 `backend/runtime`，`venv_root` 下面必须有 `bin/python`。公共函数错误分支如仍有未加引号的 `${Msg}**`，参照包内 `service-control/BaseFunction.kshrc` 修正并执行 `sh -n`；不要覆盖现场其他定制内容。

**启停脚本还必须核对配置加载环境，不能只修改路径。** 旧参考入口在启动 Gateway 时会 `set -a; . ./conf/application.env; set +a`；在同一 Shell 中继续启动 Python，会继承 Gateway 导出的同名变量。当前仓库 `java_restart.sh` 已将整个 `start_gateway()` 改为子 Shell，并在后端启动前加入以下配置检查；此前生成的压缩包及现场拆分脚本不会自动更新，须检查实际内容。现场修正时，将函数的 `start_gateway() { ... }` 改为 `start_gateway() ( ... )`，保证配置加载、Java 启动和 Gateway PID 写入都在括号内，不能只把配置加载单独放进子 Shell。

在实际启动脚本中，所有环境加载完成之后、Python 的 `nohup` 之前，加入下面的检查。示例用于仓库 `start_backend()` 函数内（失败用 `return 1`）；现场独立 start.sh 顶层使用 `exit 1`。这段检查必须运行在后端即将继承的环境中，仅在外部终端单独检查不够；全量使用脚本启动时同样适用：

```sh
"${venv_root}/bin/python" "${release_root}/ops/intranet_deploy.py" \
  validate-config --config "${config_file}" || return 1
```

与 1.7.1 联用：前者明确要求注册开启，以上检查阻止实际启动环境与文件不一致。出现冲突按报出的变量名修正来源，不让脚本打印“配置通过”后继续带着另一份环境启动。

现有服务管理平台的 Python 路径改为本次 `$PY`，工作目录改为 `$RELEASE_ROOT/backend/runtime`，配置文件仍为 `$CONFIG_FILE`；只改软链接或工作目录不够。手工启动为：
